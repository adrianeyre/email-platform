## 1. What the app's own connection can do

`docker-compose.yml:8` gives `api`, `worker` and `migrate` `postgres://email_platform:…@postgres:5432/email_platform`; `backup` and `restore` log in with `PGUSER: email_platform` (`:82,105`); `postgres` is created with `POSTGRES_USER: email_platform` (`:27`), which the official image makes the bootstrap superuser. `src/lib/database.ts:18-19` opens that URL as is. No migration in `src/drizzle/` creates a role, grants or revokes anything, or enables row-level security.

Over the probe world's pool (the same URL shape):

- `select rolsuper, rolbypassrls, rolcreaterole from pg_roles where rolname = current_user` → `true, true, true`.
- Every base table in `public`, `pgboss` and `drizzle` answers `select count(*)`, the migrations ledger `drizzle.__drizzle_migrations`, `public.sessions` and `public.api_keys` included. Inside a transaction, `drop table messages cascade` succeeds (rolled back). So whatever a later fix adds (row-level security, a trigger, a revoked grant) this connection can turn off.
- `copy … from program 'id'` → `uid=70(postgres) gid=70(postgres) …`: a shell in the `postgres` container as the data directory's owner. From there the data files, `pg_hba.conf` and the WAL are readable and writable, and every container on the `database` network (`api:4320`, `worker`, `backup`) is reachable. The `database` network is `internal`, so `postgres` itself has no way out; it reaches the containers that do.
- `printenv POSTGRES_PASSWORD` from that shell prints nothing: the image's entrypoint does not pass it to the server process. Refuted. The value is still in the container's configuration, readable by anyone who can `docker inspect` (I4).
- `create role d1_probe_role login password …` succeeds (dropped again). A bug or a password holder can mint a login that survives rotating `POSTGRES_PASSWORD`.
- `select rolpassword from pg_authid` returns 17 rows; the app's own is a `SCRAM-SHA-256$…` verifier (not reproduced here). That verifier is enough to attempt an offline guess of `POSTGRES_PASSWORD`, and its strength is unchecked (H10, I3).

## 2. Queries a request can steer

Every query was read (`grep` for `sql\``, `sql.raw`, `ilike`, `like(`, `.orderBy`, `.execute`, `.query`under`src/`, tests and `pen-test/` excluded):

- `src/sending/message-routes.ts:167-172`: the log search. The term is trimmed, `\`, `%` and `_` are escaped with `\` (Postgres's default `LIKE` escape), wrapped in `%…%` and bound as a parameter inside Drizzle's `sql` template. Searching `%`, `_`, `' or '1'='1` and `\` as the `victim` User returns `total: 0` each, against a non-zero total for no search. Refuted.
- `message-routes.ts:173-181,189`: `status` is a literal union; `after` / `before` are `date-time` strings bound as parameters; `orderBy(desc(createdAt), desc(id))` is fixed; `page` becomes a bound `offset`. Nothing chooses a column or direction. But see 2b.
- `src/templates/template-routes.ts:132-140`: `like(templates.slug, `${base.slice(0, 80)}-%`)` where `base` is `slugify(name)`, which can only hold `[a-z0-9-]` (`slug.ts`), so no `%` or `_` reaches the pattern. Refuted.
- `http-server.ts:160` (`select 1`) and the two `check` constraints in `schema.ts:71,97` take no input. Every other query is Drizzle's builder with bound values.

**2b, odd filters:** `GET /app/messages?page=100000000000000000000` passes `Type.Integer({ minimum: 1 })` and `(page - 1) * 50` reaches Postgres as an `offset` past `bigint`; `?after=0000-01-01T00:00:00Z` passes `format: "date-time"` and reaches Postgres as year 0, which `timestamptz` refuses. Both answer 500 (the fixed body, `http-server.ts:96-131`). Nothing is read or written; the gap is that the refusal comes from the database rather than above it. Only a signed-in User can send these (the `/app` hook). If B1's identities × routes matrix or I1's error handler probes file the same 500s, this folds into theirs.

## 3. Who holds `POSTGRES_PASSWORD`, and which networks they sit on

`docker compose --env-file /dev/null -f docker-compose.yml --profile restore config --format json`, with a placeholder password, read for every service whose environment carries that placeholder:

| Service    | Holds it as            | Networks              | Way out                   | Needs a way out for                                 |
| ---------- | ---------------------- | --------------------- | ------------------------- | --------------------------------------------------- |
| `postgres` | `POSTGRES_PASSWORD`    | `database`            | No (`internal: true`)     | —                                                   |
| `migrate`  | `DATABASE_URL`         | `database`, `default` | Yes                       | Nothing: it only talks to Postgres                  |
| `api`      | `DATABASE_URL`         | `database`, `default` | Yes, and publishes `4320` | Serving the LAN; `POST /app/settings/test` (H6, I5) |
| `worker`   | `DATABASE_URL`         | `database`, `default` | Yes                       | The SMTP provider                                   |
| `backup`   | `PGPASSWORD`           | `database`, `default` | Yes                       | The rclone remote                                   |
| `restore`  | `PGPASSWORD` (profile) | `database`, `default` | Yes                       | The rclone remote                                   |

Six of six hold the one superuser password; five sit on `default`, which is not internal. `migrate` needs no way out at all. `backup` and `restore` need one, so for them the defence has to be the role, not the network: today a compromise of the backup image (`apk add age rclone` by name, H14) holds a superuser login and an open route out.

## 4. Least privilege, proposed (filed as the fix #158, against #121, #138 and #139)

One owner role that nobody runs as, and one login per container, none of them superuser:

- **`email_platform_owner`** (`NOLOGIN`): owns the `public`, `drizzle` and `pgboss` schemas and every table in them. Nothing logs in as it.
- **`email_platform_migrate`** (login, member of the owner): runs `drizzle-orm` migrations and pg-boss's own install/migrate (`createJobQueues`, `jobs.ts:42-52`). Not superuser, no `CREATEROLE`, no `pg_execute_server_program`, `pg_read_server_files` or `pg_write_server_files`. On the `database` network only.
- **`email_platform_api`** (login): `USAGE` on `public` and `pgboss`; `SELECT, INSERT, UPDATE, DELETE` on the `public` tables it serves (`users`, `sessions`, `api_keys`, `settings`, `email_parts`, `configurations`, `templates`, `messages`, `message_attachments`); in `pgboss`, only what `boss.send` needs to enqueue. No `drizzle` schema. Start pg-boss with `migrate: false` and `createSchema: false` (both in pg-boss 12.38.2's `types.d.ts:145-146`) so it needs no DDL; today `startApi` calls `boss.start()`, which installs and migrates (`src/index.ts:37-44,56-59`).
- **`email_platform_worker`** (login): `SELECT` on `messages`, `message_attachments`, `settings`, `templates`, `email_parts`, `configurations`; `UPDATE` on `messages`; `DELETE` on `messages` and `message_attachments` for Retention (`src/sending/retention.ts`); DML on the `pgboss` tables to fetch, complete and schedule jobs; pg-boss with `migrate: false`, `createSchema: false`.
- **`email_platform_backup`** (login): member of `pg_read_all_data` (enough for `pg_dump`), nothing else; it can't write, drop or create.
- **`restore`**: run by hand as `email_platform_migrate` into an empty database, its password supplied for that run only rather than living in `.env` beside the others.
- **The bootstrap superuser** (`POSTGRES_USER`) keeps a password only the `postgres` container holds; no service's environment names it.
- Optionally, row-level security is not needed for one tenant; the gain is that each later control (a revoke, a trigger, an audit table) can't be undone by the connection it guards.

Each grant is checked by a probe that this file's `it.fails` tests turn into: the app's role is not a superuser, can't `COPY … PROGRAM`, create a role, read `pg_authid` or drop a table, and each service logs in as its own role.

## Checks every scope issue carries

Applied:

- **Run the probes against a real Postgres.** Every SQL probe runs in the gated world over the app's own connection string, against the image and owner Compose uses.
- **Odd input stops above the database.** Applied to the log's filters, the only request-steered query values beyond uuids: `page` past `bigint` and the year 0000 reach Postgres (2b). NUL bytes in `search` and the `/v1` inputs are S1's.
- **Every refusal comes from a closed set.** The 2b refusals are the fixed 500 body, so no driver text leaks; the status is still a 500 for a well-formed request.
- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** `POSTGRES_PASSWORD` is held in plain text by six services for their whole life, five of them on a network with a way out (3); its SCRAM verifier is readable by every one of them (1f).
- **Configuration fails closed.** Compose refuses to render without `POSTGRES_PASSWORD` (`:?`); its strength is I3's.
- **A test that passes either way proves nothing.** Each `it.fails` was run as a plain `it` and fails on its own assertion (`rolsuper`, a resolved `DROP`, a resolved `COPY`, a resolved `CREATE ROLE`, a resolved `pg_authid` read, a 500, a network list, a set of one user).

Not applied, and why:

- **Refusals give nothing away**, **middleware matches by segment**, **internal headers**: no route of D1's own; B1, A1 and I1.
- **An idempotency key is bound to its payload and owner**: S2.
- **Logs are a copy of the data**: D2. The database's own log was not swept.

Cross-references: who can `docker inspect` the password and the containers' hardening are I4's (H14); backups and the rclone credential are D3's (H13); SMTP test as a port scanner from `api` is I5's (H6).
