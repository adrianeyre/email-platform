# D2: the log, Retention and the personal data it holds

The findings note for scope issue #100 (D2) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H2 and the log half of H12; the backup half of H12 is D3's. It names exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `d81eaa9`, and the [fixtures](../fixtures.md) by handle and id. No credential, cookie, key or seed appears here; every link named is a fixture's synthetic one on `wizzaroo.pen-test.invalid`.
- **The probes** are `src/pen-test/probes/d2.test.ts`, in the gated run against a real Postgres and Mailpit (`startProbeWorld`). The container-log sweep runs the `api` role in a child process from `src/pen-test/probes/d2-log-capture.ts` (built as `startApi` builds it, `isLogging: true`, no UI) and the real `worker` role (`src/index.ts worker`), and reads their stdout and stderr and `docker logs` of the Postgres container. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a passing test.
- **Left to other scope issues:** the second Application's key reading a Wizzaroo Message's summary (recipients, subject, status) through `GET /v1/messages/:id` is K1's ("reading other app's Messages"); see K1. The database login being the Postgres superuser is D1's; see D1. Backups, and restoring them, are D3's; see D3. Any User changing Retention with no record of who did is part of A2's/H5's "one User is every User"; see A2.

## Probe 1: the link in each stored body

Six of the fifteen Built-in emails carry a link variable (`builtInEmails`' `sampleVariables` ending `Url`): `wizzaroo-confirm-your-email-address` (`confirmationUrl`), `wizzaroo-reset-your-password` (`resetUrl`), `wizzaroo-teacher-invite` and `wizzaroo-parent-invite` (`inviteUrl`), `wizzaroo-family-device-signed-in` and `wizzaroo-family-join-request` (`parentPageUrl`). The first four are credentials: the guide's copy says each "works once, and expires after" `linkLifetime` / `inviteLifetime` (24 hours in the samples, `src/templates/built-in-emails.ts:250,262,292,323,356`). `parentPageUrl` is a page link that needs a sign-in; the fixtures give it a synthetic token too, so the probe treats it the same.

What was sent: for each of the six, `POST /v1/messages` with the `wizzaroo` key, `templateSlug`, a fresh recipient on `families.pen-test.invalid`, and each link variable set to `https://wizzaroo.pen-test.invalid/<path>?token=<32 random hex>`. Each answered 202; `world.deliver(id)` ran the send worker once through Mailpit and returned `sent`.

What came back: in every row, after it was `sent`, `html` holds `href="<the link>"` (Handlebars-escaped as `token&#x3D;…`, which a browser undoes), `text` holds the link verbatim, and Mailpit's copy of the delivered HTML holds the same link. So the stored link is byte for byte the credential Wizzaroo handed over and the addressee received; nothing marks, truncates or hashes it (`src/sending/accept-message.ts:246-257` inserts `...content`; `src/lib/schema.ts:161-162`). Whether it still _works_ is up to Wizzaroo's expiry, which the platform neither knows nor enforces: for 24 hours at least, the log row is a working way into the account.

## Probe 2: who can read it

The fixture `wizzaroo-reset-your-password` Message (status `sent`, id `7e570000-0000-4000-8000-000600000002`):

| Reader                                  | Request                  | Status | Gets the link?                                 |
| --------------------------------------- | ------------------------ | ------ | ---------------------------------------------- |
| User `victim`                           | `GET /app/messages/:id`  | 200    | Yes, in `html` and `text`                      |
| User `colleague`                        | `GET /app/messages/:id`  | 200    | Yes                                            |
| Key `wizzaroo`                          | `GET /v1/messages/:id`   | 200    | No: summary only (`summariseMessage`, no body) |
| Key `secondApp`                         | `GET /v1/messages/:id`   | 200    | No body; but recipients and subject (see K1)   |
| No one                                  | either route             | 401    | No                                             |
| The platform's database login           | `select … from messages` | —      | Yes: all six fixture links, in plain text      |
| Anyone holding a backup and the age key | D3                       | —      | Yes (see D3, probe 1)                          |

`GET /app/messages/:id` returns `html` and `text` to any signed-in User (`src/sending/message-routes.ts:203-214`); `GET /v1/messages/:id` returns `summariseMessage` only (`:127-138`, `:73-88`). The UI's Logs page opens a row "as it was sent" (`docs/guide/logs.md`), which is this route.

Severity: H2 opened at high. Read literally, the PRD's critical row ("a Wizzaroo account link reaches anyone but its addressee") is met by any User opening the row; it is proposed at **high** because the reader holds a User, and ADR 0008 names the exposure without accepting it. The owner may raise it.

## Probe 3: Retention at 1 and at 3,650

`applyRetention` deletes `messages` with `created_at < now − logRetentionDays` and nothing else (`src/sending/retention.ts:8-19`). Any User sets 1 to 3,650 with `PUT /app/settings` (`src/settings/settings-routes.ts:46-48`); the probe set both as `colleague`, answered 200 each time.

**At 1 day** (run at about 21:45 UTC): of the 21 fixture Messages, 18 were older than the cutoff, in all three statuses (queued, sent and failed), and all 18 were deleted, `deletedMessages` matching exactly. The probe also aged the second-app queued Message that holds the fixture attachment (`7e570000-0000-4000-8000-000700000001`) to 10 days: its attachment went with it (`message_attachments.message_id … on delete cascade`, `src/lib/schema.ts:182-184`). A Message the probe sent through `/v1` and aged 10 days was deleted, and its `pgboss.job` row stayed, holding exactly `{"messageId": "<id>"}`. pg-boss removes that row on its own clock (`keep_until` 14 days for an unfinished job, `deletion_seconds` 7 days after completion, `node_modules/pg-boss/dist/plans.js:85-94`), and it holds no personal data. Attachments of a sent or finally-failed Message are already deleted by the worker (`src/sending/send-worker.ts:75-77,92-95`). Refuted: Retention deletes what it says.

Notes: Retention deletes a _queued_ Message as readily as a sent one, so a Message stuck in the queue past Retention is never sent (the job then finds no row and returns `skipped`). Not a security weakness; recorded for the owner. Deleted rows also stay in Postgres's heap and WAL until vacuum and checkpoint reuse them; read, not probed.

**At 3,650 days**: the sweep deleted nothing. The sent reset Message, aged to 120 days, still held its link in `html` and `text`: 119 days past its 24-hour life. Arithmetic: at the default 90 days a 24-hour reset link sits in the log 89 days after it can be used, at 3,650 days 3,649; even at the minimum of 1 day it sits there its whole working life. The range 1-3,650 is in code only: `docs/guide/logs.md` and `docs/guide/delivery-and-access.md` say "90 days to start with" and give no bound, and ADR 0008 speaks only of "90 days by default". No record says which User set it.

## Probe 4: the container-log sweep

What was sent, to the API in a child process with production's logger (`logger: parts.isLogging`, `src/api/http-server.ts:89`; `isLogging: true`, `src/index.ts:66`), signed in as `victim`:

1. `GET /app/messages?search=parent1@families.pen-test.invalid`: 200.
2. `GET /app/messages?search=parent2@families.pen-test.invalid%00`: 500 `internal_error` (Postgres refuses the NUL byte: `invalid byte sequence for encoding "UTF8": 0x00`).
3. `PUT /app/settings` pointing the SMTP provider at a second Mailpit that accepts only `@allowed.pen-test.invalid` (`MP_SMTP_ALLOWED_RECIPIENTS`).
4. Two `POST /v1/messages` with the `wizzaroo` key, `wizzaroo-reset-your-password`, each with its own random token: one to a refused recipient on `families.pen-test.invalid`, one to an allowed one. Both 202. Then the real worker (`src/index.ts worker`) ran until the first was `failed` (550, permanent) and the second `sent`.

What the logs held:

| Log                        | Searched address                                                                                           | Failed query's parameters                                                                                                                                                                                                               | Send recipients                            | Link tokens | Body                                                                                                              |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ----------- | ----------------------------------------------------------------------------------------------------------------- |
| `api` (pino, stdout)       | **Yes**: `"url":"/app/messages?search=parent1%40families.pen-test.invalid"` in the `incoming request` line | **Yes**: the `api.request.failed` line's `err` holds `"message":"Failed query: select count(*) from \"messages\" where (… ilike $1 …)\nparams: %parent2@families.pen-test.invalid\u0000%,…"`, and `query`, `params` and the stack again | No (`POST /v1/messages` logs the URL only) | No          | No                                                                                                                |
| `worker` (`writeLog`)      | —                                                                                                          | —                                                                                                                                                                                                                                       | No                                         | No          | No: `{"event":"message.send.finished","messageId":…,"outcome":"failed"}` and `"sent"` only (`src/index.ts:92-95`) |
| `postgres` (`docker logs`) | No                                                                                                         | No: `ERROR … 0x00`, `CONTEXT: unnamed portal parameter $1` and the `STATEMENT` with `$1` placeholders only                                                                                                                              | No                                         | No          | No                                                                                                                |

The error handler logs the whole error (`request.log.error({ err: error }, "api.request.failed")`, `src/api/http-server.ts:127`), and Drizzle's `DrizzleQueryError` carries its parameters in its message and as an enumerable `params`, so any failing query writes its values to the log: a search term, and on other routes whatever the failing query held. The stack also names the server's absolute paths and the log line its hostname. The worker's failed send wrote the provider's reply to `messages.error` (`Can't send mail - all recipients were rejected: 550 5.1.0 Requested action not taken: mailbox unavailable`), with no address in it from this provider; another provider's reply may name the recipient.

`docker-compose.yml` sets no `logging:` on any service, so the `json-file` driver keeps these lines with no size or age bound until the container is removed (a deploy that rebuilds the image recreates it; one that doesn't, doesn't). Retention never reaches them. A search is how a User finds a person's emails, so the log becomes a list of the people Users looked for, outliving the Messages themselves.

## Probe 5: every copy of a Message's recipients and body

After the sweep's two sends, the probe searched every column of every base table in every schema (`public`, `pgboss`, `drizzle`) for the recipient, the link token and the Message id:

| Needle             | Found in                                                                             |
| ------------------ | ------------------------------------------------------------------------------------ |
| Sent recipient     | `public.messages.to`, `.html`, `.text` (the reset's greeting names the address)      |
| Sent link token    | `public.messages.html`, `.text`                                                      |
| Refused recipient  | `public.messages.to`, `.html`, `.text`                                               |
| Refused link token | `public.messages.html`, `.text`                                                      |
| Sent Message id    | `public.messages.id`, `pgboss.job.data`, `pgboss.job_common.data` (the job, id only) |

Every copy, in and out of the database:

1. `messages`: from, to, cc, bcc, reply-to, subject, `html`, `text`, the provider's error; until Retention.
2. `message_attachments`: the attachment bytes until the Message is sent or finally fails.
3. `pgboss.job`: the Message id only, 7-14 days.
4. The `api` container log: searched addresses and any failing query's parameters, unbounded (probe 4).
5. Postgres's heap, WAL and the `postgres-data` volume: deleted rows until vacuumed (read, not probed).
6. The nightly backups: everything in 1-3, 14 more nights, and back again on a restore (D3).
7. The SMTP provider and the recipient's mailbox: outside the platform.
8. A User's browser while the Logs page is open.

**Does the platform need the body once it is sent?** No code reads `html` or `text` after the worker hands them to Nodemailer (`src/sending/send-worker.ts:53-63`) except `GET /app/messages/:id` for the Logs page. A Message that is `failed` is never sent again (no route resends one), so its body isn't needed either. The Logs page's "see the email as it was sent" is the only consumer, and the subject, recipients, Template and status answer "was it sent?" without the body. Keeping the rendered body is a product choice (ADR 0005's "simple log"); keeping it with the link in it is what makes the log a box of keys.

## Checks every scope issue carries

Applied:

- **Logs are a copy of the data.** Swept the `api`, `worker` and `postgres` logs (probe 4) and counted them in Retention: they aren't. Confirmed.
- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** Wizzaroo's links are kept in plain text for Retention, long past their 24-hour life (probes 1, 3, 5). Confirmed.
- **Every refusal comes from a closed set.** The NUL-byte search answered 500 `internal_error` / `Something went wrong`: no driver text reached the caller, but a well-formed request (a string query parameter) got a 500, so the check fails on the status. Recorded; the odd-input stop belongs with S1's odd-input checks (see S1), so not proposed here.
- **Odd input stops above the database.** The same NUL byte reached Postgres. See S1.
- **Refusals give nothing away.** `GET /v1/messages/:id` and `GET /app/messages/:id` with no credential answer 401 for a Message that exists (probe 2b); the not-found comparison is B1's.
- **Run the probes against a real Postgres.** Every probe does; the log sweep runs the real `worker` role.
- **A test that passes either way proves nothing.** Every `it.fails` was run as a plain `it` and failed on its property assertion (a token found, a log line found, a Retention bound missing), never on setup.

Not applied: **an idempotency key is bound to its payload and owner** (S2's), **internal headers** and **middleware matching by path** (A1's and B1's; no header or path is read on this surface), **configuration fails closed** (D1's and B1's), **nothing is left to a collaborator to bound** (the only lists here are the log's 50-row pages and Retention's 1-3,650 range, both bounded in code; recipient limits are S1's).

## Since the probe

#116 is fixed in the second round's pull request (fixed, unverified). A sent or finally failed Message keeps no html or text, and migration 0006 drops the bodies already kept. Its `today_` tests are now `(regression)` tests, and its `it.fails` are plain `it`s, in `src/pen-test/probes/d2.test.ts`. #147's link half passes too, but the 3,650-day maximum and its missing documentation stay open.

#126 is fixed in the third round (fixed, unverified). The `api`'s request log keeps a request's path but replaces any query string with `?[redacted]` (on every route, not only `/app/messages`: a query string is where a search term goes), and every error is logged through `describeErrorForLog` (`src/lib/log.ts`): its type, code and stack frames, never its values. A `DrizzleQueryError` is `Failed query` with no SQL or parameters, and its Postgres cause is `Database error <SQLSTATE>` with the routine and constraint names but not Postgres's own message, which quotes the offending value in some errors. Fastify's default 404 handler, which logged `Route GET:<url> not found` with the query string, is replaced by the app's own when no UI is served. The worker's `jobs.error` lines use the same shape. `docker-compose.yml` gives every service the `json-file` driver bounded to three 10 MB files (`x-logging`); Docker bounds by size, not age, and the `api` health check alone fills that in about two weeks, so a line goes well within the default 90-day Retention ([Deploying](../../operations/deploying.md#logs), [Logs](../../guide/logs.md#the-containers-own-logs)). In `src/pen-test/probes/d2.test.ts` both of #126's `it.fails` are plain `it`s, and its three `today_` tests are `(regression)` tests: the bounded Compose logs, the redacted request URL, and the failed query logged by its code alone. `src/lib/log.test.ts` covers the error shape.

#147 is fixed in the fourth round (fixed, unverified), by [ADR 0012](../../architectural-decision-record/0012-a-message-body-is-kept-at-most-seven-days.md). A Message's body is kept at most seven days whatever Retention is: the daily Retention job (`applyRetention`, `src/sending/retention.ts`, `messageBodyMaxDays`) drops the html, text and attachments of every Message older than that, and marks one still `queued` (a stopped worker, a lost job) `failed` with `Not sent within 7 days, so its body was dropped`, so it is never sent late. `restore.sh` does the same after a restore. Every link Wizzaroo sends is dead well within seven days, so the bound is tied to the links' life and not to Retention. Retention's range, 1 to 3,650 days, 90 by default, is documented in [Logs](../../guide/logs.md#retention), [Delivery and access](../../guide/delivery-and-access.md) and the glossary, and recorded as a decision in ADR 0012. No schema change: since #116 every sent or failed body is dropped already, so a credential-bearing flag on Templates was considered and rejected. The probe's `(regression)` test and plain `it` were already turned with #116; a new `(regression) at 3,650 days, a reset left queued for eight days, as by a stopped worker, loses its link and is failed, never sent late (#147)` covers the queued case, and `src/integration.test.ts` checks the bound with attachments.
