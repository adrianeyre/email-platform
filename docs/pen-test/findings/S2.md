# S2: the Idempotency-Key

The findings note for scope issue #97 (S2) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H7. It names exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `d81eaa9`, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are the tests under `pen test S2 (#97): the Idempotency-Key` in `src/pen-test/probes/s2.test.ts`. They run in the gated run against a real Postgres and Mailpit (`startProbeWorld`). Each probe uses a key of its own (`s2-<label>-<uuid>`), so no probe sees another's Message. `wizzaroo` sends the Built-in `wizzaroo-reset-your-password` with a synthetic link on Wizzaroo's fixture origin. `secondApp` sends `second-app-order-shipped`. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a passing test.
- **Left to other scope issues:** any API Key reading any Message by id (`GET /v1/messages/:id`) is K1's. This note covers only the Idempotency-Key route to another Application's Message. NUL in the header is filed under S1's NUL finding and pinned here.

## How a key is looked up

`messages.idempotency_key` is `text … unique` across the whole table (`src/lib/schema.ts:170`). Nothing records which API Key sent a Message (H3). `acceptMessage` looks the key up **first**, before the body is rendered or even checked (`src/sending/accept-message.ts:212-217`). A hit returns that row as `{ isRepeat: true }`, and the route answers 200 with `summariseMessage` (`src/sending/message-routes.ts:73-88,118-123`). The summary holds `id`, `templateId`, `from`, `to`, `cc`, `bcc`, `replyTo`, `subject`, `status`, `providerMessageId`, `error`, `attempts` and `sentAt`. It does not hold `html` or `text`. A unique violation on insert is caught and answered the same way (`src/sending/accept-message.ts:274-281`).

## Probe 1: second-app repeats Wizzaroo's key

`wizzaroo` sent the reset email to a parent with a fresh key and got 202. `secondApp` then sent its own order email with the same key and got **200 with Wizzaroo's summary**, byte for byte: the parent's address, Wizzaroo's from, the reset email's subject and the status. No Message to the customer was stored.

Keys are meant to be readable things such as "an order ID with an event name" ([Sending, Idempotency](../../guide/sending.md#idempotency)), so they can be guessed in a way a Message id cannot. The fixture `wizzaroo` Message that `failed`, whose key follows the pattern `wizzaroo-<slug>-<n>`, was read the same way by `secondApp`. The answer held the recipient, subject, `status: "failed"` and the provider's SMTP error text. The body, and so Wizzaroo's link, is not in the summary (the test checks the answer holds nothing on Wizzaroo's link origin). So Wizzaroo's links are **not** exposed by this route. What is exposed is who Wizzaroo emailed, about what, when, and whether it was delivered.

## Probe 2: second-app takes the key first

`secondApp` sent its order email with a fresh key and got 202. `wizzaroo` then sent the reset email with the same key and got **200 with second-app's summary**. No Message to the parent was stored. When the worker ran, Mailpit received the one email, second-app's, for the customer. Wizzaroo's reset email is never sent. The 200 is the documented "already sent" answer, so a client that only checks for a 2xx, or that treats 200 as "the first try worked", records success. Nothing is logged anywhere. An Application that knows or guesses Wizzaroo's key pattern can silently stop a chosen password reset, Invite or security notice ("Password changed", "Two-factor turned off") from being sent.

## Probe 3: a different body, and after Retention

- **A different body:** `secondApp` sent order `SA-FIRST` with a key, then `SA-OTHER` to a different recipient with the same key, and got 200 with the first Message. Nothing went to the second recipient. A body that would have been refused (`templateSlug: "no-such-template"`) also got 200, because the key is looked up before the body is checked. The guide promises only that "a repeated key returns the first message". The PRD's check asks that "the same key with a different body is refused".
- **After Retention:** the probe moved its own Message 91 days back and ran `applyRetention` (`src/sending/retention.ts`), which deleted it. The same body with the same key then got 202 and a new Message. A key lasts exactly as long as its Message, which is Retention's 90 days by default. That is a sound retry window, so this is refuted. The guide does not say how long a key lasts, and saying so would be a one-line documentation fix. It is not filed.

## Probe 4: one key at the same moment

Two `secondApp` requests with one key were sent with `Promise.all`, three times with a fresh key each time. Every time, one got 202 and one got 200, both named the same Message, and exactly one row held the key. The loser's insert blocks on the unique index until the winner commits, fails with 23505, and is answered from the committed row (`src/sending/accept-message.ts:274-281`). There was no 500 and no duplicate. Refuted.

## Checks every scope issue carries

Applied:

- **An idempotency key is bound to its payload and its owner:** broken on both counts (probes 1-3a). This is the check H7 was written for.
- **Refusals give nothing away:** holds. Without credentials, or with the `deleted` key, a fixture's existing key and an unknown one get the same 401 status and body. The two credentials get different 401 messages ("Send an API key…" against "The API key is not valid"), but that difference is about the credential, not the key, and is K1's to judge. The 200 repeat itself does give away another Application's Message, which is probe 1.
- **Every refusal comes from a closed set:** the race gave no 500. An `Idempotency-Key` holding NUL answers 500, because Postgres refuses the lookup (SQLSTATE 22021). That is S1's NUL finding, pinned here. A repeat can also hand an SMTP provider's error text to an Application that did not send the Message (probe 1).
- **Odd input stops above the database:** a 256-character key gets 422 (`src/sending/message-routes.ts:67-71`). NUL does not stop (above).
- **Run the probes against a real Postgres:** yes. The unique index and the race need it.
- **A test that passes either way proves nothing:** each `it.fails` was run as a plain `it` and failed on its property assertion: the same id for "not the same id", 200 for 202, 200 for 409, and 500 for < 500.

Not applied, and why: **a secret is sealed or hashed** (a key is not a secret, though probe 1 shows it acts like a capability), **logs are a copy of the data** (D2), **internal headers** (the only header read here is the key itself, probed above; `X-Forwarded-For` is A1's), **middleware matching by path** (B1), **configuration fails closed** (nothing here reads configuration), and **nothing is left to a collaborator to bound** (the key is bounded at 255 characters by the schema).

## Since the probe

#119 and #120 are fixed in the second round's pull request (fixed, unverified): an Idempotency-Key is unique within its sender's Application (ADR 0009). Their `today_` tests are now `(regression)` tests, and their `it.fails` are plain `it`s, in `src/pen-test/probes/s2.test.ts`. #135 (the same key with a different body) stays open.

#135 is fixed in the third round (fixed, unverified): a Message sent with an Idempotency-Key keeps the SHA-256 of its request (`messages.request_fingerprint`; canonical JSON, keys in order, a left-out `cc`, `bcc` or `attachments` the same as an empty one). A repeat of the key with the same request still answers `200` and the first Message; with a different request, a body that would be refused included, it answers `409 idempotency_key_reused` and stores nothing, also when two requests race and the unique constraint decides. **A Message stored before the column existed has no fingerprint, and a repeat of its key answers `200` with it whatever the request, as before:** refusing every repeat of an old key would break a client's honest retry across the upgrade, and such Messages leave with Retention (90 days by default). In `src/pen-test/probes/s2.test.ts`, `refuses the same key with a different body` is a plain `it`, and its `today_` test is `(regression) … (#135)`. `src/integration.test.ts` covers the pre-migration Message.

The Idempotency-Key NUL finding (#151) is fixed in the fourth round (fixed, unverified) by the root header hook S1's note describes. Its `today_` test is now `(regression) answers an Idempotency-Key holding a NUL byte with 422 naming the header (#151)`, and `refuses an Idempotency-Key holding a NUL byte with a 4xx` is a plain `it`.
