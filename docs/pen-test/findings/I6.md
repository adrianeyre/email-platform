The findings note for scope issue #108 (I6) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H14's workflow, deploy-script and package bullets, H16's client `http:` bullet and H17. H14's image-digest and container-hardening bullet is I4's (#106); H16's error-handler, Handlebars and SMTP-text bullets are I1's (#102). It names exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `2f11db2`, the repository's GitHub settings as `gh api` answered them on 21 November 2026, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are `src/pen-test/probes/i6.test.ts`, in the gated run. Most of this surface is files, not routes, so most probes read them: the three workflows (by line; no YAML library is a dependency), `ops/deploy-server.sh` (run with `git`, `pnpm`, `docker` and `curl` stubbed, as `src/ops/deploy-server.test.ts` runs it), `pnpm-workspace.yaml` against the installed store, the client package (built and packed as `npm pack` packs it) and every image `site/build.ts` publishes. The client probes run `@adrianeyre/email-client` from its source against [the probe world](../../../src/pen-test/probes/probe-world.ts)'s API over a real socket, with the real Postgres and the E2 fixture keys behind it. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a passing test.
- **The images** were each read by eye, at full size; what each shows is recorded in `src/pen-test/probes/i6-reviewed-images.json` with its SHA-256, which the probe pins (probe 9).

## Probes 1-3: the three workflows

`pages.yml` and `release.yml` are what H14 hoped: every action pinned by a 40-character SHA with its version in a comment (6 and 5 `uses:` lines), `permissions: contents: read` at the top, `persist-credentials: false` on every checkout, and every write scope (`contents: write` for `release`'s `publish` job, `pages: write` and `id-token: write` for `pages`'s `deploy` job) in a job that installs nothing and runs only the repository's own dependency-free script or a pinned action. `release.yml:8-13` writes the rule down: "no dependency code ever runs beside a write token".

`publish-email-client.yml` breaks all three:

- `actions/checkout@v4`, `pnpm/action-setup@v4` and `actions/setup-node@v4` are tags (`:20-24`). The repository allows all actions and doesn't require SHA pinning (`gh api …/actions/permissions`: `allowed_actions: all`, `sha_pinning_required: false`). #176.
- `packages: write` is granted at the top (`:9-11`) to the one job, `publish`, whose checkout keeps its token in `.git/config` (`:20`, no `persist-credentials`). That job runs `pnpm install --frozen-lockfile` (`esbuild`'s and `@fastify/pre-commit`'s install scripts), `typecheck`, `test` and `build` before `Publish` (`:31-52`). Any of that code can read a token that publishes to GitHub Packages. #175.

The default workflow token is read-only (`default_workflow_permissions: read`), so a workflow gets a write scope only by asking; only `publish-email-client.yml` asks for one beside dependency code.

## Probe 4: triggers

No workflow uses `pull_request_target`, and no `run:` script interpolates `${{ github.event.… }}` or `github.head_ref`; `publish-email-client.yml` reads the tag through `$GITHUB_REF_NAME` in the shell, and `release.yml` passes what `release` planned through `env:`. Refuted.

**Nothing checks a pull request.** At `2f11db2` the triggers are `push` to `main` (with paths) and `workflow_dispatch` for `pages.yml`, `push` to `main` for `release.yml`, and `push` of an `email-client-v*` tag and `workflow_dispatch` for `publish-email-client.yml`. No lint, typecheck, test, `pnpm audit` or dependency review runs anywhere on GitHub; the first place a failing test or a known advisory is found is the production host at deploy (probe 6). Confirmed. #109 (a `pull_request` workflow with lint, typecheck, test, `pnpm audit` and dependency review, SHA-pinned, `contents: read`, `persist-credentials: false`) is its fix, built in this round, so no separate finding is filed. When #109 lands, its pull request turns this pair: the `today_` test into its `(regression)` test and the `it.fails` into an `it`.

**(Added) Nothing proposes updates.** No `.github/dependabot.yml` or Renovate configuration. #109 catches an advisory in what a pull request adds, but no one is told when one is published against a package already in the lockfile, and SHA pins never move unless someone moves them. #179 (low).

## Probe 5: `workflow_dispatch` on `publish-email-client.yml`

`on:` has `workflow_dispatch:` with no inputs (`:7`). The version check runs only `if: startsWith(github.ref, 'refs/tags/email-client-v')` (`:35-36`), and `Publish` (`:54-58`) has no condition; the job has no `environment:`. So "Run workflow" on a branch that isn't `main` checks out that branch, installs, tests and builds it, and publishes whatever version its `packages/email-client/package.json` names, with no check that the version is new, matches a tag, or was ever merged. A tag push publishes from the commit the tag points at, which nothing checks is on `main`. The repository has no rulesets and `main` no branch protection (`gh api …/rulesets` is `[]`; `…/branches/main/protection` is 404), so nothing limits who can push a branch or an `email-client-v*` tag; today that is one collaborator, the owner. #177.

`pages.yml` also has `workflow_dispatch`, so it can build and deploy a branch other than `main`. GitHub normally limits the `github-pages` environment to the default branch, but the repository has no environments yet (`gh api …/environments`: none) and Pages isn't enabled on it, so the limit couldn't be read. Not filed; worth checking when Pages is switched on, since that path would publish a branch's `docs/images` before probe 9's pin ever runs on it.

## Probe 6: `ops/deploy-server.sh` on the production host

Run with its four commands stubbed to record their arguments and `id -u`, the script makes, in order and all as the invoking user: `git pull --ff-only`, `pnpm install --frozen-lockfile`, `pnpm run typecheck`, `pnpm run lint`, `pnpm test`, `docker compose build`, `docker compose run --rm migrate`, `docker compose up -d --wait` and `curl … /health`. Confirmed. #178 (medium).

## Probe 8: `@adrianeyre/email-client`

**8a, the key.** Against the probe world's API with the `wizzaroo` fixture key, a recording `fetch` saw `listTemplates` and `sendContent` each send the key only as `Authorization: Bearer …`, never in the URL or body. Against a server that answers `307` to another origin (another port), Node's `fetch` follows, drops `Authorization`, and re-sends the POST body: recipients and variables (a stand-in reset link) arrive at the second origin without the key. A redirect can come only from the server the client already trusts or, on `http:`, from anyone on the path, who already reads the body; so no new exposure. Refuted.

**8b, an `http:` `baseUrl`.** `createEmailClient` checks only that the key isn't empty (`client.ts:234-236`); `baseUrl` may be any scheme and host. Through a TCP relay in front of the API, the relay's bytes hold the `Authorization` header and the key in the clear; with `http://mail.example.com` and a recording `fetch`, the request goes out with the key and `console.warn` is never called. ADR 0003 puts no TLS in front of port 4320, so on the LAN an `http:` `baseUrl` is the only one that works: every Application's key, and every send's body (Wizzaroo's links included), crosses the LAN in the clear; over the tailnet WireGuard encrypts it. Confirmed. #180 (low) is the client's half; I3's #168 is the server's (`APP_URL` accepts `http:`, and ADR 0003's plain-HTTP decision records no expiry); whether to offer TLS is I1's (H9).

**8c, its errors.** For a deleted key (401), an empty `to` (422 `validation_failed`, with field errors), an unknown Message id (404), a closed port (`EmailNetworkError`, "Couldn't reach the email app at http://127.0.0.1:1") and a proxy's 502 plain-text body (`http_502`, the first 200 characters kept), the error, inspected to any depth with hidden properties, its JSON and its stack never hold the key. What it does carry is the app's own `error`, `message` and `errors`, verbatim: the client adds nothing, and what the server puts there (Fastify's codes, SMTP replies) is I1's (#173, #174). Refuted for the key.

## Checks every scope issue carries

Applied:

- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** The CI token is kept in `.git/config` past the checkout that needed it (#175); the client sends the key in the clear on `http:` (#180); the deploy runs development code beside `.env` (#178). The published package and images hold no secret (probes 7c, 9).
- **Every refusal comes from a closed set.** The client's errors are three classes with a `status` and `code`, and never carry the key (8c); the codes and messages themselves are the server's, I1's.
- **Configuration fails closed.** `publish-email-client.yml`'s version check is skipped, not failed, when the run isn't a tag (#177); the client takes any `baseUrl` scheme (#180). `pages.yml` and `release.yml` fail closed on permissions (read by default, write only where asked).
- **Nothing is left to a collaborator to bound.** A moved action tag (#176), a development dependency (#175, #178) and GitHub's default environment rules (probe 5's `pages.yml` remark) are each trusted to bound what runs beside a write credential. `allowBuilds` and `--frozen-lockfile` do bound what installs (probe 7).
- **Run the probes against a real Postgres.** The client probes do, through the probe world's API over a real socket; the rest read files and need none.
- **A test that passes either way proves nothing.** Every `it.fails` was run as a plain `it` and failed on its property assertion (the three tags, the one checkout, the `publish` job, no `pull_request` workflow, no update configuration, the conditional version check, four `pnpm` calls without `--prod`, the recorded `http:` request), never on setup. The image pin was checked by its own failure modes: a changed hash fails as `changed`, an unread file as `unread`.

Not applied: **refusals give nothing away**, **odd input stops above the database**, **idempotency keys**, **logs are a copy of the data**, **internal headers** and **path-matching middleware**: this surface has no route of its own. The client forwards whatever `Idempotency-Key` it is given; binding it is S2's.
