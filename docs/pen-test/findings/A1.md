# A1: passwords, sessions and the sign-in throttle

The findings note for scope issue #92 (A1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H1 and the session bullets of H5. It names exploit chains, so **keep it private on the same terms as the PRD**. Probed at commit `d81eaa9`. The probes are `src/pen-test/probes/a1.test.ts`: the hashing and throttle-memory checks run without a container; the rest run in the gated run against a real Postgres from [the probe world](../../../src/pen-test/probes/probe-world.ts), with the fixtures loaded again before each probe. Every throttle probe builds a server of its own, as production builds it, so its throttle starts empty. No credential appears here; Users are named by fixture handle (`victim`, `colleague`).

## The throttle and `X-Forwarded-For` (probes 1 and 2)

`buildHttpServer` sets `trustProxy: true` (`src/api/http-server.ts:91`), so `request.ip` is the left-most `X-Forwarded-For` a caller sends. The throttle key is `` `${request.ip}:${normaliseEmail(email)}` `` (`src/access/access-routes.ts:68`), 10 failures in 15 minutes (`:24-25`).

- **No header** (1a): 11 wrong passwords for `colleague` from one socket answer `401` ten times and `429` (`too_many_attempts`, "Too many failed sign-ins. Try again in 15 minutes") the eleventh. The right password is then refused `429` too, and so is the same email in capitals with spaces round it: the key folds case and spaces. Good.
- **Fresh header** (1b): the same 11 tries, each with a different `X-Forwarded-For` (`203.0.113.1`…`.11`), answer `401` eleven times. And once the socket's own address is blocked, the right password with any made-up header (`198.51.100.200`) answers `200` and a session. So the throttle bounds nobody who sends one header. Nothing legitimate sets it: the platform has no proxy in front of it (PRD, "Current state of play").
- **Spray** (2): one wrong password across 11 emails (both fixture Users and nine with no account) from one socket answers `401` eleven times; with a fresh header each try, the same. The key holds the email, so there is no per-address limit at all, header or not: a spray of one guess per account is never throttled.
- Because the key holds the IP as well, nobody can lock a User out from another address: the colleague's own browser is never refused for an attacker's failures. That is the right side of the trade, and should survive a fix (the PRD's request-rate section asks for per-IP and per-account limits that don't tell which emails have accounts).

## scrypt arithmetic (probe 3)

Every attempt runs one scrypt, `N=16384, r=8, p=1`, 64-byte key (`src/lib/secrets.ts:34-37`), for an email with no account too (`src/access/users.ts:130-132`). That is 16 MiB of memory per hash. Node runs `crypto.scrypt` on the libuv pool, 4 threads unless `UV_THREADPOOL_SIZE` is set; nothing in `Dockerfile`, `docker-compose.yml`, `package.json` or `src/` sets it.

Measured on the machine the probes ran on (Apple M5 Max): one scrypt 20-22 ms on one thread; 40 in parallel in 214 ms, about **187 a second** through the pool. A wrong password through `POST /auth/sign-in` took 22 ms (median of 5). The home server's CPU isn't known here, so the table also gives a quarter of that.

| With probe 1b or 2 (no effective throttle)           | 187 guesses/s (measured)                  | 47 guesses/s (a CPU four times slower) |
| ---------------------------------------------------- | ----------------------------------------- | -------------------------------------- |
| An hour                                              | 673,000                                   | 168,000                                |
| A day                                                | 16.2 million                              | 4.0 million                            |
| A list of 1 million candidate passwords, one account | 89 minutes                                | 5.9 hours                              |
| A list of 10 million                                 | 15 hours                                  | 2.5 days                               |
| A spray of 1 password over every User                | one guess per User; the same rate, shared |                                        |

With the throttle working (no header, one email): 10 guesses per 15 minutes per (address, email) is 40 an hour, 960 a day, so a million-password list takes 1,042 days from one address. That figure only holds for a caller who neither sends `X-Forwarded-For` nor varies the email, which is no attacker. The password rule is a length of 12 or more (`users.ts:13,27-33`) with no check against common or breached passwords, so a person's own twelve characters is the kind of password a candidate list holds. There is no second factor (ADR 0005), so one guessed password is the account, and with H5 the platform (see A2).

OWASP's Password Storage Cheat Sheet gives scrypt `N=2^17, r=8, p=1` as its minimum; the platform's `N=2^14` is an eighth of that work and memory (probe 3b).

## Long passwords (probe 4)

`credentialsBody` gives `email` and `password` a `minLength` and no `maxLength` (`access-routes.ts:50-53`), and the body limit is 36 MB (`http-server.ts:50`). A 35 MB password for `colleague` was parsed, run through scrypt and refused `401` with the usual body in **110 ms**, against 22 ms for a short one. scrypt hashes a long password with PBKDF2-HMAC-SHA256, so its own extra cost is two SHA-256 passes over the password; the rest is `JSON.parse` of the 35 MB body, which runs on the event loop and holds every other request up while it does. `POST /app/users` and `PUT /app/me/password` take the same unbounded `password` (and the email, see A2). Volume was not tested; one request of each size was enough to see the behaviour.

## The throttle's memory (probe 5)

`createSignInThrottle` keeps a `Map` of key to failure times in one process (`access-routes.ts:27-43`). A key is deleted only when the same (address, email) signs in successfully (`:39-41`, `:89`). A failure older than 15 minutes is filtered when the key is read, but the key and its array stay.

- **Restart** (5a): ten failures on one server make it answer `429`; a second server built on the same database (what a restarted or second `api` process is) answers the same eleventh try with `401`. The state is lost on every restart and is not shared if the `api` is ever scaled to two processes.
- **Growth** (5b): recording one failure for each of 40 keys of 1 MB, each with its window long passed before the next, leaves **41.8 MB** of heap reachable after a full collection (measured with V8's `gc`). Nothing evicts a key whose window has passed. Arithmetic: an email with no account never signs in, so its key is kept until the process ends. A 36 MB body carries an email of about 36 MB, and the key holds all of it: about 30 such requests hold 1 GB, and a few dozen more reach Node's default old-space limit and end the `api`. With short emails and a fresh `X-Forwarded-For` each try, each key costs a few hundred bytes, so a million tries hold a few hundred MB. Not exercised (denial of service is out of scope).

## Sessions (probe 6)

A session is a 32-byte random token kept as its SHA-256, with `expires_at` 30 days after it was made (`users.ts:139-152`); `loadSignedInUser` checks the hash and `expires_at > now()` (`:163-181`).

- **Password change** (6a): with two sessions of `victim`, changing the password through one (`PUT /app/me/password`, `200`) leaves the other answering `GET /app/me` with `victim`'s id and email. `changePassword` updates the hash and nothing else (`users.ts:98-119`). So changing the password, the one thing a User who suspects a stolen session can do, does not end it. There is no other way to end one's other sessions. The guide says "You stay signed in" for the session that asks, which is right; it says nothing about the others. What a stolen session makes in the meantime is A2's.
- 6b: a stolen session can't change the password without the current one: `422`, "The current password is wrong".
- **Expiry** (6c): a session moved past its `expires_at` is refused `401`. Its row stays until the next sign-in by anyone, which deletes every expired row (`users.ts:145`); the row can't sign anyone in, so it isn't filed.
- **Idle** (6d): a session made 29 days ago and never used since is served. There is no last-used time, so no idle timeout. The 30 days is documented (`docs/guide/delivery-and-access.md`, Access); the absence of an idle timeout is not.
- **Sign-out** (6e): `POST /auth/sign-out` deletes the row (`users.ts:154-161`) and clears the cookie; the token is refused afterwards, and another session of the same User still works.
- **Deleted User** (6f): `sessions.user_id` cascades on delete (`src/lib/schema.ts:34-45`); the colleague's session is refused once the victim deletes them, and no row is left. The guide's "Remove signs that person out everywhere at once" holds.

## Refusals for emails with and without an account (probe 7)

For `colleague` and for an email with no account: a wrong password answers `401` with the same body and `content-length`; an empty password answers the same `422`; the eleventh wrong try answers the same `429`. Timing, medians of 7 alternating tries, each from its own header so the throttle stays out of it: **21.9 ms** with an account and **21.9 ms** without. The no-account path runs `hashPassword` with the same parameters (`users.ts:130-132`), so the work is the same. Refuted.

## Checks every scope issue carries

Applied:

- **Refusals give nothing away:** probe 7. Holds at sign-in. (`POST /app/users` is A2's.)
- **Every refusal comes from a closed set:** a 35 MB password gets the usual `401`. A NUL byte in the email does not: `POST /auth/sign-in` with `victim\u0000@users.pen-test.invalid` answers `500` (`internal_error`, "Something went wrong"), because Postgres refuses the `0x00` in the `where` clause. The fixed 500 body leaks nothing, but the request is well-formed JSON and should be a `401` or `422`. Filed as #144, with A2's `POST /app/users` case in the same finding.
- **Odd input stops above the database:** very long strings (probe 4) and NUL bytes (above). Numbers and dates don't apply to this body.
- **Nothing is left to a collaborator to bound:** the throttle's map (probe 5b) and the password's length (probe 4) have no bound of their own.
- **A secret is sealed or hashed where it is kept:** passwords are salted scrypt, session tokens SHA-256; neither is kept in the clear. Holds (cost is probe 3b).
- **Internal headers are trusted only when the server set them:** `X-Forwarded-For` (probe 1b). Fails.
- **Run the probes against a real Postgres:** all session and sign-in probes do.
- **A test that passes either way proves nothing:** every `it.fails` was run as a plain `it` and failed on its property assertion (for example `expected 401 to be 429`), never on setup.

Not applied, and why:

- **An idempotency key is bound to its payload and owner:** no idempotency key on these routes (S2's).
- **Logs are a copy of the data:** the sign-in body is not in Fastify's request log; the log sweep is D2's.
- **Middleware that matches by path matches by segment:** B1's.
- **Configuration fails closed:** I3's. Note for I3: no setting names a trusted proxy; `trustProxy: true` is hard-coded.
- Cookie flags (`HttpOnly`, `SameSite=Lax`, `Secure` only for `https:`) are I1's.

## Left to other scope issues

- What a stolen session can make that survives the password change: A2, which builds on #124.
- Rate limits on the API and their figures: I2a and I2b. The PRD's request-rate section already says `trustProxy: true` with no named proxy is never acceptable.
- Not filed: the UI asks for a new password "different from the current one" (guide, Access), and the server doesn't check it (`users.ts:114`). It weakens nothing an attacker can use.

## Since the probe

#114 and #124 are fixed in the second round's pull request (fixed, unverified). `trustProxy` is `false`, so the throttle keys on the socket's address. Changing a password ends every other session of that User. Their `today_` tests are now `(regression)` tests, and their `it.fails` are plain `it`s, in `src/pen-test/probes/a1.test.ts`.

#122 and #123 are fixed in the third round's pull request (fixed, unverified). The throttles moved to `src/access/sign-in-throttle.ts`.

- **#122, the per-IP limit.** `POST /auth/sign-in` now counts every try against the socket's address (`request.ip` with `trustProxy: false`, an IPv4-mapped IPv6 address folded to IPv4), whatever email it names, a success or a try the per-email throttle refuses included. The PRD's table gives the per-IP column "Burst 10" and "30 tries per 15 minutes"; they are read together as a **token bucket of 10 that refills one try every 30 seconds (30 per 15 minutes), capped by a count of 30 tries in any 15 minutes**. So the 11th try in a row from one address is refused, a steady caller gets one try every 30 seconds, and no 15 minutes holds more than 30 (the bucket alone would let 10 + 30 through in the first 15). The probe's "429 by the 11th" is the burst of 10, so it agrees with the PRD and was not changed. Either limit refuses with the same `429` body, `too_many_attempts`, "Too many sign-ins. Try again later" (the old "Try again in 15 minutes" was wrong for the per-IP limit), with `Retry-After` in seconds: until a try comes back to the bucket, or the oldest try leaves the window, or the oldest failure for the (address, email) does. The per-(address, email) throttle, 10 failures in 15 minutes, is unchanged. Probe 2's `today_` test is now `(regression) answers one password sprayed across 11 emails from one address with 10 × 401 then 429 and a Retry-After, with or without X-Forwarded-For (#122)`, and `answers a spray of one password across 11 emails from one address with 429 by the 11th` is a plain `it`. The probe world's `signIn` and `src/integration.test.ts`'s `signInAs` now sign each fixture in from an address of its own (`inject`'s `remoteAddress`), because one shared server signs in dozens of times a file and the setup would otherwise meet the limit it doesn't test.
- **#123, the throttle's memory.** Both throttles forget a key once 15 minutes pass with no failure (or try) in it: a sweep runs at most once a minute, on the next call. Each holds at most **10,000 keys**; when it is full of live keys, a key it doesn't hold is refused with `429` (it fails closed) until keys expire, rather than evicting one, since eviction would let a caller with many addresses wipe its own count. The cost is that a caller with about 250 addresses (40 keys each per window, the per-IP limit's bound) could keep new callers out for up to 15 minutes; callers are LAN or tailnet only (ADR 0003). A key's failure times are capped at the limit's 10. The sign-in email is limited to 320 characters (RFC 5321's longest address) with a `422` before the handler runs, so a key is at most a few hundred bytes and a full throttle a few MB. Only sign-in's email: `POST /app/users` keeps its own body, which is #144's and A2's, and the password's length is #141's. Probe 5b's `today_` test is now `(regression) drops each failed sign-in's key once its 15-minute window has passed, so of 40 keys of 1 MB at most the last is held (#123)`, and `forgets a failed sign-in's key once its 15-minute window has passed` is a plain `it`; `refuses a sign-in whose email is longer than 320 characters with 422, so the throttle never keys on it (#123)` is new.
- Still open: the counts are per process and lost on restart (#142), and the per-account count is not yet across addresses in Postgres (#163).

Every `429` is now one body, `too_many_requests` with `Retry-After` (`TooManyRequestsError`, which the error handler answers), whichever limit fired: the per-address and per-email sign-in limits, step-up's and K1's send limit (#133). The sign-in `429`s used to say `too_many_attempts`.

- **#144, a NUL byte in a sign-in email.** Refused with `422 validation_failed` (`body.email`) by the root body hook S1's note describes for #151, before the throttle or the database. Probe 7's `today_` test is now `(regression) answers a sign-in whose email holds a NUL byte with 422 validation_failed, before the database (#144)`, and `answers a sign-in whose email holds a NUL byte from the closed set of refusals, not 500` is a plain `it`. Sign-in's email keeps its 320-character limit (#123); no User's email can be longer than 254, so a longer one is answered `401` as any unknown email is.

#140, #141, #142 and #143 are fixed in the fourth round (fixed, unverified).

- **#140, scrypt's cost.** A new password hash is made at OWASP's minimum, **N=2^17 (131,072), r=8, p=1** (`passwordHashCost` in `src/lib/secrets.ts`): about 128 MiB and 170 ms a hash, eight times the old cost, so probe 3a's 187 guesses a second on one core is now about 23. Node's scrypt refuses more than 32 MiB unless told, so `maxmem` is set to twice what the cost needs. A stored hash carries its own cost, so a hash made at N=2^14 still matches, and a successful sign-in makes it again at the new cost (`isPasswordHashOutdated`); a User who never signs in again keeps the cheaper hash. The test suite runs at the production cost too, about 30 seconds slower. Probe 3b's `today_` test is now `(regression) hashes every password with scrypt at OWASP's N=131072 (2^17), r=8, p=1 (#140)`, and `hashes every password with at least OWASP's scrypt cost, N=2^17 with r=8` is a plain `it`.
- **#141, the password's length.** Every password a body takes (sign-in's `password`, `POST /app/users`'s `password`, `PUT /app/me/password`'s `newPassword`, and every step-up `currentPassword`) is limited to **1,024 characters** (`maxPasswordLength` in `src/access/users.ts`), refused with `422 validation_failed` before it is hashed; `createUser` and `changePassword` refuse a longer one too, so the CLI does. `/auth/sign-in` and `/auth/sign-out` have a route `bodyLimit` of **16 KiB**, so a 35 MB body is refused with `413` before it is read or parsed, and counts as no failure. The `413` still cites the 25 MB message limit, which is #172's. Probe 4's `today_` test is now `(regression) refuses a 35 MB password with 413 before parsing it, and one of 1,025 characters with 422 before hashing it, counting neither as a failure (#141)`, and `refuses a password longer than 1,024 characters before hashing it` is a plain `it`. Probe 5b's email test now sends a 4,096-character email, since a megabyte one meets the body limit first. In I1's probe 3 (#172), `sign-in refuses a body much larger than an email and a password with 413, before parsing it` is a plain `it`, and the `today_` test pins what is left: a bodiless `/app` DELETE still reads 36 MB.
- **#142, the throttle across restarts and processes.** The sign-in throttles (per address, and per address and email) and step-up's (per User) keep their counts in Postgres, in the `throttle_keys` table (migration `0010_shared_throttle_and_session_idle`), so every `api` process counts against one figure and a restart forgets nothing. Each change takes a transaction-scoped advisory lock on its key, reads the row and writes it back, as K1's send limit counts in one statement (#133), so two processes can't both count from the same figure. The figures are unchanged. A row is deleted once 15 minutes pass with nothing in it, by a sweep that runs at most once a minute. The 10,000-key cap is gone: it bounded the `api`'s memory (#123), and nothing is held in memory now; a caller with many addresses adds rows (a few hundred bytes each, deleted 15 minutes after their last try) rather than locking new callers out, as the full cap did. `api` reaches the table through `email_platform_app`'s grants on every table in `public`, which `grantRuntimeAccess` gives after each migration. Probe 5a's `today_` test is now `(regression) still answers 429 from a new process after the old one answered 429, as the throttle is kept in Postgres (#142)`, and `still answers 429 after the api restarts mid-throttle` is a plain `it`. Probe 5b's tests now count rows: `(regression) drops each failed sign-in's key once its 15-minute window has passed, so of 40 keys none is held (#123, #142)`. The probe world has `forgetSignInThrottle`, which A1's and I2a's probes call before each test, as a fresh server once started them empty. The per-account count across addresses is still #163's.
- **#143, the idle timeout.** A session is refused once it goes unused for **7 days**, within its 30 (`sessionIdleDays` in `src/access/users.ts`). Seven days is a decision the owner may change: a User who signs in weekly stays signed in, and a cookie in a forgotten browser profile or backup stops working within a week. Each session records `last_used_at`, written at most every 5 minutes, so not every request is a write; signing in deletes idle sessions as well as expired ones. Probe 6d's `today_` test is now `(regression) refuses a session made 29 days ago and never used since, and one last used 8 days ago, but serves one made 29 days ago and used yesterday (#143)`, and `refuses a session left unused for 29 days` is a plain `it`; the probe's `moveSession` now moves the last use with the creation.
