# S1: Message input, from and headers

The findings note for scope issue #96 (S1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H8. It names exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `d81eaa9`, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are the tests under `pen test S1 (#96): Message input, from and headers` in `src/pen-test/probes/s1.test.ts`. They run in the gated run against a real Postgres and a real Mailpit (`startProbeWorld`). Each probe sends `POST /v1/messages` as `secondApp`, runs the send worker once through Mailpit (`world.deliver`) and reads what Mailpit received, raw headers included (`world.readRawMail`). A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a passing test.
- **Left to other scope issues:** any API Key sending from any address is K1's ("any from"). This note pins it again from the header side and refers to K1's finding. It does not file it again. Handlebars, Block URLs and preview cost are S3's. The log copy of recipients and bodies is D2's.

## Header injection (probe 1)

Nodemailer 10.6.0 (`src/sending/delivery.ts:44-58`) is what stands between the free text and the headers. The platform passes every field through unchanged. The one exception is a Configuration's from name, which `formatFromAddress` folds itself (`src/templates/configuration-routes.ts:52`). Each payload below carried `\r\nX-Injected: …`, and the subject's also carried `\r\nBcc: evil@evil.pen-test.invalid`. No raw email had a header line starting `X-Injected:` or `Bcc:`. Mailpit received each one for the single fixture recipient only.

| Field                                                                | Accepted                       | What Mailpit received                                                                                                                                                                                  |
| -------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `subject` (raw)                                                      | 202                            | `Subject: Hello X-Injected: subject Bcc: evil@…`: CR and LF folded to spaces                                                                                                                           |
| `subject` through `orderNumber` in `second-app-order-shipped`        | 202                            | `Subject: Your order SA-1 X-Injected: variable has shipped`. The HTML part has `X-Injected:` at the start of a body line, which is body, not a header                                                  |
| `from`                                                               | 202                            | `From: "Evil X-Injected":from <evil@evil.pen-test.invalid>;`. Nodemailer parses the folded text as an address group. The From header is mangled but no header is added                                 |
| `replyTo`                                                            | 202                            | `Reply-To: "reply@s1.pen-test.invalid X-Injected":;`: an empty group                                                                                                                                   |
| Configuration `fromName` (`PUT /app/configurations/:id` as `victim`) | 200, stored with the CR and LF | `From: "Second X-Injected: fromName Bcc: evil@…" <orders@second-app.pen-test.invalid>`, folded by `formatFromAddress`                                                                                  |
| Configuration `fromEmail`                                            | 422                            | Refused by the `email` format                                                                                                                                                                          |
| attachment `filename`                                                | 202                            | RFC 2231-encoded: `filename*0*=utf-8''a.txt%0D%0AX-Injected%3A%20filename`                                                                                                                             |
| `to` entry                                                           | 202                            | Nothing. The worker failed the Message with `No recipients defined`                                                                                                                                    |
| attachment `contentType`                                             | 202                            | Nothing. So H8's header-injection bullet is refuted with Nodemailer as it is. The defence is all Nodemailer's, though. The platform stores CR and LF in `from`, `replyTo`, `to` and a from name, and gives a 202 for input that can only fail at the worker. This is folded into the address and attachment findings below.

## Several addresses in one entry (probe 2)

`to`, `cc` and `bcc` entries are strings of 3 to 320 characters with no format check (`src/sending/message-routes.ts:14,28-30`). Nodemailer parses each entry as an address list.

- `to: ["a@…, b@…, c@…"]` stores **one** entry (`to` in the summary and log is that one string) and Mailpit receives it for **three** addresses.
- `to: ["Team: d@…, e@…;"]` (a group) is delivered to both members.
- `to` with 50 entries of two addresses each passes the schema's `maxItems: 50` and Mailpit receives **100** To recipients.
- `to: ['"Doe, Jane" <jane@…>']` goes to one address, as it should.

**Arithmetic.** A 320-character entry holds about 22 short addresses (`a1@x.invalid, ` is 14 characters). That makes 50 × 22 ≈ 1,100 recipients per field, and about 3,300 per request across `to`, `cc` and `bcc`. The documented limit is 50 each, 150 in all ([Sending, Fields](../../guide/sending.md#fields)). Nodemailer and the SMTP provider are then the only limit. The PRD's "Nothing is left to a collaborator to bound" says they must not be.

## A from no Configuration names (probe 3)

`secondApp` sent `from: "Wizzaroo <no-reply@…>"`, which is the Wizzaroo Configuration's name and address. The request got 202, and Mailpit's From was `{ Name: <Wizzaroo's from name>, Address: <Wizzaroo's from address> }`. Nothing compares `from` with a Configuration (`src/sending/accept-message.ts:220-223`). This is K1's "any from" finding. See K1.

## Attachments (probe 4)

`filename` has `minLength: 1` and no maximum, `contentType` is any string, and the array has no `maxItems` (`src/sending/message-routes.ts:54-62`). `decodeAttachments` only checks base64 (`src/sending/accept-message.ts:67-88`).

- **Odd types** were accepted and sent as given: `application/x-msdownload` for `setup.exe`, `multipart/mixed; boundary=zzz` on a leaf part named `../../etc/passwd`, and `""` (Nodemailer guessed `text/html` from `page.html`). A `contentType` holding CR and LF is accepted with 202, and the Message then fails at the provider (above).
- **Very long:** a 100,000-character `filename` and a 100,000-character `contentType` were accepted and sent. Mailpit received a 235 KB and a 100 KB email.
- **Many tiny ones:** 999 empty attachments were accepted, and Mailpit refused the email (`554 5.6.0 Unable to parse message`). Between 300 (sent) and 999 is where this Mailpit gives up, and a real provider sets its own limit. 16,383 were accepted. **16,384 answered `500 internal_error`.** All the rows go in one `INSERT` (`src/sending/accept-message.ts:262-268`) with 4 bound parameters per row (`message_id`, `filename`, `content_type`, `content`, `src/lib/schema.ts:178-189`). 16,384 × 4 = 65,536, one over Postgres's 65,535-parameter limit. That request body is 491,592 bytes, far below the 36 MiB `bodyLimit` (`src/api/http-server.ts:50`).
- **Just over 25 MB, sent once:** one attachment of 26,214,401 decoded bytes (34,952,536 base64 characters) was refused with `413 message_too_large` in about 40 ms by the size check (`src/sending/accept-message.ts:233-244`), before anything was stored. **Arithmetic:** the body limit of 37,748,736 bytes holds up to about 28.3 MB of decoded content, so the app's 25 MiB check is the one that bites. The check counts decoded bytes. On the wire, base64 makes a 25 MiB message about 34-35 MB, which some providers refuse. That is a provider limit, not a gap here.

## Odd input (probe 5)

- **NUL** (`a\u0000b`) in `subject`, `html`, `text`, `from`, `to`, `cc`, `bcc`, `replyTo`, `templateSlug`, `templateName`, a template variable, `filename` and `contentType` answered `500 {"error":"internal_error","message":"Something went wrong"}` every time. The `Idempotency-Key` header does the same (pinned in S2). Postgres refuses NUL in `text` (SQLSTATE 22021). Nothing above the database checks for it, so the error reaches the catch-all (`src/api/http-server.ts:127-130`). The body gives nothing away, but the refusal is not from the closed set.
- **`0x10`, `1e3`, `1.5`, `Infinity`:** as strings they are kept as text. As JSON numbers in a string field (`to`, `subject`, `from`) they get 422. `templateId: "0x10"` and `GET /v1/messages/0x10` get 422 (`uuid` format). No field is numeric, and the year 0000 has no field to go in.
- **Very long strings:** `subject` 999, `from`/`to`/`cc`/`bcc`/`replyTo` 321, `templateSlug` 101, `templateName` 201 and a 51st `to` entry all get 422. `html`, `text` and variables are bounded only by the 25 MB message check and the 36 MiB body.
- **A rendered subject has no limit:** `subject` is capped at 998 characters only when sent raw (`src/sending/message-routes.ts:32`). A Template's subject is rendered with the caller's variables (`src/templates/render.ts:57`), and `orderNumber` of 100,000 characters gave a stored and sent subject of more than 100,000 characters. RFC 5322 caps a line at 998 characters. Nodemailer folds the header, so the email is delivered.

## Checks every scope issue carries

Applied:

- **Every refusal comes from a closed set:** broken twice. NUL in any field answers 500, and so do 16,384 attachments. Every other refusal probed was 413 or 422 with the platform's own body. No SMTP or driver text reached the HTTP caller. SMTP text (`554 5.6.0…`, `No recipients defined`) does reach the Message's `error`, which its sender reads. Who else reads it is K1's and S2's.
- **Odd input stops above the database:** NUL does not. The other odd inputs do (probe 5).
- **Nothing is left to a collaborator to bound:** broken for recipients (probe 2) and attachment count and field length (probe 4). Nodemailer, Mailpit and Postgres are the limits.
- **Run the probes against a real Postgres:** yes, with Mailpit, through `startProbeWorld`.
- **A test that passes either way proves nothing:** every confirmed probe pins the exact status or count observed. Each `it.fails` was run as a plain `it` and failed on its property assertion (202 for 422, 100 for ≤ 50, 500 for < 500, 202 for 4xx).

Not applied, and why:

- **Refusals give nothing away:** the unauthenticated refusal of `/v1/messages` is the same with or without a body, and route enumeration is B1's. The one thing a refusal echoes is the caller's own `filename` in the not-base64 message.
- **An idempotency key is bound to its payload and its owner:** S2's.
- **A secret is sealed or hashed** and **Logs are a copy of the data:** D1's and D2's. This surface holds no secret of its own.
- **Internal headers are trusted only when the server set them:** this route reads only `Authorization` and `Idempotency-Key`. Those are K1's and S2's, and `X-Forwarded-For` is A1's.
- **Middleware that matches by path:** B1's.
- **Configuration fails closed:** nothing on this surface reads configuration. The SMTP settings are I-scope's.

## Since the probe

#134 is fixed in the third round (fixed, unverified): `acceptMessage` (`src/sending/accept-message.ts`) parses each `to`, `cc` and `bcc` entry with Nodemailer's own `addressparser`, the way Nodemailer will read it when it sends, and refuses with `422` on the entry (such as `to.0`) any entry that is not exactly one mailbox: a list, a group, an address without one `@`, or any control character (NUL, CR and LF among them). A display name, quoted commas included, still works. So the 50-a-field cap, the stored recipients and the log count people, and the K1 send limit (#133) counts recipient addresses. In `src/pen-test/probes/s1.test.ts`, probe 2's two `it.fails` (`refuses a to entry that holds more than one address`, `sends to no more than 50 To recipients from one request`) are plain `it`s, and their `today_` tests are `(regression) … (#134)` tests. Two plain tests changed with it: CR and LF in a `to` entry are now refused with `422` (the `contentType` half still accepts and fails), and the NUL-byte `today_` test now expects `422` for `to`, `cc` and `bcc` (the other fields are still #151's). `replyTo` is not parsed this way: it never adds a recipient. #150, #151 and #152 stay open.

#151 is fixed in the fourth round (fixed, unverified): two root hooks in `buildHttpServer` (`src/api/http-server.ts`) refuse a NUL byte anywhere in a JSON body (key or value, at any depth) or in any header with `422 validation_failed`, naming the field as `body.subject` or `headers.idempotency-key`. The header hook runs on `onRequest`, before any scope's hook reads an API Key or a session cookie; the body hook on `preValidation`, before any handler or query. Probe 5's `today_` test is now `(regression) answers a NUL byte in every string field with 422 validation_failed naming the field, before any query (#151)`, and `refuses a NUL byte in every string field with a 4xx` is a plain `it`.

#150 is fixed in the fourth round (fixed, unverified): the send route's schema (`src/sending/message-routes.ts`) takes at most 100 attachments, a `filename` of 1 to 255 characters and a `contentType` of 1 to 255, and `acceptMessage` (`src/sending/accept-message.ts`) checks the same before any query, refusing with `422` on `attachments` or on the field (such as `attachments.0.contentType`) any `contentType` that is not one MIME type: RFC 2045's `type/subtype` with optional `; name=value` parameters, with no control character (CR and LF among them), and not a `multipart/` type, which is a container and never one file. A left-out `contentType` is still `application/octet-stream`; an empty one is now refused rather than left to Nodemailer's guess. At 100 attachments of four parameters each, the one INSERT stays far below Postgres's 65,535 parameters, so 16,384 attachments get `422`, not `500`. Probe 4's `today_` tests are now `(regression) refuses an attachment whose contentType is not one MIME type, or whose filename or contentType is over 255 characters, with 422 naming the field, and still sends any one MIME type (#150)` and `(regression) refuses 101 attachments, and 16,384, with 422 before the database, and accepts and sends 100 (#150)`, and `refuses an attachment whose contentType is not one MIME type, or whose filename or contentType is longer than 255 characters` and `refuses too many attachments with a 4xx of its own` are plain `it`s. Probe 1's CR and LF test now expects `422` for the `contentType` half too.

#152 is fixed in the fourth round (fixed, unverified): `renderTemplate` (`src/templates/render.ts`) holds a Template's rendered subject to the 998 characters a raw `subject` may have, and `acceptMessage` refuses a longer one with `422` on the field that named the Template (such as `templateSlug`), before the Message is stored. The same bound holds in `/v1/templates/preview` and when a Template is saved with its sample variables, where the field is `subject`. Probe 5's `today_` test is now `(regression) refuses a template whose subject renders past 998 characters with 422 on the template field, storing nothing, and sends one of 998 (#152)`, and `refuses a template whose rendered subject is longer than 998 characters` is a plain `it`.
