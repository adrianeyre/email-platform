# D3: backups and restore

The findings note for scope issue #101 (D3) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H13 and the backup half of H12; the log half of H12, and Retention's own scope, are D2's. It names exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `d81eaa9`, and the [fixtures](../fixtures.md) by handle and id. No credential, key or seed appears here; the age keys were made in a throwaway container and died with it.
- **The probes** are `src/pen-test/probes/d3.test.ts`, in the gated run. They run production's backup image (`backup/Dockerfile`), as `src/backup-restore.test.ts` does, against the probe world's real Postgres with the E2 fixtures loaded, with a throwaway age identity made in the container, a local rclone remote path (`/tmp/backups`) standing in for the off-server target, and a second, empty Postgres to restore into. "Full disk" is a second backup container whose `/tmp` (where `backup.sh`'s `mktemp -d` work folder goes) is a 64 KiB tmpfs. The `.gitignore` probe is a plain test that needs no container. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a passing test.
- **Left to other scope issues:** the backup and restore containers logging in as the Postgres superuser with `POSTGRES_PASSWORD`, on a network with a way out, are D1's; see D1. What the log holds, and Retention's scope, are D2's; see D2.

## Probe 1: encryption

`backup.sh` pipes `pg_dump --format=custom` into `age --recipient "$BACKUP_AGE_RECIPIENT"` and writes only the ciphertext (`backup/backup.sh:13`); the server holds the recipient (public key) only. Against a fresh backup of the fixture database:

- the file starts `age-encryption.org/v1`;
- `age --decrypt` with a second, unrelated identity exits non-zero: `no identity matched any of the recipients`;
- `pg_restore --list` on the file exits non-zero;
- `grep -a -c -- -not-a-real-token` (the suffix of every fixture link token) finds 0 lines in the file;
- with the right identity, `age --decrypt | pg_restore --data-only --table=messages` finds the token on exactly 6 lines: one per fixture Wizzaroo Message with a link.

Refuted: without the identity a backup can't be read. With it, each backup is a full copy of the log, every link included (H2), kept `BACKUP_KEEP_DAYS` (14) more nights after Retention deletes the row. So the age identity is as sensitive as the database itself; probe 5 is about where it lives.

## Probe 2: the rclone credential

`backup.sh` prunes with `rclone deletefile "$BACKUP_RCLONE_REMOTE/$old"` (`backup/backup.sh:21-30`), so the credential in `rclone.conf` on the server must be able to delete. In the probe, from the backup container, as its `postgres` user:

- `rclone deletefile /tmp/backups/<one backup>`: exit 0, that backup gone, the other kept;
- `rclone delete /tmp/backups --include 'email-platform-*'`: exit 0, the remote empty.

The local remote has no credential of its own, so the probe shows what the _script's_ access lets anyone on the server do; for a real B2 or S3 remote the same holds, because the script needs `deleteFiles` (or `s3:DeleteObject`) to prune. Nothing in the repository sets object lock, versioning or a lifecycle rule that would keep a deleted backup, and the runbook asks for none (`docs/operations/backups-and-restore.md`). Whoever controls the server, the one machine the backups exist to survive, can erase every backup first.

**Probe 2b (added).** The same two things the server holds, the rclone credential and the age _recipient_, are all it takes to write a backup the restore will trust. age encrypts; it doesn't sign, and `restore.sh` takes the name that sorts last (`backup/restore.sh:9-16`). The probe inserted a User `planted@attacker.pen-test.invalid` into the source, wrote `pg_dump | age --recipient … | rclone rcat /tmp/backups/email-platform-2099-01-01T000000Z.dump.age`, deleted the User from the source, took an honest backup, then ran `restore.sh latest` into an empty database: it printed `backup.restore.finished stamp=2099-01-01T000000Z`, and the restored `users` table holds the planted User. A User row is a sign-in (with a password hash the forger chose), so whoever held the server can survive being restored away from: the restore that recovers from the breach plants them back. The future stamp also outlives every prune (it is never older than the cutoff). This answers H13's "the backups trust the server that makes them" more widely than H13 put it.

## Probe 3: a night that fails

`nightly.sh` sleeps until `BACKUP_HOUR_UTC`, runs `backup.sh`, and on failure writes `backup.nightly.failed: see the lines above for the step that failed` to stderr and loops (`backup/nightly.sh:6-20`). The probe ran the real `nightly.sh` with `sleep` replaced by a one-second sleep (so a "night" is a second), under `timeout 12`:

- **Bad remote** (`BACKUP_RCLONE_REMOTE=unreachable-target:email-platform`): stderr holds `backup.upload.failed remote=unreachable-target:email-platform` and `backup.nightly.failed…` once per night (10 in 12 seconds); `nightly.sh` never exits on its own (exit 143, the probe's `timeout`).
- **Full disk** (`/tmp` a 64 KiB tmpfs): stderr holds `age: error: write /dev/stdout: no space left on device` and `backup.nightly.failed…` each night; `backup.sh` writes no `backup.…failed` line of its own (the runbook says "logs which step failed"); nothing reached the remote; `nightly.sh` carries on.

Who is told: no one. The container stays up, so `restart: unless-stopped` never fires and `docker compose ps` shows it running; the `backup` service has no healthcheck (`docker-compose.yml:77-97`); there is no alert, email (the platform sends email, but not this) or success marker anyone checks. The only trace is a line in `docker compose logs backup`, which no one reads unless they already suspect something. With `BACKUP_KEEP_DAYS` 14, after 14 silent failed nights the newest backup is older than the window the owner believes they have; and the first night that succeeds again prunes everything older than 14 days, leaving one backup.

## Probe 4: Retention, then restore

The probe took a backup of the fixture database, set Retention to 1 as `victim` (`PUT /app/settings`, 200), ran `applyRetention`, and restored the backup into an empty database with `restore.sh <stamp>`. At the time of the run (about 21:50 UTC), Retention deleted 18 of the 21 fixture Messages, four of them Wizzaroo Messages with a link (`wizzaroo-teacher-invite`, `wizzaroo-parent-invite`, `wizzaroo-family-device-signed-in`, `wizzaroo-family-join-request`).

All 18 came back, each linked one with its link in `text`, and the restored `settings.log_retention_days` is 90, the value at backup time, not the 1 set since. So a restore undoes every Retention sweep since the backup, and the next sweep runs with the old setting: at 90 days, the Messages between 1 and 90 days old stay a further 89 days. There is no step in the runbook to re-apply Retention or to re-run a sweep after a restore (`docs/operations/backups-and-restore.md`, Restore). Each backup also holds every deleted Message for up to 14 nights (`BACKUP_KEEP_DAYS`), so a Message's real lifetime is Retention plus 14 days, which the guide (`docs/guide/logs.md`, Retention) doesn't say.

## Probes 1 and 2 on the E1 deployment

The gated run's probes were repeated on [the pen-test deployment](../deployment.md) itself, on 20 November 2026, with the same results. A backup taken with `pen_test_compose exec backup backup.sh` begins `age-encryption.org/v1`. `age --decrypt` with a freshly made identity answers `no identity matched any of the recipients`, and `pg_restore --list` can't read the file, while the deployment's own throwaway identity opens it (21 `TABLE DATA` entries). Then `rclone deletefile` with the backup container's own credential deleted it from the stand-in remote (exit 0, remote empty). Refuted and confirmed (#127) as above. No production secret, remote or identity was used.

## Checks every scope issue carries

Applied:

- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** Backups are sealed (probe 1, refuted); Wizzaroo's links inside them are kept 14 nights past Retention and come back on a restore (probe 4); the age identity's default place is unignored and on the server (probe 5).
- **Logs are a copy of the data.** The backup container's log holds remote names and stamps, no personal data; counted in Retention: it isn't, but it holds nothing to count. The backups themselves are the copy, counted in probe 4.
- **Configuration fails closed.** `backup.sh` and `restore.sh` refuse to run with `BACKUP_AGE_RECIPIENT`, `BACKUP_RCLONE_REMOTE` or `BACKUP_AGE_IDENTITY_FILE` unset (`:?`; `src/backup-restore.test.ts` pins one). The `BACKUP_AGE_IDENTITY_FILE` Compose default (`./backup-identity.txt`) is a fail-open default: a restore runs with whatever file is there.
- **Nothing is left to a collaborator to bound.** The nightly loop has no bound on failed nights (probe 3), and `restore latest` trusts whatever sorts last on the remote (probe 2b).
- **Run the probes against a real Postgres.** Every container probe does, with production's backup image.
- **A test that passes either way proves nothing.** Every `it.fails` was run as a plain `it` and failed on its property assertion (exit 0 where refusal was expected, the planted User present, ten failed nights, 18 Messages back, the files not ignored), never on setup.

Not applied: **refusals give nothing away**, **every refusal comes from a closed set**, **odd input**, **idempotency keys**, **internal headers** and **path-matching middleware**: backups and restore have no HTTP surface.

## Since the probe

#127, #128, #129, #130 and #131 are fixed in the third round's pull request (fixed, unverified). In `src/pen-test/probes/d3.test.ts` each `today_` test is now a `(regression)` test asserting the fixed behaviour, and each `it.fails` is a plain `it`. `src/backup-restore.test.ts` covers the rest.

- **#127, the rclone credential.** `backup.sh` deletes nothing by default. Old backups are the remote's lifecycle rule's to delete, and the runbook (`docs/operations/backups-and-restore.md`, "An append-only remote") asks for a credential that can add, list and read but not delete or overwrite, with Object Lock, for B2, S3 and SFTP. Pruning from the server is kept only behind `BACKUP_PRUNE_RCLONE_REMOTE`, a second remote with a credential that may delete; the runbook says that brings the finding back. `backup.sh` uploads with `rclone copyto --inplace`, as an append-only server refuses rclone's upload-then-rename. The probe's `it` now runs against a real append-only remote rather than the local path: an SFTP server (OpenSSH's `internal-sftp -u 0222 -P remove,rename,…,setstat,…`) whose account can create files and can't remove, rename or rewrite them, enforced by the server. `backup.sh` takes a backup with that credential (exit 0); `rclone deletefile`, `rclone delete` and an overwrite of the backup with the same credential all fail, and the backup's sha256 is unchanged. The local remote, which can delete, stays as the stand-in for the other probes.
- **#128, the forged backup.** No signing key on the server would help: the backup job runs there, so an intruder can use any key it can. Instead a restore takes no backup on trust. `restore.sh` with no argument, or with `latest`, lists the backups (stamp, size, remote modified time; a stamp later than now marked `refused=future-stamp`) and restores nothing. It restores only `restore.sh <stamp> <sha256>`, refuses a future stamp, and checks the downloaded file's sha256 against the one given before it decrypts. `backup.sh` logs each backup's record, `backup.finished stamp=… size=… sha256=…`, and the runbook asks the operator to keep a copy of those lines off the server (copied off weekly, or a logging driver to an off-server store). The trade-off, as the runbook states it: a forged backup with a stamp from after the copy was taken isn't in the record, and a forged dump put under a recorded name doesn't match its sha256, so neither is restored; a backup the job itself made after an undetected break-in is in the record and can't be told apart, so the operator restores one from before the break-in. Without a record kept off the server the check is only as good as the operator's own `sha256sum` (the runbook says so). The regression test plants the probe's 2099 backup and shows `latest` refused and listed as a future stamp, and the forged stamp refused even with its own sha256; the `it` also puts the forged dump under the honest backup's name and shows the restore refuses it (sha256 mismatch), the planted User restored by neither.
- **#129, the silent night.** `nightly.sh` exits when a night fails, so the container restarts (and waits for the next night) instead of carrying on. `backup.sh` records each run's outcome (`last-success`, `last-failure` in `BACKUP_STATE_DIR`), and a new `backup-health.sh` is the `backup` service's healthcheck in `docker-compose.yml`: unhealthy when the last run failed, or when none has succeeded for 26 hours (counted from the container's start before the first). A run by hand (`docker compose exec backup backup.sh`) counts, so a fixed backup turns healthy without waiting. Each step of `backup.sh` names itself when it fails; a full disk now logs `backup.dump.failed` after age's error. Both nights in probe 3 now stop after one failure (`nightly.exit=1`) and the healthcheck fails (`backup.health.failed reason=last-night-failed`). Nothing emails the owner: the health status is what a monitor watches, and an unhealthy `backup` also fails `ops/deploy-server.sh`'s `docker compose up -d --wait`, which the owner sees.
- **#130, Retention and restore.** `restore.sh` requires `RESTORE_RETENTION_DAYS`, the Retention in force now (1 to 3650). After `pg_restore` it sets the restored Settings' Retention to it and deletes every Message older than it, as the worker's sweep does (`src/sending/retention.ts`), logging `backup.restore.retention-applied days=… deleted_messages=…`. Probe 4 now restores with 1 day: none of the Messages the sweep deleted comes back, nor any link, and the restored Retention is 1. `docs/guide/logs.md` now says an email's real lifetime is Retention plus `BACKUP_KEEP_DAYS`.
- **#131, `.gitignore`.** It names `backup-identity.txt` and `key.txt`. The Compose file's `restore` service no longer defaults the identity to `./backup-identity.txt` in the checkout (it mounts `/dev/null` unless one is named, and `restore.sh` refuses an empty identity), and the runbook has the operator make the key on their own machine, copy it to the server outside the checkout for the restore, and `shred` it after.

Left for the owner: whether the record of sha256s should leave the server automatically (the platform sends email, but the backup container has no SMTP settings, and a channel the server writes to is one an intruder can write to as well), and whether an unhealthy `backup` should block a deploy, as `--wait` now makes it.
