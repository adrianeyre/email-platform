# I5: the SMTP provider settings

The findings note for scope issue #107 (I5) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H6. It names files, lines and exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `2f11db2`, and the [fixtures](../fixtures.md) by handle and id. No credential, key or seed appears here: the stored SMTP password is read from the database and only ever compared, never printed.
- **The probes** are `src/pen-test/probes/i5.test.ts`, in the gated run against a real Postgres with the E2 fixtures loaded and the API built as production builds it, with production's `sendEmailOverSmtp`. The servers the SMTP host is pointed at are ones the tester controls: a small SMTP server and a non-SMTP banner service written with Node's `net` in the test, and a Mailpit with a self-signed certificate that offers STARTTLS. The relay in the middle is a TCP proxy in the test that removes `STARTTLS` from the server's EHLO answer and records every byte the client sends. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a plain passing test.
- **The live observations** below were taken on the [E1 deployment](../deployment.md) on 21 November 2026, as `victim`, pointing the SMTP provider at addresses on each network and reading what `POST /app/settings/test` answered.
- **Cited, not refiled:** that the SMTP reply text reaches the Message's `error`, read by the Message's sender (any API Key, #118) and by the Idempotency-Key replay (#119), is S1's and S2's; that any API Key reads any Message's `error` is K1 #118. This note cites those rather than refiling them.

## Probe 1: the test send as a port scanner and banner grabber

`POST /app/settings/test` (`settings-routes.ts:61-104`) reads the stored SMTP settings and calls `sendEmail` at once, then hands the caller `providerMessageId` on success or, in a `502`, `describeError(error)` — the connection error or the server's own greeting. `smtpHost` is any string and `smtpPort` any port 1-65535 (`settings-routes.ts:38-42`), and the `api` container sits on the internal `database` network as well as `default`, so the test reaches anything the container can. The error it returns tells the states apart:

- **a closed port** → `connect ECONNREFUSED <host>:<port>`, at once;
- **a name that will not resolve** → `getaddrinfo ENOTFOUND <name>` / `EAI_AGAIN <name>`;
- **a service that is not SMTP** → its greeting verbatim: a service answering with a non-`220` banner comes straight back in the message (`Invalid greeting. response=<banner>`), a banner grab;
- **a port that hangs** → `Greeting never received` after the 30 s greeting timeout (`delivery.ts:30`).

Live on the E1 deployment, as `victim`, each `smtpHost`/`smtpPort` through `POST /app/settings/test`:

| Target (from the `api` container) | What the test send answered                                                 |
| --------------------------------- | --------------------------------------------------------------------------- |
| `postgres:5432`                   | `502` `Greeting never received` after 30 s — the port is open and held      |
| `postgres:5433` (closed)          | `502` `connect ECONNREFUSED 172.20.0.2:5433` — and it reveals the IP        |
| `api:4320`, `entry:43320`         | `502` `Timeout` after 30 s — open, HTTP, no SMTP greeting                   |
| `mailpit:8025` (Mailpit's HTTP)   | `502` `Connection closed unexpectedly`                                      |
| `worker:4320`, `backup:5432`      | `502` `connect ECONNREFUSED 172.20.0.5:4320` / `…0.4:5432` — mapped, closed |
| `mailpit:1025` (the real SMTP)    | `200` `providerMessageId` — the one that is actually SMTP                   |
| `1.1.1.1:25`                      | `502` `connect ENETUNREACH 1.1.1.1:25` — the deployment has no way out      |

So a User maps the internal network — which hosts answer, which IPs they have, which ports are open, closed or non-SMTP — from the published port alone, including `postgres:5432`, which no User can otherwise reach. The gated run pins the same behaviour against a closed port, a name that will not resolve, a non-SMTP banner service and the tester's SMTP server. Confirmed; filed as **D** (#184).

## Probe 2: the AUTH credentials reach a server the tester controls

Pointing `smtpHost`/`smtpPort` at the tester's own SMTP server and running the test send, the worker completes the AUTH exchange: the stored `smtpUsername` and the decrypted `smtpPassword` both arrive at the server (the probe reads them back from the database, decrypts them as the worker does, and finds each in the bytes the server received, in the clear and as the base64 of the `AUTH LOGIN`/`PLAIN` exchange). The password is the one the UI "never shows again" and `GET /app/settings` returns only as `hasSmtpPassword: true` (`settings-store.ts:68`). Because `PUT /app/settings` keeps the saved password when none is given (`settings-store.ts:84-91`), a User changes **only** the host and port, leaves the password untouched (`hasSmtpPassword` stays true), runs the test send, and the saved password is delivered to a server they chose — recovering a write-only secret without ever re-entering it. Every User has full rights (ADR 0005), so this is any User exfiltrating the shared SMTP credential. Confirmed; filed as **E** (#185).

## Probe 3: STARTTLS stripped with `smtpSecure: false`

`smtpPort` defaults to 587 and `smtpSecure` to false (`schema.ts:61-62`), and `delivery.ts:31-42` passes neither `requireTLS` nor `ignoreTLS` to Nodemailer, so the connection is opportunistic: it upgrades with STARTTLS only if the server offers it. A relay that removes the `250-STARTTLS` line from the server's EHLO answer — anything on the path between the home server and the provider — leaves the client believing the server cannot do TLS. In the probe, with STARTTLS stripped, the worker went on in plaintext and completed AUTH: the relay saw the username and password in the clear and never saw a `STARTTLS` command. The control (the same relay, not stripping) shows the password does not cross the relay in the clear when STARTTLS is left alone. Because Mailpit allows insecure AUTH, the stripped send still succeeded (`200`); a real provider that requires TLS would refuse, but only _after_ the client had already sent the credentials in the clear on the earlier attempt. Confirmed; filed as **F** (#186).

## Probe 4: are certificates verified when TLS is used (refuted)

`delivery.ts` passes no `tls` options, so Nodemailer uses Node's default, `rejectUnauthorized: true`. Pointed at the self-signed Mailpit with `smtpSecure: false` so STARTTLS is offered and attempted, the worker refused the upgrade with a certificate error (`self-signed certificate`) and the send failed `502`, rather than trusting it. The same default applies to the `smtpSecure: true` implicit-TLS path. So when the worker does reach TLS it verifies the certificate; this is **refuted** as a weakness, and pinned by a passing test. The gap is not that TLS is unverified but that nothing _requires_ TLS (probe 3): verification only bites once a TLS handshake happens, and stripping STARTTLS means none does.

## Probe 5: what an SMTP reply puts into `messages.error`, and who reads it

A send that the provider refuses stores the provider's reply verbatim in `messages.error` (`send-worker.ts:85-96`, via `describeError`), with the Message marked `failed`. In the probe, the tester's server answered `RCPT` with `550 5.1.1 …` and that whole line landed in `messages.error`. `summariseMessage` returns `error` on `GET /v1/messages/:id` (`message-routes.ts:85`), which any API Key reads for any Message (K1 #118), and the UI log page shows it to every User (`page-logs.tsx:203-205`). So an SMTP reply — including one from a server the tester steered the send toward — becomes a field read back by the Message's sender and by every User. The disclosure of the reply text is already filed as S1's SMTP-text note and K1 #118 / S2 #119; the steering is probe 1's finding **D** (#184). Cited, not refiled.

## Checks every scope issue carries

Applied:

- **Configuration fails closed.** `smtpHost`/`smtpPort` accept any host and port and the test send connects to them at once (probe 1); `smtpSecure: false` falls back to plaintext when STARTTLS is removed rather than refusing (probe 3). Neither fails closed.
- **A secret is sealed or hashed where it is kept.** The SMTP password is sealed at rest (AES-256-GCM, `settings-store.ts`), but it is handed in the clear to any server a User names (probe 2) and to the path when STARTTLS is stripped (probe 3), and recoverable without re-entry (probe 2).
- **Nothing is left to a collaborator to bound.** TLS is left to the provider offering STARTTLS and to the network not stripping it (probe 3); the test send's reach is left to what the container's networks allow (probe 1).
- **Every refusal comes from a closed set.** The test send's `502` carries the provider's connection error or greeting verbatim (`describeError`), which is how it doubles as a scanner (probe 1); `messages.error` carries the SMTP reply verbatim (probe 5).
- **Run the probes against a real Postgres.** The probe world is a real Postgres with the fixtures and production's `sendEmailOverSmtp`; the servers pointed at are real listeners the test controls.
- **A test that passes either way proves nothing.** Every `it.fails` was run once as a plain `it` and failed on its property assertion (a closed and an open port gave different answers; the password reached the tester's server; the password crossed the stripping relay in the clear; an open and a closed port were told apart), never on setup.

Not applied: **refusals give nothing away** (the test send is meant to report, and does — that is probe 1, not a separate check), **odd input / NUL** (S1's, pinned there), **idempotency keys**, **internal headers** and **path-matching middleware**: this surface is the SMTP settings and the test send, not the `/v1` message routes.

## Since the probe

#184 is fixed, unverified (21 November 2026, sixth pull request), but for two residues no test send can lose. A failed test send answers `502` `smtp_failed` with `The test email was not sent: ` and the failure's class from `classifySendFailure` (`src/sending/send-failure.ts`), the one classifier a Message's `error` uses too (I1's #173), and the test send's record in the Logs keeps the same class. Every failure before an SMTP session (a closed port, a name that won't resolve, a timeout, a failed TLS handshake, a greeting that isn't SMTP's `220`, whatever its first digits) is one class, `The SMTP provider could not be reached, or the connection to it failed (a name, network, TLS or timeout failure)`, with no host, container IP, port or banner. An SMTP server that refuses a command after its greeting is told as `The SMTP provider refused it with reply <code>[ <status>] (permanent|temporary)`, the reply and RFC 3463 status codes without the text, which a User needs to fix a wrong password (`535 5.7.8`) or sender. Nodemailer's code, the system error's code, the command and the reply code go to the api's log (`settings.test_send.failed`) for the owner. The residues, pinned by `today_ the test send still tells an SMTP server that takes the test email from anything else…`: a test send that works must say so, so a User still learns that something speaking SMTP answers at a host and port (by a `200`, or by a refusal with a reply code), and a port that holds the connection still takes the 30 s timeout to answer where a closed one answers at once. Neither tells closed, unresolved, filtered and non-SMTP apart, or names an address. Probe 5's `it.fails` `the test send does not let a User reach and tell apart hosts only the api container can talk to` asks for a working SMTP server and a closed port to answer alike, which is that residue, so it stays an `it.fails`, beside that `today_`. In `src/pen-test/probes/i5.test.ts` the two probe 1 `today_` tests are now `(regression) the test send answers a closed port, a name that will not resolve and a service that is not SMTP alike, naming none of them (#184)` and `(regression) the test send no longer hands back the banner of a service that is not SMTP (#184)`, and `the test send does not report whether an arbitrary host and port answered, so it is not a port scanner` is a plain `it`. Probe 4's refuted test now asserts the class rather than Node's certificate message, and probe 5's `today_` is I1's #173 regression, `(regression) an SMTP refusal is stored in messages.error by its reply and status code only…`.

#185 is fixed, unverified (21 November 2026, sixth pull request). `PUT /app/settings` refuses with `422` `validation_failed`, on `smtpPassword` ("Enter the SMTP password again: changing the host or port doesn't keep the saved one"), a change that moves the host (compared without case) or the port while keeping a saved password, and changes nothing. Giving the password, or clearing it with `null`, is taken; so is clearing the host, which sends the password nowhere. The check and the update run in one transaction on the locked settings row (`updateSettings` in `src/settings/settings-store.ts`), so a concurrent save can't slip a host change past it. Refusing was chosen over clearing the password: the Delivery page always sends the whole form, so a silent clear would leave a User believing the provider still had its password until sends failed, where the `422` shows under the form and the field's hint now says a host or port change needs it again. In `src/pen-test/probes/i5.test.ts` the `today_` test is now `(regression) pointing the provider at the tester's own server without re-entering the password is refused with 422, and the stored password never reaches it (#185)`, and `the stored SMTP password is not sent to a host a User points the provider at without re-entering it` is a plain `it`, rewritten so it no longer expects the repointing `PUT` to succeed (it sets a username first, so a send would AUTH). The probes that repoint the provider now re-enter the password, as a User who knows it can. `src/integration.test.ts` covers a host change, a port change, the same host in upper case and clearing the password.

#186 is fixed, unverified (21 November 2026, sixth pull request). `sendEmailOverSmtp` passes Nodemailer `requireTLS` whenever it sends AUTH, that is whenever a username is set, so without `smtpSecure` the client always issues `STARTTLS` and fails the send, before AUTH, when the server refuses it or the upgrade fails; with `smtpSecure` the connection is TLS from the start. With no username there is no AUTH, and STARTTLS stays opportunistic, so Mailpit, which has no TLS, keeps working as the development and test stacks' SMTP server (ADR 0001) as long as it is set with no username, as the local setup guide already said. The pen-test fixtures and `src/integration.test.ts` set no username for the same reason (the fixtures still seal a password, which I3's probes need), and the integration suite checks that a username against Mailpit fails the test send and delivers nothing. Requiring TLS on every connection was not chosen: it would take Mailpit away from development and the tests, and protects nothing when no credential is sent. An owner whose provider lacks STARTTLS on its submission port has to use port 465 with **Connect with TLS from the start**. In `src/pen-test/probes/i5.test.ts` the `today_` test is now `(regression) with smtpSecure false and a username, a relay that removes STARTTLS still sees STARTTLS sent, and never AUTH in the clear (#186)` and `with smtpSecure false the worker will not fall back to plaintext AUTH when STARTTLS is removed` is a plain `it`.
