# I3: Secrets and fail-closed configuration

Scope issue #105. Answers H10. Keep private on the same terms as the PRD (`docs/product-requirements-document/pen-testing.md`): this note names files, lines and exploit chains. Read against: commit `2f11db2`. The probes are in `src/pen-test/probes/i3.test.ts`, in three parts:

- the config parser, `loadVars` (`src/config/vars.ts`), driven in-process with `vi.stubEnv`;
- the real entrypoint, `src/index.ts`, started with tsx as a child process in each role (`api`, `worker`, `migrate`, `cli`), with an environment built from nothing, against the probe world's Postgres (or a Postgres of its own, made as Compose makes production's) and Mailpit, in the gated run;
- `docker compose --env-file /dev/null -f docker-compose.yml --profile restore config`, with placeholder values and no `.env` read, gated on `docker compose` being available.

## 1. Unsetting each variable

**The app** reads four variables, all in `src/config/vars.ts:63-68`: `DATABASE_URL`, `APP_URL` and `ENCRYPTION_KEY` are required (`required`, `:16-22`, treats unset and `""` alike), `PORT` defaults to 4320. `src/index.ts` checks the role, then calls `loadVars()` at the top level before anything connects, so a throw is an uncaught error and exit 1. Started as a child process with each required variable unset, in each of the four roles, all twelve exit 1 with `Error: <NAME> must be set` on stderr. A wrong-length `ENCRYPTION_KEY` is refused by name and its value is not printed. Refuted. `PEN_TEST_DEPLOYMENT` is read only by the fixture loader, which refuses without it (E2), and `SITE_*`, `CHROME_PATH` only by the site build: out of this scope.

**Compose** requires, with `:?`, `POSTGRES_PASSWORD`, `APP_URL`, `ENCRYPTION_KEY`, `BACKUP_AGE_RECIPIENT`, `BACKUP_RCLONE_REMOTE` and `BACKUP_RCLONE_CONFIG_FILE`. With each unset, and each set to `""`, `docker compose config` exits non-zero and its stderr carries the `set <NAME> in .env` message. `BACKUP_KEEP_DAYS` (14), `BACKUP_HOUR_UTC` (2), `RESTORE_DATABASE` (`email_platform`) and `BACKUP_AGE_IDENTITY_FILE` (`./backup-identity.txt`, D3's #131) default, as `docs/operations/backups-and-restore.md` documents. `backup.sh`, `nightly.sh` and `restore.sh` repeat the `:?` checks under `set -eu`. Refuted. `PORT` and `DATABASE_URL` are fixed by Compose (`docker-compose.yml:8-9`), so the operator never sets them in production.

**1c, whitespace** (`vars.ts:11-22` counts only `""` as unset): a whitespace `ENCRYPTION_KEY` decodes to 0 bytes and a whitespace `APP_URL` doesn't parse, so both are refused by name. But `PORT=" "` reads as `Number(" ")`, 0, and the api listens on a port the OS picks; `DATABASE_URL=" "` passes the parser and `migrate` then fails on connecting with a driver error that doesn't name it. Compose fixes both in production, so it reaches `pnpm local`, `pnpm migrate` and `pnpm cli` from a `.env`: low (#169). Compose's own `:?` takes `" "` as set (2b).

## 2. Weak values

**2a, `.env.example`'s `ENCRYPTION_KEY`** is 32 bytes of `0x07`; `vars.ts:53-61` checks only the decoded length, so it, and an all-zero key, load. With it, `migrate` exits 0, `worker` logs `worker.started`, and `api` answers `/health` 200, with no warning. Signed in as `victim` over HTTP to that api, saving an SMTP password under Delivery seals it so that the key committed in the repository opens it. Compose renders it into `api`, `worker` and `migrate` unchanged (`docker-compose.yml:11`). Confirmed, medium (#165): this is H10's own case.

**2b, `POSTGRES_PASSWORD`** is never seen by the app, only by Compose (`:8,29,84,107`), whose `:?` refuses only unset or empty. `x` and `" "` both render, substituted as they are into `POSTGRES_PASSWORD`, `PGPASSWORD` and every `DATABASE_URL`. A `postgres:18-alpine` made with either initialises, and `migrate` (exit 0) and `api` (`/health` 200) start against it over a `DATABASE_URL` built as Compose builds it, the space included. Confirmed, medium (#166). With D1's superuser login (#121), shared by every container (#138), held on networks with a way out (#139) and with its SCRAM verifier readable (D1 1f), a one-character password is the whole of Postgres's defence.

**2c, an `http:` `APP_URL`** starts the api and serves `/health`; there is no notion of development in the app to refuse it outside of. The parser takes any scheme `URL.canParse` does, `javascript:` and `ftp:` included. ADR 0003 decides "no reverse proxy, TLS terminator" across the LAN and tailnet, and `docker-compose.yml:10`'s own hint suggests `http://email.home:4320`, so plain HTTP is the documented production. Confirmed as a documented decision, with no date or condition for it to stop being true: low (#168), as A2's #146 was for ADR 0005. The session cookie's attributes on `http:` are I1's (#102).

## 3. Changing `ENCRYPTION_KEY` on a running install

The probe world seals the SMTP password with one key (the fixture loader, as Delivery does). A second api, built with another valid key over the same database, and a real `worker` started with that key, stand in for the restart.

- **Boot:** `worker` logs `worker.started` and `api` answers `/health`. Nothing opens the sealed value at boot.
- **Delivery page:** `GET /app/settings` answers 200 with `hasSmtpPassword: true` (`toPublicSettings`, `settings-store.ts:67`, reports only that a sealed value exists).
- **Send a test email:** `POST /app/settings/test` answers 500 `internal_error`, "Something went wrong": `readSmtpSettings` throws GCM's `Unsupported state or unable to authenticate data` outside the route's `try` (`settings-routes.ts:68-69`). Nothing reaches Mailpit.
- **The worker:** each attempt records that same error on the Message and throws to retry; at the retry limit (3, `jobs.ts:12`) the Message is `failed`. The real worker did the same to a Message queued through `/v1`. Nothing reaches Mailpit. The old key, the control, still sends.
- **The way back:** re-entering the SMTP password under Delivery reseals it under the new key, after which the old key can't open it. There is no rotation path otherwise: no second key to read with, no reseal command, and the docs say only that restoring needs the same key (`backups-and-restore.md:35`).

Confirmed, medium (#167): rotating away from the `.env.example` key (#165), or restoring under the wrong key, starts a stack that looks healthy and loses every email, Wizzaroo's resets included, until someone reads a Message's error.

## 4. The sealed format

`src/lib/secrets.ts:92-129`: AES-256-GCM, `v1.<iv>.<tag>.<ciphertext>` in base64url.

- **IV reuse:** a fresh `randomBytes(12)` per seal; 10,000 seals of one password reuse none. Every save under Delivery reseals with a fresh IV. Refuted.
- **Tag length:** 16 bytes, as written and as stored in the fixture's `settings` row (`^v1\.[\w-]{16}\.[\w-]{22}\.`). Refuted.
- **A truncated tag:** `decryptValue` passes the stored tag to `setAuthTag` with no `authTagLength`, so the check is Node's: Node 26 refuses every length but 16 (`Invalid authentication tag length`), so 15, 12, 8, 4, 1 and 0 bytes are all refused, as is a flipped ciphertext bit and the right value under another key. Refuted, on the runtime's default: a fix could still pin `authTagLength: 16` so it doesn't rest on Node's version. Not filed.
- Not probed further: no associated data binds the sealed value to its row, which is moot while it is the only sealed value; `decryptValue` ignores any fifth `.`-separated part.

## Checks every scope issue carries

Applied:

- **Configuration fails closed.** This issue's subject: unset, empty and whitespace for each variable the app and Compose read, and the weak values H10 names (1, 2).
- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** The SMTP password is sealed in `settings` (AES-256-GCM, a fresh IV, a full tag) and `GET /app/settings` serves neither it nor the sealed value: holds. Under `.env.example`'s key the seal is only nominal (#165). `ENCRYPTION_KEY` and `POSTGRES_PASSWORD` themselves are kept in plain text in `.env` and every container's environment for the container's life (D1's #139; who can `docker inspect` them is I4's, #106).
- **Every refusal comes from a closed set.** A key that can't open the sealed password turns the test send into a 500 (#167); the boot refusals are uncaught errors on stderr, by name, which is right for a process that must not start.
- **Logs are a copy of the data.** Boot refusals name the variable and echo `PORT`'s and `APP_URL`'s values, never `ENCRYPTION_KEY`'s; the worker records GCM's message, not the password or key, on the Message.
- **Run the probes against a real Postgres.** The entrypoint probes run against the probe world's Postgres and two more made as Compose makes production's, and the key-change probes send through Mailpit.
- **A test that passes either way proves nothing.** Each `it.fails` was run as a plain `it` and fails on its own assertion: no throw from `loadVars` (three), an exit code 0 (two), a running api, a running worker, a 500, and a Compose exit 0.

Not applied, and why:

- **Refusals give nothing away**, **internal headers**, **middleware matches by segment**: no route of I3's own; A1, B1 and I1.
- **Odd input stops above the database**, **an idempotency key is bound to its payload and owner**, **nothing is left to a collaborator to bound**: no request input here; S1, S2 and K1.

Cross-references: the cookie on `http:` is I1's (#102); the containers' environments and hardening are I4's (#106); the SMTP provider settings themselves are I5's (#107); Postgres privilege is D1's (#121, #138, #139); backups and the age identity are D3's (#127-#131).

## Since the probe

#165, #166, #167, #168 and #169 are fixed in the fifth pull request (fixed, unverified). Their `today_` tests are now `(regression)` tests and their `it.fails` plain `it`s in `src/pen-test/probes/i3.test.ts`, except where noted; the parser's own cases are in `src/config/vars.test.ts`.

- **#165, `.env.example`'s `ENCRYPTION_KEY`.** Fixed, unverified (21 November 2026, fifth pull request). `loadVars` refuses a key whose 32 bytes are all one byte, the old `0x07` key and all-zero included, naming `ENCRYPTION_KEY` and never printing it, so `api`, `worker`, `migrate` and `cli` all exit 1. `.env.example` now leaves `ENCRYPTION_KEY` empty, with the `openssl rand -base64 32` hint, so a copied `.env` is refused as unset until a key is made. The tests' own key (`vitest.config.ts`) and the in-process fixtures (`src/integration.test.ts`, `src/api/route-guard.test.ts`) no longer use a repeated byte.
- **#166, a weak `POSTGRES_PASSWORD`.** Fixed, unverified (21 November 2026, fifth pull request). Compose's `:?` can't look inside a value, so the floor is checked where the password is first used: `provision` refuses a `POSTGRES_PASSWORD` (inside its `DATABASE_URL`) or a `DATABASE_*_PASSWORD` under 16 characters, holding whitespace or a control character, or one character repeated, by name, and every other app container waits on `provision`. Every role also refuses such a password inside its own `DATABASE_URL`, and any whitespace in it (the URL parser would drop a tab). A `DATABASE_URL` with no password (the development stack's trust login) is left to the server. Postgres itself still starts with the weak password; nothing that could log in with it does. The Compose `it.fails` `refuses a whitespace POSTGRES_PASSWORD` asserted `docker compose config` exits non-zero, which no change to `docker-compose.yml` can make true for an arbitrary password; it is rewritten to assert that `provision`, given the environment Compose renders, refuses it by name, and that `migrate`, `backup` and `restore` wait on `provision` and `api` and `worker` on `migrate`.
- **#167, a changed `ENCRYPTION_KEY`.** Fixed, unverified (21 November 2026, fifth pull request). `api` and `worker` open the saved SMTP password at boot and refuse to start, exit 1, with `ENCRYPTION_KEY can't open the saved SMTP password`, so queued Messages wait untouched for the right key. Under a running stack, `GET /app/settings` adds `isSmtpPasswordUnreadable`, the Delivery page says the password can't be read, the test send answers `409 smtp_password_unreadable` naming `ENCRYPTION_KEY`, and the worker records the same message instead of GCM's. The rotation path is `cli smtp-password:reseal` (prompts for the old key, reseals under the new) or `cli smtp-password:forget` when the old key is lost, documented in `docs/operations/backups-and-restore.md#changing-encryption_key`.
- **#168, an `http:` `APP_URL`.** Fixed, unverified (21 November 2026, fifth pull request), by the issue's second option: ADR 0003 now records when its plain-HTTP decision ends (reachable from beyond the LAN and tailnet, a second school or non-owner User, a sending application outside them, or a review by 21 November 2027), and `loadVars` refuses any `APP_URL` scheme but `http:` and `https:`, naming it. The two `it.fails` asserted that `http:` itself is refused, the first option; they are rewritten to assert that `javascript:` and `ftp:` are refused (by the parser, and by the real api) and that ADR 0003 carries the expiry, and the `today_` tests now pin that `http:` still starts, by decision.
- **#169, whitespace values.** Fixed, unverified (21 November 2026, fifth pull request). `PORT` must be digits only, so `" "` is refused by name rather than read as 0; `DATABASE_URL` must parse as a `postgres://` URL, so `" "` is refused by name before connecting. `APP_URL` and `ENCRYPTION_KEY` already refused whitespace by name.
