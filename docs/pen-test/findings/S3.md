## 1. Handlebars and prototype access

`src/templates/render.ts:23-37` compiles with Handlebars 4.7.10 (`node_modules/handlebars/package.json`), `noEscape` for subject and text, `strict: false`, no helpers registered and no `allowProto*` runtime options, so prototype access stays at its safe default.

**Sent:** 18 tricks, each wrapped in `[…]`, put in turn in `subject`, `html` and `text` of `POST /v1/templates/preview` with `variables: {name, list, obj}`: `{{constructor}}`, `{{constructor.name}}`, `{{__proto__}}`, `{{this.constructor.constructor}}`, `{{@root.constructor}}`, `{{name.constructor.prototype}}`, `{{list.constructor}}`, `{{obj.__proto__.polluted}}`, `{{lookup this "constructor"}}`, `{{lookup this "__proto__"}}`, `{{lookup (lookup this "constructor") "name"}}`, `{{#with "s" as |s|}}{{s.constructor.name}}{{/with}}`, `{{#with __proto__}}{{constructor}}{{/with}}`, `{{toString}}`, `{{valueOf}}`, `{{hasOwnProperty}}`, `{{__defineGetter__}}`, and the published pre-4.6 RCE chain (`string.sub.apply` building `Function`).

**Came back:** 200 and exactly `[]` for all 54. The RCE chain stops at `split` ("Access has been denied to resolve the property \"split\"…"). A Template saved with three of them (`slug: s3-prototype-probe`) and sent with `POST /v1/messages` stores `subject: "[]"`, `html: "[]"`, `text: "[]"` in `messages`. A raw body with `"variables":{"__proto__":…}` or `"constructor":{"prototype":…}` is refused 400 `FST_ERR_CTP_INVALID_JSON_BODY` by Fastify's secure JSON parser before Handlebars sees it. An own `constructor` variable renders normally (`"own"`), which is right.

**What an author can still reach** is Handlebars' built-in helpers (`if`, `unless`, `each`, `with`, `lookup`, `log`):

- `{{log x}}` calls `console.info` with `x` (`handlebars/dist/cjs/handlebars/logger.js`, level `info` by default). Preview with `html: "<p>{{log resetUrl}}</p>"` and `variables.resetUrl = https://wizzaroo.pen-test.invalid/reset/s3` called `console.info("https://wizzaroo.pen-test.invalid/reset/s3")`. On a send it runs at accept time in the `api` process (`acceptMessage` renders), and the `api` container's stdout is its container log. So any author, which is any API Key (H3, see K1), can make every future reset or Invite link it carries land in the container log, outside the `messages` table, outside Retention and in plain text. That is a copy D2 should count.
- The prototype-access denial itself writes a multi-line `console.error` the first time each property is tried, unstructured, into the same JSON-lines log.
- `{{helperMissing}}` / `{{blockHelperMissing}}` answer 422 with V8's own text "Cannot read properties of undefined (reading 'call')": Handlebars and engine text reaching the caller. See I1 / B1 (H16, `template-routes.ts:203-219`); not proposed here.

**`showIf`:** `renderBlock` writes `{{#if ${condition}}}` with the Block's `showIf` verbatim (`src/templates/design/render-html.ts:321-322`). A Design with `showIf: 'true}}{{log "show-if-ran"}}{{/if}}{{#if true'` made the server call `console.info("show-if-ran")` when it rendered the Design (preview with the fixture Header, so `composeHtml` re-renders it, `compose.ts:67-72`). The designer shows `showIf` as a condition field, so a User who opens a Design an API Key wrote sees a condition, not the Handlebars it carries.

## 2. URLs in Button, Image and Socials Blocks

`wrapLink`, `renderButton`, `renderImage` and `renderSocial` escape `& < > "` but keep any scheme (`render-html.ts:157-160,183,213,239`). Design sent through preview with the fixture Header (`world.ids.parts.header`) so the server renders it:

| Block   | Field  | Sent                                       | In the rendered HTML                                                            |
| ------- | ------ | ------------------------------------------ | ------------------------------------------------------------------------------- |
| Button  | `url`  | `javascript:alert(document.domain)`        | `href="javascript:alert(document.domain)"`, twice (VML `v:roundrect` and `<a>`) |
| Image   | `src`  | `data:image/svg+xml,<svg onload=alert(1)>` | `src="data:image/svg+xml,&lt;svg onload=alert(1)&gt;"`                          |
| Image   | `href` | `javascript:alert(2)`                      | `href="javascript:alert(2)"`                                                    |
| Socials | `url`  | `javascript:alert(3)`                      | `href="javascript:alert(3)"`                                                    |
| Socials | `url`  | `data:text/html,<script>alert(4)</script>` | `href="data:text/html,&lt;script&gt;alert(4)&lt;/script&gt;"`                   |

What it does to a recipient: mainstream webmail strips or neuters `javascript:` links and `data:` navigation, so the risk is to desktop or self-hosted clients and to anyone who opens the HTML part in a browser; it is a hygiene gap rather than a working exploit on its own. In the platform's own UI the previews are `sandbox=""` (no scripts), so clicking such a link there runs nothing. The designer's Image preview renders `<img src={block.src}>` in the app's own document (`designer.tsx:296-305`); React and browsers don't run script from an `<img src>`, but a remote `src` loads in the User's browser with the app's origin as referrer.

## 3. HTML Block and Header contents, the designer frames and the previews

The HTML Block is emitted verbatim (`render-html.ts:263-264`) and a hand-written Header's body is spliced in by `composeHtml` (`compose.ts:73-84`). Sent: `<script>parent.document.title="pwned"</script><img src="x" onerror=…><base href="https://evil.pen-test.invalid/"><meta http-equiv="refresh" content="0;url=https://evil.pen-test.invalid/"><link rel="stylesheet" href="https://evil.pen-test.invalid/x.css">`. It reaches the rendered HTML byte for byte, both as an HTML Block in a Design and as the fixture Header's HTML (`PUT /v1/headers/:id` with the `secondApp` key, then a preview using it). That is the documented power of an author (ADR 0006, 0007); who counts as an author is K1's H3 finding.

**Frames, read by rendering `Designer` to static markup** with that HTML in one HTML Block and in `lockedTop`:

| Frame                                     | Source                         | `sandbox`           | `srcdoc` carries                                                                  |
| ----------------------------------------- | ------------------------------ | ------------------- | --------------------------------------------------------------------------------- |
| Locked Header / Footer (`LockedPartView`) | `designer.tsx:793-806`         | `allow-same-origin` | the part's HTML verbatim (via `renderDesignFragment` in `page-templates.tsx:714`) |
| HTML Block (`HtmlPreview`)                | `designer.tsx:396-404`         | `allow-same-origin` | `<style>body{…font-family:${fontFamily}…}</style>` then the HTML verbatim         |
| Template preview                          | `page-templates.tsx:418-422`   | `""`                | the server-rendered HTML (plus the dark-mode style)                               |
| Template thumbnail                        | `page-templates.tsx:1171-1174` | `""`                | the design rendered client-side                                                   |
| Message in the log                        | `page-logs.tsx:240-244`        | `""`                | the stored HTML                                                                   |

What a browser does with `sandbox="allow-same-origin"` and no other token: scripts, inline handlers and `javascript:` URLs don't run; forms don't submit; popups, modals and top-level navigation are blocked; `<meta http-equiv="refresh">` may navigate only the frame itself, and the page it lands on stays sandboxed. So nothing runs. What still happens in the User's browser while they edit:

- `<img>`, `<link rel=stylesheet>`, `@import`, CSS `url()` and web fonts load from any host, telling it the User's IP, browser and when they opened the Template;
- a `<meta refresh>` replaces the Header strip with any remote page (no scripts there either), which can be dressed as the platform's own UI;
- the frame is same-origin with the app, so the app's own code reads it (`contentDocument.body.scrollHeight`, `designer.tsx:389-392`, `:800-805`), and the moment anyone adds `allow-scripts` for convenience, the HTML of any author runs as the signed-in User with full rights (H5). The previews' `sandbox=""` is the safe pattern; the comment "a frame that runs no scripts" (`designer.tsx:384`) is true only while that second token is never added.

With no content security policy on the app (H9, see I1), nothing else limits what the frames fetch.

## 4. `fontFamily`

`safeFont` removes `" ; < > { }` (`render-html.ts:50`) but leaves `&`. In a `style="…"` attribute the browser decodes character references before CSS sees the value, so `&#59` becomes `;`. Design `settings.fontFamily = "Arial&#59background:url(https://evil.pen-test.invalid/f)"` comes back as `style="font-family:Arial&#59background:url(https://evil.pen-test.invalid/f);…"` on every text `<div>` and Social label (`:235,245`), and a Button's `fontFamily` the same way (`:176,194`): one extra CSS declaration per element, here a remote background that loads when the recipient opens the email. Server-side this only matters when a Design is re-rendered (`composeHtml` with a Header or Footer), and an author can already write any HTML, so its weight is that the designer's own "can't break out" escaping is weaker than it says and that a User reusing a Design an API Key wrote inherits it.

In the designer the value goes into the HTML-block frame's `<style>` with no escaping at all (`designer.tsx:403`): `Arial}</style><script>alert(1)</script><style>` closes the style element and writes elements into the frame (the script doesn't run, per section 3). The `--email-font` custom property and React `style` objects (`designer.tsx:259,364,895`) go through the CSSOM and can't break out.

## 5. Server cost through `/v1/templates/preview`

The route compiles whatever it is sent, uncached, under the 36 MB `bodyLimit` (`http-server.ts:50`), with no output bound (`template-routes.ts:342-389`). Measured once each, small samples, on the tester's laptop:

- **Nested `{{#each}}`:** `{{#each l}}{{#each ../l}}{{#each ../../l}}x{{/each}}{{/each}}{{/each}}` (70 characters) with `l` of n numbers renders n³ characters: n = 50 → 122,500 in 14 ms; 100 → 990,000 in 84 ms (pinned); 200 → 7,960,000 in 687 ms. A fourth level, or n ≈ 812 at three levels, reaches V8's maximum string length (2²⁹ − 24 ≈ 536 M characters) and ends in `RangeError: Invalid string length` after holding that much memory, from a request of a few KB. The render is synchronous, so the `api` process answers nothing else meanwhile.
- **`<body` scan:** with a Header or Footer, `composeHtml` runs `/<body[^>]*>/iu` over a hand-written Template (`compose.ts:75`) and `bodyOf`'s `/<body[^>]*>([\s\S]*)<\/body>/iu` over a part's HTML (`:25-29`). On `"<body".repeat(n)` with no `>` each is quadratic: n = 2,000 (10 KB) 7 ms / 16 ms; 4,000 → 23 / 51 ms; 8,000 (40 KB) → 94 / 241 ms, about 4× per doubling. Arithmetic from the 40 KB point: 1 MB (200,000 tags) is 25² × 94 ms ≈ 59 s; the 36 MB limit (7.2 M tags) is 900² × 94 ms ≈ 76,000 s ≈ 21 hours of one event loop, from one key-authenticated request. The pinned test sends 40 KB and gets 200. A Header or Footer saved with such HTML makes every send and preview that uses it pay the same.
- **Depth:** 1,000 nested `{{#if}}` compile in 78 ms; 5,000 overflow the stack in about 1 s and are answered 422 "Maximum call stack size exceeded" (pinned). Depth is bounded by the stack; this one is refuted. The designer's own nesting is one level (`columns` hold leaves only, `model.ts` `readBlock`).

No load was sent: each size was rendered once. The figures belong to the request-rate pre-condition (I2a/I2b); the finding is that preview has no cost bound of its own.

## Checks every scope issue carries

Applied:

- **Every refusal comes from a closed set.** Deep nesting answers 422 rather than 500; but `{{helperMissing}}` echoes V8's text and a parse error echoes Handlebars' text in 422s. Recorded here, owned by I1/B1 (H16).
- **Odd input stops above the database.** Preview never reaches the database except to load a Header/Footer by uuid; prototype-poisoning JSON stops at Fastify's parser (400). Very long input: see section 5.
- **Nothing is left to a collaborator to bound.** Handlebars and V8 are today the only bound on render size and time (section 5).
- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** `{{log}}` lets an author copy Wizzaroo's links into the container log, unsealed and outside Retention (1d).
- **Logs are a copy of the data.** Same; and the denial warnings are unstructured multi-line writes into the JSON-lines log. Hand-off to D2.
- **Run the probes against a real Postgres.** Every server probe runs in the gated world; the send probe reads the stored row back.
- **A test that passes either way proves nothing.** Each `it.fails` was run as a plain `it` and fails on its own assertion (sandbox value, srcdoc content, spy calls, URL list, regex, status).

Not applied, and why:

- **Refusals give nothing away** and **middleware matches by segment**: these routes sit behind the `/v1` and `/app` hooks; B1 owns them.
- **An idempotency key is bound to its payload and owner**: S2.
- **Internal headers are trusted only when the server set them**: no header is read on these routes; A1/I1.
- **Configuration fails closed**: I3.

Cross-references: any API Key rewriting the Wizzaroo Templates and Header is K1's (H3); the missing content security policy and frame headers are I1's (H9); `subject` header injection is S1's (H8).

The guide's [Templates](../../guide/templates.md) says so.

The `showIf` probes (#153, still open) used `{{log "show-if-ran"}}` as their witness, which now writes nothing; they inject `{{#with "show-if-ran"}}{{this}}{{/with}}` instead and look for that text in the rendered HTML, with the same `today_` / `it.fails` pair.

#137 is fixed in the fourth round (fixed, unverified). The `<body` scans in `src/templates/compose.ts` find the first `<body` and then the next `>`, and the last `</body>` with a global match, so `bodyOf` and `composeHtml` are linear and give the same answers: 200,000 unclosed tags (1 MB) take milliseconds. `renderTemplate` (`src/templates/render.ts`) bounds every render, send, preview and save alike, four ways, each refused with `422`: the rendered HTML and text may have 1,000,000 characters each and the subject 998 (#152); the subject, HTML and text may each hold 50,000 characters of `{{…}}` expressions, Header and Footer included, counted before compiling, since compiling costs time in proportion to them (10,000 `{{v}}` took a quarter of a second, 200,000 ran out of memory); and a render may spend 10,000,000 steps of work. The work budget is charged from inside Handlebars, in the Template's own environment: a compiler subclass makes each compiled block charge the length of its code each time it runs and puts every piece of output through a helper that charges its length, and the built-in helpers, each `{{#each}}` round, partials and decorators charge too. A compiled block has no loop of its own, so this pays for everything a render does: the three nested `{{#each}}` over 100 items are refused after a few milliseconds, as are a million empty rounds, a long variable escaped a thousand times, a path of 52 steps repeated in a loop, and inline partials that call themselves twice 40 deep; every shape tried stops within about 200 ms. Probe 5's first `today_` test is now `(regression) three nested {{#each}} over 100 variables are refused with 422 for the work they do, and a render past 1,000,000 characters for its length (#137)`, and `/v1/templates/preview refuses a render that grows past a bound (1 MB of output here)` is a plain `it`. The `<body` `today_` test is now `(regression) a hand-written Template of 150,000 unclosed <body tags (750 KB) is composed with a Header in linear time and answered 200 (#137)`. The depth `today_` test (5c) now sees 5,000 nested `{{#if}}` refused for their Handlebars length before compiling, and checks that 2,500, within it, still overflow the stack and are answered `422`. `src/templates/render.test.ts` and `compose.test.ts` hold the same checks.
