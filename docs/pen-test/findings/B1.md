# B1: every route compared with the hook it should have

The findings note for scope issue #95 (B1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H16's `/docs` bullet; H16's error-handler bullets are I1's (scope issue I1, #102). It names exploit chains, so **keep it private on the same terms as the PRD**. Probed at commit `d81eaa9`. The probes are `src/pen-test/probes/b1.test.ts`, with the router reading in `src/pen-test/probes/b1-routes.ts`. They run in the gated run against a real Postgres from [the probe world](../../../src/pen-test/probes/probe-world.ts), on an API built as production builds it **with a UI directory** (a two-file stand-in for `dist/ui`), so the SPA fallback and `@fastify/static`'s routes are in every list. The path tricks go over a real socket, because `inject` resolves `..` before Fastify sees it. No credential appears here; Users and keys are named by fixture handle.

## How the routes are found (probe 1)

`buildHttpServer` (`src/api/http-server.ts:84-259`) registers routes in three places:

- the root scope: `/docs` and its children (`@fastify/swagger-ui`, `:156`), `/health` (`:158-167`), `/auth/sign-in` and `/auth/sign-out` (`registerSignInRoutes`, `:169`; `src/access/access-routes.ts:57-114`), `/robots.txt` and `/sitemap.xml` (`:214-227`), and, when there is a UI directory, `/` and one route per UI file (`:229-256`);
- a scope with prefix `/v1` and an `onRequest` hook that authenticates a key (`:171-182`);
- a scope with prefix `/app` and an `onRequest` hook that loads the session's User and refuses `401` without one (`:184-211`).

The hooks are scope hooks, so they run for every route registered inside the scope, whatever URL reached it; they don't match paths. The probe reads the routes from Fastify's router (`printRoutes({ method })` for each method, parsed by `b1-routes.ts`; `HEAD` routes are Fastify's automatic ones for each `GET`), then finds each route's hook by asking it: refused `401` with no credential, then let in by a key and not by a session (key hook), or the other way round (session hook). Each request carries an id no fixture has and, where a body is taken, a JSON array, so a request that gets past a hook meets a `404` or `422` and changes nothing.

**102 routes**: 25 under `/v1`, every one in the key hook; 49 under `/app`, every one in the session hook; 28 under neither. The 28, and why each has no hook:

| Route(s)                                                                                                                                               | Why it has no hook                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`/`HEAD /`, and `GET`/`HEAD` on each UI file                                                                                                       | The UI: static HTML, JS and CSS that hold no data, and sign in through `/auth`. In production these are `dist/ui`'s files, served with `wildcard: false` (`:239-243`), one route each. |
| `GET`/`HEAD /health`                                                                                                                                   | Compose's health check (`docker-compose.yml`). It says `{"status":"ok","database":"ok"}` or `503` with `"unreachable"`: whether the database answers, nothing more.                    |
| `POST /auth/sign-in`                                                                                                                                   | How a session is made. Its own throttle is A1's.                                                                                                                                       |
| `POST /auth/sign-out`                                                                                                                                  | Deletes the session its cookie names, if any, and clears the cookie; with no cookie it does nothing.                                                                                   |
| `GET`/`HEAD /robots.txt`, `GET`/`HEAD /sitemap.xml`                                                                                                    | Public crawler files; they give away only `APP_URL`, which is public anyway.                                                                                                           |
| `GET`/`HEAD` on `/docs`, `/docs/`, `/docs/json`, `/docs/yaml`, `/docs/static/index.html`, `/docs/static/swagger-initializer.js`, `/docs/static/*` (14) | **No reason found.** See probe 4.                                                                                                                                                      |

## Every route as every identity (probe 2)

Nine identities, every one of the 102 routes, 918 calls. Expected: a `/v1` route lets in (answers anything but `401`) only `wizzaroo` and `secondApp`; an `/app` route only `victim` and `colleague`; a route under neither answers every identity with the same status as no credential.

- No call broke that. In particular: the `deleted` key, an expired session (a `sessions` row for `victim` whose `expires_at` had passed), the `wizzaroo` key sent as `Cookie: session=…`, and a live `victim` session sent as `Authorization: Bearer …` were each refused on every `/v1` and `/app` route, and a live session got nothing from `/v1`, nor a live key from `/app`.
- No call answered `5xx`.
- Every `401` body was one of three: `{"error":"unauthenticated","message":"Send an API key as a Bearer token in the Authorization header"}` (no or malformed `Authorization`), `…"The API key is not valid"` (a token that looks like a key but isn't one), and `…"Sign in first"` (no live session).
- `/auth/sign-out` went last, because it ends the session it is sent.

## Path tricks (probe 3)

Sent over a real socket with no credential, as `GET`, `HEAD` and `POST` (with `[]`), to the API built with a UI directory. Outcomes, as the probe pins them:

| Path                                                                                                                                                                                                         | `GET`              | `HEAD` | `POST`                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------ | ------ | --------------------- |
| `/v1X/templates`, `/v1X`, `//v1/templates`, `//app/settings`, `/v1%2Ftemplates`, `/app%2Fsettings`, `/v1./templates`, `/app./settings`, `/V1/templates`, `/APP/settings`, `/v1;/templates`, `/app;/settings` | the UI's page      | `404`  | `404`                 |
| `/app/../v1/templates`, `/v1/../app/settings`, `/app/%2e%2e/v1/templates`                                                                                                                                    | `404`              | `404`  | `404`                 |
| `/v1/templates%2F`, `/v1/templates.`, `/app/settings.`, `/app/settings/`                                                                                                                                     | `404`              | `404`  | `404`                 |
| `/%761/templates` (an encoded `v`)                                                                                                                                                                           | key hook `401`     | `401`  | key hook `401`        |
| `/%61pp/settings` (an encoded `a`)                                                                                                                                                                           | session hook `401` | `401`  | `404` (no such route) |
| `/v1/templates/` (trailing slash; matches `/v1/templates/:id` with an empty id)                                                                                                                              | key hook `401`     | `401`  | `404`                 |
| `/v1/templates?x=/app`, `/v1/templates#`                                                                                                                                                                     | key hook `401`     | `401`  | key hook `401`        |

- Fastify does not resolve `..` or decode `%2F`, so neither crosses from one scope to the other; it does decode an encoded letter, and then the route's own hook runs. No URL reached a `/v1` or `/app` handler without its hook, because the hooks belong to the routes, not to a path.
- The SPA fallback (`:247-255`) is the one thing here that matches by path: it serves the UI's page to any unknown `GET` whose path does not match `^\/(v1|app|auth|docs)(\/|$)`. So `/v1X`, `//v1/…`, `/V1/…` and the like get the page (`200`, the same `index.html` as `/`). That serves no data and no route, so it is not a finding; under `/v1`, `/app`, `/auth` and `/docs` an unknown path gets `404 {"error":"not_found"}`, never the page (3b). `HEAD` gets `404` from the fallback, and `401` (no body) from each hook, like `GET`.
- 3c: `GET /v1/templates`, `POST /v1/messages`, `GET /app/settings` and `PUT /app/settings`, each with every header in the probe's name set to a value that would point at `/health` or a trusted origin, all answered `401`. Nothing in `src/` reads `request.hostname` or `request.protocol`; `trustProxy` (`:91`) matters only for `request.ip`, which is A1's.

## `/docs` with no credential (probe 4)

`@fastify/swagger` builds an OpenAPI 3.1 document from every route not marked `hide` (`:138-155`), and `@fastify/swagger-ui` serves it at `/docs` in the root scope (`:156`), outside both hooks. The `/app` scope marks all its routes `hide` (`:186-188`), and the root's own routes are marked `hide` one by one.

- `GET /docs/`: `200`, Swagger UI's page, 873 bytes. `GET /docs/json`: `200`, 11,336 bytes. `GET /docs/yaml`: `200`, 17,845 bytes. No credential.
- What they give away: `info` `{"title":"Email API","version":"2.0.0","description":"Send emails from your templates or raw content. Authenticate with an API key as a Bearer token."}`; `servers` `[{"url": <APP_URL's origin>}]`; and nine paths, `/v1/messages`, `/v1/messages/{id}`, `/v1/templates`, `/v1/templates/{id}`, `/v1/templates/preview`, `/v1/headers`, `/v1/headers/{id}`, `/v1/footers`, `/v1/footers/{id}`, each with its methods, request schemas, limits (50 recipients a field, 998-character subject, 100-character slug, and so on) and descriptions. That tells an unauthenticated caller exactly what a leaked key can do (K1's chain: replace a Template or a Header), and which version is running.
- What they don't: no `/app`, `/auth` or `/health` route, no fixture address, no `wizzaroo` and no key (passing test). Good.
- `docs/guide/sending.md` says "The full reference is at `/docs` on a running app", so its existence is documented; no ADR or guide says it should be readable without a key or a session. So this is confirmed, not a documented decision. It is low: nothing in it is a secret, and Wizzaroo's own client already knows the API. The fix is a choice for the owner: put `/docs` behind the session hook (Users read it in the UI) or behind either credential, or record that it is public on purpose and add it to the allow-list below.

## The guard test (probe 5)

Nothing in the suite stops a future route being registered in the root scope, outside both hooks. `grep` for `printRoutes`, `onRoute` or `hasRoute` in `src/` finds only the `/app` scope's `hide` hook (`:186-188`) and these probes. The `today_` test shows what that means: a server from `buildHttpServer` with one more route added beside the hooks (`GET /export`) builds, starts and answers `200` with its data to no credential, and only the enumeration in these probes notices it.

The `it.fails` beside it is the proposed guard: enumerate every route, find each one's hook, and fail on any route under neither that is not on a reviewed allow-list. With the allow-list as reviewed here (`/`, the UI's files, `/health`, `/auth/sign-in`, `/auth/sign-out`, `/robots.txt`, `/sitemap.xml`) it fails today on the 14 `/docs` routes, so it can't pass until probe 4's finding is answered one way or the other. The proposed fix moves it to `src/api/` beside `http-server.ts`, where it runs in every `pnpm test`, not only in the gated run. Two ways to write it, both proven here:

- read each method's router tree with `server.printRoutes({ method })` after `ready()` (what `b1-routes.ts` does), or add an `onRoute` hook in `buildHttpServer` itself that records each route's scope; and
- find the hook by behaviour (no credential `401`, then a key or a session lets it in) rather than by URL prefix, so a route that sits under `/v1` by path but outside the scope is caught too.

## Checks every scope issue carries

Applied:

- **Refusals give nothing away.** With no credential, `GET` on a Message, a Template and a Header that exist and on an id that doesn't, under both `/v1` and `/app`: the same `401`, body and `content-length`, because the hook answers before any lookup. Held.
- **Every refusal comes from a closed set.** 918 calls: no `5xx`, and every `401` one of three fixed bodies. Held for the hooks; `4xx` messages from Fastify and Handlebars are I1's.
- **Internal headers are trusted only when the server set them.** Rewrite and forwarding headers against both hooks (3c). Held; `X-Forwarded-For` on sign-in is A1's.
- **Middleware that matches by path matches by segment.** `/v1X`, `//v1`, `/app/../v1`, encoded slashes, encoded letters, trailing dots, trailing slashes, `;`, case and `HEAD`, over a real socket, against both hooks and the SPA fallback (probe 3). Held: the hooks are by scope, and the fallback's path match only ever serves the page.
- **Run the probes against a real Postgres.** Every probe here does.
- **A test that passes either way proves nothing.** Both `it.fails` here were run as plain `it` and fail on their property assertions (14 `/docs` routes off the allow-list; `[200, 200, 200]` where `401`s should be). The trick outcomes are pinned exactly, so a router or fallback change shows up.

Not applied, and why:

- **Odd input stops above the database** and **An idempotency key is bound to its payload and its owner**: S1's and S2's; B1 sends no payload past a hook.
- **Nothing is left to a collaborator to bound**, **A secret is sealed or hashed**, **Logs are a copy of the data**, **Configuration fails closed**: not route placement; K1, D2 and I-scope issues own them.

## Since the probe

#148 is fixed in the fourth round (fixed, unverified). `/docs`, `/docs/`, `/docs/json`, `/docs/yaml` and the page's static files sit in a scope of their own in `src/api/http-server.ts` whose `onRequest` hook lets in a signed-in User (the session cookie, which the browser sends same-origin) or a live API Key (the key hook's own check, so a dead key gets `The API key is not valid`), and refuses anyone else with `401` (`Sign in, or send an API key as a Bearer token in the Authorization header`). The UI has no link to `/docs`; [Sending](../../guide/sending.md) says who may read it. In `src/pen-test/probes/b1.test.ts` its `today_` test is now `(regression) /docs, /docs/json, /docs/yaml and the page's files refuse a caller with no credential, or a dead one, with 401, and serve every /v1 route to a signed-in User or a key holder (#148)`, and `the API document is refused to a caller with no credential` is a plain `it`. Probe 1 knows a third hook, `either`, for `/docs`, and probe 2 checks every identity against it. I1's probes now ask for `/docs` with a credential, and its closed set of refusals has the new `401`.

#149 is fixed in the fourth round (fixed, unverified). `src/api/route-guard.test.ts`, in every `pnpm test` and with no container, builds the server with a UI directory, lists every route from Fastify's router (`src/api/route-list.ts`, moved there from `b1-routes.ts`, which re-exports it), asks each with no credential, and fails on any that doesn't answer `401` and isn't on its reviewed allow-list: `/`, the UI's files, `/health`, `/auth/sign-in`, `/auth/sign-out`, `/robots.txt` and `/sitemap.xml`. `/docs` is not on it (#148). A second test adds `GET /export` beside the hooks and checks the guard names it. In `b1.test.ts` the `today_` test is now `(regression) the routes outside every hook are the allow-list's alone, /docs no longer among them, and src/api/route-guard.test.ts fails on a route added outside them, as this one is (#149, #148)`, and `every route outside both hooks is on the reviewed allow-list` is a plain `it`.

The route guard has a second half in `src/integration.test.ts`, which runs in every `pnpm test` with Docker: `lets every guarded route's caller in by its hook: a key on /v1, a session on /app, either on /docs (#149)` asks every route outside the allow-list as no one (`401`), with an API Key and with a session, and fails unless each `/v1` route lets the key in, each `/app` route the session, and each `/docs` route both. The allow-list lives in `src/api/route-list.ts`, shared by both tests.
