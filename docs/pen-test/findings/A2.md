# A2: User management

The findings note for scope issue #93 (A2) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H5: what one User can do to another, and what one stolen session can make that outlives the victim changing their password. It names exploit chains, so **keep it private on the same terms as the PRD**. Probed at commit `d81eaa9`. The probes are `src/pen-test/probes/a2.test.ts`: the ADR 0005 check runs without a container; the rest run in the gated run against a real Postgres and Mailpit from [the probe world](../../../src/pen-test/probes/probe-world.ts). Before each probe the fixtures are loaded again and any User or API Key a probe made is removed. No credential appears here; Users and keys are named by fixture handle (`victim`, `colleague`, `wizzaroo`).

## The takeover chain (probe 1)

The probe signs `victim` in twice: one session stands for the stolen cookie, the other for the victim's own browser. With the stolen one it sends:

| Request                                                     | Answer | What it leaves                                                                     |
| ----------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------- |
| `POST /app/users` with an attacker's email and own password | `201`  | A User the attacker signs in as                                                    |
| `POST /app/api-keys` named "Backups"                        | `201`  | An `ek_…` key, shown once, to the attacker                                         |
| `DELETE /app/users/<colleague id>`                          | `200`  | The colleague, and every session of theirs, gone                                   |
| `PUT /app/settings` with `logRetentionDays: 3650`           | `200`  | Every Message, Wizzaroo's links included, kept ten years (D2 owns what that keeps) |

None of these asks for the current password or anything else the cookie doesn't carry (`src/access/access-routes.ts:143-192`, `src/settings/settings-routes.ts:32-58`). Then the victim changes their password from their own session (`200`). Afterwards:

- the stolen session still answers `GET /app/me` as `victim` (A1, #124);
- the attacker's User signs in (`200`) with the attacker's password;
- the minted key reads `GET /v1/templates` (`200`), and with it every power K1 lists, rewriting `wizzaroo-reset-your-password` included;
- the colleague's sign-in is refused (`401`): their account is gone, and nothing restores it;
- Retention reads 3650.

So one stolen cookie, used once, makes access that no action of the victim's ends except finding and deleting the added User and key by hand, and nothing (probe 2) tells them to look. Changing the password ends neither, and would not even if A1's finding were fixed: the attacker's User and key are credentials of their own. The fix belongs to the creating requests: ask for the current password again before adding a User, minting a key or deleting a User (step-up), and record and announce them (probe 2).

## Who made what, and who is told (probe 2)

- `users` has `id, email, password_hash, created_at`; `api_keys` has `id, name, lookup_id, secret_hash, last_used_at, created_at` (`src/lib/schema.ts:27-54`). Neither says which User made the row. There is no audit, event or activity table in the schema. `created_at` says when, not who; `GET /app/users` and `GET /app/api-keys` show the row with nothing tying it to a User.
- After a User and a key are added, no Message is queued to `colleague` and Mailpit holds nothing: nobody is told. Deleting a User is equally silent, to the deleted User as well.

## Which emails have accounts (probe 3)

`createUser` answers `422` "A user with the email `<normalised email>` exists" for an email that has an account (`src/access/users.ts:57-63`), and `201` otherwise. Sent with `colleague`'s email in capitals, the answer names it normalised. But the route sits behind the `/app` session hook (`src/api/http-server.ts:184-211`), and the same User can read every User's email at `GET /app/users` (`access-routes.ts:143`), so it tells a User nothing they can't already list. Without a session, and with an API Key, `POST /app/users` answers the same `401` body for an email with an account and one without: the hook runs before the body is read. Sign-in's refusals are A1's (refuted there). No other route takes an email of a User. Refuted as a disclosure; nothing filed.

## Deleting oneself, and the last User (probe 4)

- `DELETE /app/users/<own id>` answers `409` `cannot_delete_self` (`users.ts:84-90`).
- The check compares the id from the path with the session's id as strings. The path's id is validated as `format: "uuid"` (`access-routes.ts:55`), which accepts upper case, and Postgres compares `uuid`s by value. So `DELETE /app/users/<own id in upper case>` answers `200` and deletes the User, their sessions with them. After deleting the colleague first, the victim deletes themselves this way and **the `users` table is empty**. The guide says "You can't remove yourself" (`docs/guide/delivery-and-access.md`, Access).
- With no User: every sign-in is refused `401`; API Keys keep working (`GET /v1/templates` with `wizzaroo`, `200`), and nobody can see or delete them in the UI. The CLI has no command to delete a User (`src/access/cli.ts:22-28`; `user:delete` answers with the usage text), and `pnpm cli user:create` makes a User again, so an operator with a shell gets back in. Deleting the last User from the database is an operator action with a recovery, so it isn't filed; through the app it is 4a's finding.

## ADR 0005: every User has full rights (probe 5)

[ADR 0005](../../architectural-decision-record/0005-templates-and-sending-only.md) says "Every user has full rights." and records no review date, expiry or condition for it to stop being true. The probe confirms the decision is what the code does: `colleague` changes Retention to 1 day, mints a key, deletes `wizzaroo`'s key and deletes `victim`, each answered `200` or `201`. The PRD's Findings workflow makes a documented decision with no recorded expiry a low finding. It matters more than its label: with probes 1 and 2, any one User's session is every User's power, permanently. The natural end is Wizzaroo's second School, or a second Application getting a key (the PRD's problem statement).

## Checks every scope issue carries

Applied:

- **Refusals give nothing away:** probe 3. Holds for callers without a session.
- **Every refusal comes from a closed set:** `POST /app/users` with `nul\u0000@users.pen-test.invalid` answers `500`, because the email passes the address pattern (`users.ts:53`; `\s` doesn't match NUL) and Postgres refuses the byte. Same cause as A1's sign-in case; filed once, as A1's #144. By reading, not probed: `DELETE /app/users/<unknown uuid>` answers `404` and a non-uuid `422` (`access-routes.ts:156-170`).
- **Odd input stops above the database:** NUL (above); a 100,000-character email is accepted and stored (`201`), as is any password length (A1, probe 4). No `maxLength` on either field (`access-routes.ts:50-53`). Upper-case uuids: probe 4a.
- **Nothing is left to a collaborator to bound:** the number of Users and API Keys has no limit; the email's length is left to Postgres (a less compressible long email fails the unique index with a `500`, by arithmetic: btree rows are capped near 2.7 kB). Part of #144.
- **A secret is sealed or hashed where it is kept:** a new User's password is salted scrypt; a minted key is shown once and kept as SHA-256 (K1 owns the key's storage).
- **Run the probes against a real Postgres:** every probe but the ADR text check.
- **A test that passes either way proves nothing:** every `it.fails` was run as a plain `it` and failed on its property assertion (for example `expected 200 to be 409`).

Not applied, and why:

- **An idempotency key is bound to its payload and owner:** these routes take none.
- **Logs are a copy of the data:** D2's.
- **Internal headers are trusted only when the server set them:** these routes read only the session cookie; `X-Forwarded-For` is A1's.
- **Middleware that matches by path matches by segment:** B1's.
- **Configuration fails closed:** I3's.

## Since the probe

#115 is fixed in the second round's pull request (fixed, unverified). Adding a User, minting an API Key and deleting a User ask for the current password (`currentPassword`), and wrong tries are throttled per User. Changing a password ends the stolen session (#124). Its `today_` test is now its `(regression)` test, and its `it.fails` is a plain `it`, in `src/pen-test/probes/a2.test.ts`. Retention can still be changed by a stolen session.

#125 is fixed in the third round (fixed, unverified). Each User and API Key records the User who made it in `created_by_user_id` (migration `0008_record_who_made_and_changed`). It is a bare ID with no foreign key, so the record outlives the creator being deleted; it is null for rows older than the migration and for ones the CLI makes, since the CLI runs as an operator with no User. `/app/users` and `/app/api-keys` return `createdByUserId` and `createdByEmail`, and the Users and API keys pages show them as **Added by** and **Created by**. Adding a User, minting an API Key and deleting a User now email every other User (not the one who acted, nor the User just added), one Message each, queued through the normal send path (`src/access/user-notices.ts`, `acceptMessage` with no sender). The notices have no Application and no key: they show in the Logs to Users, as a test send does, and no API Key can read them. They are sent from the default from address; with none set, no notice is queued and the change still stands, with `access.user-notice.not-queued` logged, so a missing setting can't lock an operator out. Turned in `src/pen-test/probes/a2.test.ts`: `records which User made each User and API Key` and `tells the other Users when a User is added or an API Key minted` are plain `it`s; their `today_` tests are now `(regression) records which User made a User or an API Key, shows it in /app, and records none for the CLI's (#125)` and `(regression) emails the other Users, and not the one who acted, when a User is added or deleted or an API Key minted; the notices have no Application (#125)`, which delivers the notices to Mailpit. `src/integration.test.ts` checks a User is still added with no default from address.

#144 is fixed in the fourth round (fixed, unverified): `POST /app/users` refuses an email longer than 254 characters (RFC 5321's 256-octet path less its angle brackets, `maxEmailLength` in `src/access/access-routes.ts`) with `422`, and a NUL byte with `422` from the root body hook (S1's note, #151), both before the database. The two `today_` tests are now one, `(regression) refuses adding a User whose email holds a NUL byte, or is 100,000 characters long, with 422 naming the email, and stores neither (#144)`, and `refuses adding a User whose email holds a NUL byte or runs past 254 characters, with 422` is a plain `it`. Since I1's #172 gave `/app` routes a 16 KiB body limit, a 100,000-character email is refused with `413` before it is read, so both tests now use 10,000 characters to reach the 254-character check; the first is `(regression) refuses adding a User whose email holds a NUL byte, or is 10,000 characters long (a longer one is past the 16 KiB body limit, #172)…`.

#145 is fixed in the fourth round (fixed, unverified): `deleteUser` compares the id in the path with the signed-in User's in lower case, as Postgres reads a uuid in any case, so a User's own id in upper case is refused with `409 cannot_delete_self` and the last User can't be deleted that way. Its `today_` test is now `(regression) refuses a User deleting themselves by their id in upper case with 409 cannot_delete_self, so the last User stays (#145)`, and `refuses a User deleting themselves whatever the case of their id` is a plain `it`. `src/integration.test.ts` checks the upper-case id too.

#146 is fixed in the fourth round (fixed, unverified): [ADR 0011](../../architectural-decision-record/0011-every-user-has-full-rights-until-the-second-school.md) records that "every User has full rights" stops being true before Wizzaroo adds a second School or another Application is given an API Key (ADR 0008's gate), when the owner decides User rights in a new ADR, and that it is reviewed on 2027-05-21 or at the external round, whichever is sooner. ADR 0005 says so beside the decision and links it. Its `today_` test is now `(regression) still decides that every User has full rights, and names when that ends, before a second School or a second Application's API Key, and a review date (#146)`, and `records when ADR 0005's "every User has full rights" has to stop being true` is a plain `it`. `today_ lets any User change Settings, mint an API Key, delete an API Key and delete another User, as ADR 0005 decides` stays: it is what ADR 0011 decides, until its end.
