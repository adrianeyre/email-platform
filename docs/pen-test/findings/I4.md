The findings note for scope issue #106 (I4) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H9 (the published port half) and H14 (the container and image half). It names files, lines and exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `2f11db2`, and the [E1 deployment](../deployment.md) by its project name `email-platform-pen-test`. No credential, key or seed appears here.
- **The probes** are `src/pen-test/probes/i4.test.ts`, in the gated run. They are static facts of production's own `docker-compose.yml`, `Dockerfile` and `backup/Dockerfile`, read with `docker compose config` (placeholder values, `--env-file /dev/null`, so no real secret is loaded) and from the Dockerfiles directly, as D1's Compose probes are. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now; a refuted probe is a plain passing test.
- **The live observations** below — which host interfaces answer on the published port, whether a host firewall's `INPUT` rules stop it, each container's user, capabilities, read-only root, `no-new-privileges` and limits, the networks each container reaches, and the log driver's bound — were taken on the E1 deployment on 21 November 2026 with `docker inspect`, `docker top`, `docker exec`, a port probe and a throwaway Docker-in-Docker, because they are runtime facts, not host-independent, and the gated probes do not assert them.
- **This host is macOS with Docker Desktop.** Docker Desktop's userland networking (gVisor/vpnkit) differs from the Linux home server the ADR describes, so where it matters this note says which host the observation is from and reasons about the Linux server from the Compose file, as [the deployment page](../deployment.md#the-one-network-with-a-way-out) does.
- **Left to other scope issues / cited:** the five containers holding `POSTGRES_PASSWORD` on a network with a way out, and `migrate` needing none, are D1's (#139); the api container log keeping personal data with no `logging:` bound is D2's (#126). This note cites both rather than refiling them.

## Probe 1: the published port and the interfaces it answers on

`docker-compose.yml:58-59` publishes `api` as `4320:4320`. `docker compose config` shows the published port with no `host_ip`, which Docker binds to `0.0.0.0` and `::`: every interface routed to the host, the LAN and the tailnet both. [ADR 0003](../../architectural-decision-record/0003-self-hosted-on-a-home-server-with-docker-compose.md) says "the UI and API are reached over the home network or tailnet … No router ports are opened", but the binding itself is to everything, not to those two.

Live, on Docker Desktop, a stand-in container published as `4320:4320` answered `GET /health` with `200` on `127.0.0.1`, on both LAN addresses (`192.168.1.60`, `192.168.1.61`) and on `[::1]`. The macOS application firewall is enabled with stealth mode on, yet the LAN addresses answered: Docker Desktop's userland proxy carries the traffic in ahead of the host packet filter. (The E1 deployment, which publishes `127.0.0.1:43320` instead, answered only on `127.0.0.1`; `192.168.1.60:43320` and `[::1]:43320` timed out — so the narrow binding the deployment uses is exactly what production lacks.)

**Whether a host firewall's `INPUT` rules stop it.** On the Linux home server a published port is DNAT'd in the `nat` table's `PREROUTING`/`DOCKER` chains and forwarded through `FORWARD`/`DOCKER-FORWARD`, not delivered through `INPUT`. Reproduced in a throwaway Docker-in-Docker: with a service published on `4320`, an `iptables -I INPUT -p tcp --dport 4320 -j DROP` rule did **not** stop a connection from another host (it still got the banner); the rule that stopped it was in `DOCKER-USER` (and `FORWARD`), the Docker-managed chains. So an operator who firewalls the server with the obvious `INPUT`/`ufw` rule, believing ADR 0003's "no router ports are opened" extends to the LAN, still serves 4320 to every device on it. Confirmed; filed as **A** (#181).

## Probe 2: container hardening

`docker compose config` shows that no service sets `cap_drop`, `read_only`, `security_opt` (so no `no-new-privileges`), `mem_limit` or `pids_limit`. Live, `docker inspect` and `/proc/1/status` on the deployment:

| Container       | PID 1 runs as                           | `NoNewPrivs` | Read-only root | `CapBnd` (bounding set)     | Limits |
| --------------- | --------------------------------------- | ------------ | -------------- | --------------------------- | ------ |
| `api`, `worker` | `node` (uid 1000)                       | 0            | no             | `a80425fb` (Docker default) | none   |
| `migrate`       | `node` (uid 1000)                       | 0            | no             | `a80425fb`                  | none   |
| `backup`        | `postgres` (70)                         | 0            | no             | `a80425fb`                  | none   |
| `postgres`      | server as 70; entrypoint/`exec` as root | 0            | no             | `a80425fb`                  | none   |
| `mailpit`       | **root**                                | 0            | no             | `a80425fb` (`CapEff` full)  | none   |
| `entry` (nginx) | **root**                                | 0            | no             | `a80425fb` (`CapEff` full)  | none   |

The app and backup images do set a non-root `USER` in their Dockerfile (`Dockerfile:16` `USER node`, `backup/Dockerfile:4` `USER postgres`), which is why `api`, `worker` and `backup` run unprivileged — that half is **refuted**, and pinned by a passing test. But nothing is dropped or sealed on top: every container keeps Docker's default capability set in its bounding set, so `no-new-privileges` being 0 means a setuid binary inside any of them can regain privilege, and `mailpit` and `entry` run their main process as root with `CHOWN`, `DAC_OVERRIDE`, `SETUID`, `SETGID`, `NET_RAW` and the rest of the default set live. No container is read-only, and none bounds memory, CPU or PIDs, so one compromised or runaway container can exhaust the host (ADR 0003's single home server). Confirmed; filed as **B** (#182).

## Probe 3: images and packages by tag, not digest

Every image is named by a mutable tag, none by `@sha256:` digest: `email-platform:local` (`docker-compose.yml:24`, built from `Dockerfile`), `postgres:18-alpine` (`docker-compose.yml`, `backup/Dockerfile:1`), and the Dockerfile base `node:26-slim` (`Dockerfile:1,10`). `backup/Dockerfile:2` is `apk add --no-cache age rclone` with no `=<version>`, so the two tools that encrypt and ship every backup are whatever the Alpine repository serves at build time. A tag or an unversioned package can be repointed upstream between builds, so what runs on the home server is not fixed by this checkout. (The pen-test override and the two third-party images it adds, `mailpit` and `nginx`, _are_ digest-pinned in `docker-compose.pen-test.yml`, which shows the shape the production file is missing.) Confirmed; filed as **C** (#183), low. The CI side of H14 — actions pinned by tag, the deploy script — is I6's (#108); this note owns only the images and packages the Compose file and Dockerfiles name.

## Probe 4: the container log driver's bound

`docker compose config` shows no `logging:` on any service, so each container's log is whatever the host Docker daemon defaults to. On this host the daemon default is `local` (about 100 MB per container, rotated), so the deployment's logs happen to be bounded — but that is the host's default, not anything the repository pins. A home server left on Docker's historical `json-file` default has no size or file limit at all, so the api container log (which D2 #126 shows holds searched addresses and failed-query parameters) grows until the disk fills. The bound is left to the host; the Compose file sets none. Confirmed, and already filed on its content side as **D2 #126** ("no `logging:` bound"); cited here rather than refiled.

## Probe 5: which networks have a way out

`docker compose config`: `default` is not internal, `database` is; `api`, `worker`, `backup`, `migrate` and `restore` all sit on `default`, `postgres` only on `database`. In production `default` reaches the LAN, the tailnet and the internet (`docker-compose.yml` has no `internal: true` on it), so any of those five containers has a way out. Live on the E1 deployment (where the override makes `default` internal, so this is the inverse of production): `api`, `worker` and `backup` reached `postgres`, `api`, `mailpit` and `entry` but not `1.1.1.1` or the LAN (`ENETUNREACH`); only `entry`, on the one non-internal network, reached `1.1.1.1` — the single way out the deployment is built to have. That confirms, by its opposite, that in production the five on a non-internal `default` do have a way out. This is **D1 #139** ("five of the six containers … sit on a network with a way out, migrate included"); cited, not refiled.

## Checks every scope issue carries

Applied:

- **Configuration fails closed.** The published port fails _open_ to every interface (probe 1); container hardening is absent, so a compromise keeps every default capability (probe 2); the log bound is left to the host (probe 4). None of these fails closed.
- **A secret is sealed where it is kept.** The images that run as root (`mailpit`, `entry`) and the unpinned `age`/`rclone` (probe 3) widen what a supply-chain or container compromise reaches; the backups those tools make hold Wizzaroo's links (H2, D3).
- **Nothing is left to a collaborator to bound.** The log size and the capability set are left to the host daemon and the base images rather than pinned in the repository (probes 2-4).
- **Run the probes against a real Postgres.** The Compose probes read production's own `docker-compose.yml` with `docker compose config`; the live observations were taken on the E1 deployment, which runs production's images.
- **A test that passes either way proves nothing.** Every `it.fails` was run once as a plain `it` and failed on its property assertion (the port has no `host_ip`; no `cap_drop`/`read_only`/`security_opt`; images are tags not digests; the log has no `max-size`; `migrate` has a way out), never on setup.

Not applied: **refusals give nothing away**, **every refusal comes from a closed set**, **odd input**, **idempotency keys**, **logs are a copy of the data** (D2's), **internal headers** and **path-matching middleware**: this surface is Compose, images and the network, not an HTTP route.

## Since the probe

Probe 4's bound is fixed with D2 #126 in the third round (fixed, unverified): `docker-compose.yml` pins every service to the `json-file` driver with three 10 MB files (`x-logging`), so the bound no longer depends on the host daemon's default. In `src/pen-test/probes/i4.test.ts` probe 4's `it.fails` is a plain `it`, and its `today_` test is `(regression) every long-running service pins the json-file driver to three 10 MB files, whatever the host's default (#126)`.

#181, #182 and #183 are fixed in the sixth pull request (fixed, unverified). Their `today_` tests are now `(regression)` tests and their `it.fails` plain `it`s in `src/pen-test/probes/i4.test.ts`; three `today_` tests, which pinned the gap itself, are rewritten to assert the fix, as noted in the file.

- **#181, the published port.** Fixed, unverified (21 November 2026, sixth pull request). `api` publishes `${API_BIND_ADDRESS:-127.0.0.1}:4320:4320`: one host address, loopback unless `.env` names the server's LAN or tailnet address, never every interface. Loopback is the default because it fails closed: an install that hasn't set it serves the server alone, not the LAN. `docs/operations/deploying.md` ("The published port") says how to choose the address, that a published port skips `INPUT` so `ufw` can't close it, and gives a `DOCKER-USER` rule that can; ADR 0003 records the binding, and `.env.example` and the environment-variables reference carry the variable. The app itself never reads it, so `src/config/` has no check to add. An existing install must set `API_BIND_ADDRESS` (and `DEPLOY_HEALTH_URL`, as the deploy script's health check asks `127.0.0.1`) or its UI goes dark to every other device. Checked live with a throwaway project on Docker Desktop: unset, `docker port` showed `127.0.0.1:4320`, `/health` answered on `127.0.0.1` and not on the LAN address; with `API_BIND_ADDRESS` set to the LAN address it answered there and not on `127.0.0.1`.
- **#182, container hardening.** Fixed, unverified (21 November 2026, sixth pull request). Every service in `docker-compose.yml`, one-shot ones included, sets `cap_drop: [ALL]` with no `cap_add`, `no-new-privileges:true`, `read_only: true`, `mem_limit` and `pids_limit` (an `x-hardening` anchor, and `x-app` for the four app containers). `postgres` now runs as `user: postgres`, so its entrypoint needs no capability (it neither chowns nor drops privilege), with `/var/run/postgresql` and `/tmp` as tmpfs; the app containers get a `/tmp` tmpfs; `backup` and `restore` write the dump to an anonymous `/tmp` volume on disk and the health state to `/var/lib/postgresql`, as before. In the pen-test override `mailpit` runs as `65534` and `entry` (nginx) as `101`, both read-only with no capability; `entry`'s configuration moved from an inline Compose config, which Compose can't write into a read-only container, to `src/pen-test/deployment/entry-nginx.conf`, unchanged but for a `/tmp` pid file. `backup-stand-in-folder` keeps root and `CHOWN` only. Checked live with throwaway `.env`s: the production stack came up healthy (`up -d --wait`), `/health` answered 200, and in `api`, `worker`, `postgres` and `backup` `/proc/1/status` showed `CapEff` and `CapBnd` `0000000000000000`, `NoNewPrivs 1`, a non-root uid, and `touch /x` refused as a read-only file system; `backup.sh` made and uploaded an encrypted backup, `backup-health.sh` was healthy, and `restore.sh` restored it into a provisioned `restore_check` database. The production files with the pen-test override also came up healthy, with `entry` passing `/health` and Mailpit's UI through on `127.0.0.1:43320` and `:43325`.
- **#183, digests and package versions.** Fixed, unverified (21 November 2026, sixth pull request). `postgres:18-alpine` (`docker-compose.yml`, `backup/Dockerfile`, `docker-compose.dev.yml`) is pinned to `sha256:ff64c9e3…876738ff`, `node:26-slim` (both stages of `Dockerfile`) to `sha256:e6bedef2…b8820bc`, and the development stack's `mailpit` to the digest the override already used; each is the multi-architecture index digest from `docker buildx imagetools inspect`. `backup/Dockerfile` installs `age=1.3.2-r1 rclone=1.75.2-r0`, the versions `apk policy` gave on that pinned Alpine 3.24 base. `email-platform:local` and the backup image are never pulled: Compose builds them from those Dockerfiles, so the probe checks their `FROM` lines rather than the tag. `docs/operations/deploying.md` ("Updating an image") says how to bump a digest and the package versions together. Nothing proposes the bumps yet; Dependabot's `docker` ecosystem could, for digests. The tests' own Testcontainers images are still named by tag.
