# I1: HTTP hardening, the cookie and the error handler

The findings note for scope issue #102 (I1) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H9's header, cookie and body-limit bullets and H16's error-handler, Handlebars and SMTP-text bullets. H9's published-port bullet is I4's (#106), and H16's `/docs` bullet was B1's (#148) and its client `http:` bullet is I6's (#108). It names exploit chains, so keep it private on the same terms as the PRD.

- **Read against:** commit `2f11db2`, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are the tests under `pen test I1 (#102): HTTP hardening, the cookie and the error handler` in `src/pen-test/probes/i1.test.ts`, with the second origin, the browser and a refusing SMTP server in `src/pen-test/probes/i1-origins.ts`. They run in the gated run against a real Postgres (`startProbeWorld`). The API is built as production builds it, with a stand-in UI directory: one `index.html` that, like the real UI, is served for `/users` and `/api-keys` by the SPA fallback and reads `/app/me`, `/app/users` and `/app/api-keys` with the session cookie, writing what it got into the page. It listens on a real socket at `localhost`. The framing and cookie probes drive Chrome (playwright-core, a dev dependency; `CHROME_PATH` overrides) against it and against a second origin: a plain Node server on another port of the same machine, reached as `localhost:<port>` (the same site, as another service on `email.home` would be) and as `127.0.0.1:<port>` (another site, as another LAN host would be). Without Chrome those probes skip, saying so. Everything else runs with `inject`.
- A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a passing test.

## Probe 1: headers and framing

Twelve requests, one on each surface: `/`, `/users` and `/api-keys` (the UI), `/v1/templates` as `wizzaroo`, `/app/users` and `/app/api-keys` as `victim`, `/auth/sign-in` and `/auth/sign-out`, `/docs/`, `/docs/json`, `/docs/static/swagger-ui.css` and `/health`, on a server built with `APP_URL` on `http:` and again on `https:`. Besides `date` and `connection`, the only headers are `content-type`, `content-length`, `cache-control` (the UI's page and static files), `set-cookie` (`/auth`), and `etag`, `last-modified` and `accept-ranges` (static files). None carries `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, `Cross-Origin-Resource-Policy` or `Permissions-Policy`, and `https:` adds no `Strict-Transport-Security`. Nothing in `src/api/http-server.ts` sets one. No response names its server or framework (`Server`, `X-Powered-By`), which is good.

Framing, in Chrome, with `victim` signed in:

- **From another port of the same host** (`localhost:<other>` framing `localhost:<api>/users` and `/api-keys`): the frame loads and runs signed in. It shows `/app/me` as `victim`, the Users list with `colleague` and `victim`, and the API Keys list. The two origins are the same site (ports don't count), so `SameSite=Lax` sends the cookie. A hostile page there can clickjack a User into any UI action.
- **From another LAN host** (`127.0.0.1:<other>`, another site): the frame loads, since nothing forbids it, but every `/app` call is `401 Sign in first`, because `Lax` withholds the cookie from a cross-site frame. Only the cookie default holds; nothing about framing does.

Filed as #170 (medium: a boundary with no defence in depth).

## Probe 2: the session cookie

`Set-Cookie` after a sign-in as `colleague`:

- `APP_URL` on `http:`: `session=<43 characters>; Max-Age=2592000; Path=/; HttpOnly; SameSite=Lax`.
- `APP_URL` on `https:`: the same, with `Secure`.

No `Domain` (host-only, which is right) and no `__Host-` prefix. `X-Forwarded-Proto: https` doesn't add `Secure` (the flag is fixed from `APP_URL` at start, `access-routes.ts:62`), which is right, though `trustProxy: true` is set.

**Not `Secure` on `http:`** is what the guide documents (`docs/guide/delivery-and-access.md`) under ADR 0003's decision to put no TLS terminator in front of port 4320, and the documented `APP_URL` examples are `http:`. So every password at sign-in and every 30-day session crosses the LAN and the tailnet in clear. That decision has no recorded end, which I3 filed as #168 (low) and left the cookie's attributes to this issue. They are recorded here and pinned by the tests above, and not filed a second time. Were it not a documented decision, a session read off the wire would meet the critical definition ("acts as a User").

**Another port of the same host**, in Chrome, `victim` signed in:

- **Reading.** Cookies are scoped by host, not port. Every request to the other port carries `Cookie: session=<victim's token>`, and that token works at `/app/me`. Any other service on `email.home` (another container, a dev server, a compromised UI) holds every signed-in User's session, and with it the log and every Wizzaroo link in it (#116). `__Host-` would not stop this; only a host name of the platform's own does.
- **Planting.** The other port answers `Set-Cookie: session=<a session of colleague's>; Path=/`. It replaces the victim's `HttpOnly` cookie (an HTTP response may), and the UI then runs as `colleague`. A cookie planted on `Path=/app` is sent ahead of the real one, and survives sign-out, which clears only `Path=/` (`access-routes.ts:111`). A `__Host-` name, which needs `Secure` and so `https:`, would stop both.
- **Riding.** A `text/plain` form posted from the other port to `/auth/sign-out` carries the session (same-site, so `Lax` sends it). Fastify parses `text/plain` and sign-out takes any body, so the victim's session is deleted. Every `/app` POST refuses a form body: `text/plain` with 422 (`body.body must be object`) and form encoding with 415. A JSON `fetch` from the other port fails its CORS preflight (no CORS headers are sent), and no API Key was made. So riding reaches sign-out only.

Filed together as #171 (medium).

## Probe 3: 36 MB bodies

`bodyLimit` is 36 MB for the whole server (`http-server.ts:50,90`). Measured once each, in-process:

- `POST /auth/sign-in` with no credential and 36 MB (an email and a long password): read, parsed and answered 401 in 45 ms.
- `POST /auth/sign-out`, which takes no body, with no credential and 36 MB that isn't JSON: answered `400 FST_ERR_CTP_INVALID_JSON_BODY` in 21 ms. The 400 shows that the whole body went through the JSON parser.
- `DELETE /app/api-keys/<unknown id>` as `victim`: the same 400 (25 ms). Without a session it is 401 in 1 ms, because the `/app` hook refuses on `onRequest`, before the body is read. That holds.
- Just over 36 MB at sign-in: `413 message_too_large`, "The request is larger than the 25 MB message limit allows", on a route that sends no message.

The unbounded password itself is #141 (A1), and the throttle keeping a 36 MB email is #123 (A1); they are cited, not filed again. The limit, the bodiless routes and the 413's wording are filed as #172 (low). Volume was not tested (denial of service is out of scope).

## Probe 4: make every route fail

- **Postgres refusing the password.** A second server was built on a pool with the wrong password, and every route the router lists was called as no one, as `wizzaroo` and with `victim`'s session. Every refusal is one of eight bodies: the two fixed 401s (and their empty `HEAD` forms), the fixed `500 internal_error "Something went wrong"`, `/health`'s `503 {"status":"failing","database":"unreachable"}`, and sign-in's 422 for a body that isn't an object. No body holds driver text, SQLSTATE, SQL, the role name, a path, a stack or a version. The error handler logs the error and answers the fixed body (`http-server.ts:127-130`). **Refuted.**
- **A Template that won't compile.** `{{#if}}`, `{{x.[}}`, `{{> partial}}` and `{{foo bar}}` sent to `/v1/templates/preview`, `/v1/templates` and `/app/templates` get 422 with `The template does not render: ` and Handlebars' message: the parse error with the line and a caret, the expected tokens, "The partial partial could not be found" or `Missing helper: "foo"`. It holds only the author's own template and Handlebars' grammar, with no path, version or stack, and goes only to the caller who wrote it, who needs it to fix it. The guide documents that a Template that does not render can't be saved. **Refuted.**
- **A dead SMTP host, and a provider that refuses.** Settings were pointed at an SMTP server that refuses every sender with `550 5.7.1 Relay denied for 10.20.30.40 by smtp-7.internal.provider.example (account 4411)`, then at `127.0.0.1:1` and at `smtp.internal.invalid:587`. A Message sent as `secondApp` and run through the worker reads back on `GET /v1/messages/:id` with `error` set to `Mail command failed: 550 5.7.1 Relay denied…` word for word, `connect ECONNREFUSED 127.0.0.1:1`, and `getaddrinfo ENOTFOUND smtp.internal.invalid`. `describeError` stores the error's message as it is (`send-worker.ts:88`, `lib/http.ts:75-92`). The API Key that sent it, and any other (#118), learns the provider's internal host, address and account, and the SMTP host and port. Filed as #173 (low). The Delivery page's test send gives the User who set the provider the same text (502 `smtp_failed`), which they need. That part is **refuted**.
- **Fastify's own refusals.** `application/xml` and form encoding get `415 FST_ERR_CTP_INVALID_MEDIA_TYPE`, `{` gets `400 FST_ERR_CTP_INVALID_JSON_BODY`, and an empty JSON body gets `400 FST_ERR_CTP_EMPTY_JSON_BODY`, at sign-in with no credential and on `/v1/messages`. The messages are fixed and echo nothing the caller sent. But the error handler passes any Fastify error under 500 through as `{ error: error.code, message: error.message }` (`http-server.ts:118-126`), so the `error` field is not from the platform's own set and names the framework. Filed as #174 (low).

## Checks every scope issue carries

Applied:

- **Every refusal comes from a closed set:** holds when Postgres refuses (probe 4a) and for a Template that won't compile (4b). It is broken by Fastify's own codes (#174), by the SMTP text in a Message's error (#173), and by the 413 naming the message limit on every route (#172).
- **Refusals give nothing away:** with Postgres down, no credential, a key and a session get only fixed bodies, so a dead database tells a caller nothing about what exists. The 401 bodies are B1's three.
- **Nothing is left to a collaborator to bound:** the body limit is one 36 MB figure for every route (#172), and the cookie's protection from other services on the host is left to the browser's `Lax` default (#170, #171).
- **Internal headers are trusted only when the server set them:** `trustProxy: true` honours `X-Forwarded-Proto` and `X-Forwarded-Host`. Sent from outside, neither adds `Secure` to the cookie nor changes the API document's `servers` origin, which come from `APP_URL`. Refuted for this surface. `X-Forwarded-For` is A1's (#114).
- **Odd input stops above the database:** a 36 MB body stops before the database (it is parsed, not stored). Odd bodies (XML, a form, broken or empty JSON) stop at Fastify with a 4xx, never a 500.
- **Run the probes against a real Postgres:** yes, and Chrome for the framing and cookie probes.
- **A test that passes either way proves nothing:** each `it.fails` was run once as a plain `it` and failed on its property assertion: the missing-headers map for `{}`, `undefined` for HSTS, the framed text for `undefined`, no `secure` property, `session` for `/^__Host-/`, the stolen token in the other port's cookies, `colleague` for `victim` after planting, 401 for 200 after the sign-out form, 401 and 400 for 413 at sign-in and sign-out, the provider's reply for the redacted error, and `FST_ERR_` in the refusals.

Not applied, and why: **an idempotency key is bound to its payload and owner** (S2), **a secret is sealed or hashed where it is kept** (I3, D3), **logs are a copy of the data** (D2; the error handler's log line is D2's #126), **middleware that matches by path matches by segment** (B1), and **configuration fails closed** (I3; the `http:` `APP_URL` is #168).
