# I2a: rate limiting, probed and quantified

The findings note for scope issue #103 (I2a) of [the first pen-test round](../../product-requirements-document/pen-testing.md). It answers H1's figures and H11's API-wide half, and gives I2b (#104) the numbers for [the request-rate pre-condition](../../product-requirements-document/pen-testing.md#pre-condition-the-request-rate-policy-before-the-gate). It names exploit chains, so **keep it private on the same terms as the PRD**.

- **Read against:** commit `2f11db2`, and the [fixtures](../fixtures.md) by handle. No credential appears here.
- **The probes** are the tests under `pen test I2a (#103): rate limiting, probed and quantified` in `src/pen-test/probes/i2a.test.ts`. They run in the gated run against a real Postgres and Mailpit from [the probe world](../../../src/pen-test/probes/probe-world.ts). Every sign-in probe builds a server of its own, as production builds it, so its throttle starts empty. A confirmed gap is an `it.fails` for the property that should hold beside a `today_…` test pinning what happens now. A refuted probe is a plain passing test.
- **By arithmetic, not load.** The PRD puts denial of service and volume testing out of scope. Each probe sends 101 requests one after another, in-process (`inject`: no network, no TLS), and times them; everything past that is arithmetic. Times are from an Apple M5 Max. A1's and K1's figures are reused, not re-measured: scrypt at about **187 guesses a second** through the libuv pool, and intake at about **345 Messages a second** from one key ([A1](A1.md), [K1](K1.md)). This run's figures agree with them.
- **Already filed, cited not repeated:** #114 (a fresh `X-Forwarded-For` beats the sign-in throttle), #122 (a spray across emails is never throttled), #123 (the throttle's map never forgets), #133 (one key queues about 345 Messages a second), #137 (the preview has no cost bound), #141 (sign-in fields unbounded), #142 (the throttle is lost on restart).

## What limits anything today

There is one limit in the server: the sign-in throttle, 10 failures per `${request.ip}:${normalisedEmail}` in 15 minutes, in one process's memory (`src/access/access-routes.ts:24-43,68`). No rate-limit plugin is a dependency or registered (`package.json`, `src/api/http-server.ts:84-211`). No answer in this run, a `429` included, carried a `RateLimit-*`, `X-RateLimit-*` or `Retry-After` header.

## 1. `POST /auth/sign-in`

- **One User, one address (1a).** The throttle works as A1 found: ten `401`s, then `429` for the other 91. A blocked try is refused before `verifyCredentials`, so the 91 cost no scrypt (2.3 ms each on average across all 101). The `429` has no `Retry-After`, so a client can only read "Try again in 15 minutes" from its message.
- **Many emails, one address (1b).** 101 × `401`, 21.7 ms each: every one ran scrypt. The key holds the email, so an address naming a new email each try is never throttled. That is #122, here at 101 tries rather than 11. One at a time it is 46 guesses a second; in parallel, A1's 187 a second, which is all four libuv threads, so one address can hold every sign-in on the platform behind its own.
- **One User, many addresses (1c).** 101 tries for `colleague`, each from its own socket address (`198.51.100.1`-`.101`, set as `inject`'s `remoteAddress`, no header): 101 × `401`. Ten more from the first of those addresses answer nine `401`s, then `429`: that address's own throttle. So the throttle is per address and email and **nothing counts per account**: each address brings its own 40 guesses an hour. That is not #114 (no header is sent, and `trustProxy: false` leaves it as it is) nor #122 (one email, not many). Filed as **#163**.

## 2. `POST /v1/messages`

101 × `202` from `secondApp`, 2.4 ms each, no limit reported. This is #133 at 101 rather than 20 sends; the rate agrees with K1's 345 a second (2.9 ms), which this note keeps as the figure. Each send left a 252-byte `messages` row (a short text Message, before indexes) and a 200-byte `pgboss.job` row, and the key's `last_used_at` moved. A send by Template renders on accept in the `api` process, before the `202`: 4.6 ms each for `second-app-order-shipped`, about 220 a second.

## 3. `POST /v1/templates/preview`, and the API besides

101 previews from `secondApp`, 101 `GET /v1/templates` from `secondApp` and 101 `POST /app/templates/preview` from `victim`'s session: all `200`, no limit reported. Each `/v1` call, the reads included, is one `UPDATE api_keys SET last_used_at` (K1). Nothing limits any request but a failed sign-in: not reads, not writes, not previews, not `/app`. Filed as **#162**. The designer previews after a 400 ms pause in typing (`src/ui/preview-scheduler.ts:6`), so a User at work makes at most about 150 previews a minute; that is the floor for any `/app` figure.

## 4. `POST /app/settings/test`

101 test emails from `victim`'s session to 101 addresses on the fixtures' `.invalid` domain: 101 × `200`, 101 "Test email" messages in Mailpit, one to each, and no new row in `messages`. The route reads the Settings and calls `sendEmailOverSmtp` there and then (`src/settings/settings-routes.ts:61-103`), which opens a new SMTP connection per call (`src/sending/delivery.ts:31-62`). So it is the one send path outside the queue: the worker's pace doesn't apply, nothing bounds how many run at once, and the only trace is the request log's URL line. The subject and body are fixed; `to` is the caller's. Filed as **#164** (low: it needs a User session and carries no content of the caller's).

## 5. What one key and one address can do, by arithmetic

### The SMTP provider's quota

Delivery is one `send-message` worker taking one job per fetch (`batchSize: 1`, `src/index.ts:83-86`). pg-boss 12.38 only fetches again at once in burst mode, which isn't configured, so with nothing waking it the worker fetches every 2 s: a floor of **0.5 Messages a second, 1,800 an hour** (K1). Each Message may have 150 recipients (`src/sending/message-routes.ts:28-30`), so the worker can hand the provider 75 recipients a second, 270,000 an hour.

The provider isn't named in the code. The guide names Amazon SES first; a new SES production account starts at **50,000 recipients a day and 14 messages a second**. Against that:

| One key, today                          | Messages                                             | Recipients (×150) | SES's 50,000 a day                              |
| --------------------------------------- | ---------------------------------------------------- | ----------------- | ----------------------------------------------- |
| Intake, one second                      | 345                                                  | 51,750            | more than a day's quota                         |
| Intake, one minute                      | 20,700                                               | 3.1 million       | 62 days of quota                                |
| Delivery at the worker's floor, an hour | 1,800                                                | 270,000           | the day's quota in 11 min                       |
| `/app/settings/test`, one session       | about 3 a second (0.3 s SMTP each), more in parallel | 1 each            | 14 a second reached by about 5 parallel callers |

Once the quota is spent, every send fails, Wizzaroo's resets and Invites included, until the provider's day rolls over: three retries with backoff, then `failed`.

### The queue

The queue is one, shared, first in first out. One minute of one key's intake (20,700 Messages) is 11.5 hours of the worker's floor (#133). This run's 101 sends alone are 3.4 minutes of it, and a Wizzaroo reset queued after them waits that long.

### Postgres

Each send is one `messages` row (252 bytes for a short text Message, up to 25 MB of body and attachments, `src/sending/accept-message.ts:233-244`), one `pgboss.job` row (200 bytes), one `last_used_at` update, and an Idempotency-Key lookup when one is sent: three writes. At 345 a second that is about 1,000 writes a second and, for short Messages, 160 KB of row a second, 560 MB an hour before indexes and WAL, kept for Retention's 90 days. With large Messages the network is the bound: at 1 Gbit/s about 4 Messages of 25 MB a second, 100 MB a second, 360 GB an hour, also kept 90 days. `pg`'s pool is the default 10 connections (`src/lib/database.ts`), shared by the UI, `/v1` and sign-in, so callers in parallel queue for it. Reads write too: 510 `GET`s a second is 510 updates a second of one `api_keys` row.

### CPU

The `api` is one Node process (ADR 0003, ADR 0004): one event loop, and four libuv threads for scrypt.

- **Sign-in:** 187 scrypts a second fill the four threads. One address naming a new email each try (#122), or many addresses naming one (#163), can take all of them; a User signing in waits behind.
- **Preview:** a small preview is 1.1 ms of event loop. S3's 70-character nested `{{#each}}` renders 7.96 M characters in 687 ms, and its `<body` scan is quadratic (#137). One key sending one such preview after another keeps the event loop busy nearly all the time; nothing else, the UI, `/v1` and sign-in included, is answered meanwhile. A send by Template renders the same way on accept.
- **Body parsing:** the 36 MB `bodyLimit` (`src/api/http-server.ts:50`) is parsed on the event loop; a 35 MB sign-in took 110 ms (A1, #141).

## 6. What the limit should key on

`buildHttpServer` sets `trustProxy: true` (`src/api/http-server.ts:91`), so Fastify makes `request.ip` the left-most `X-Forwarded-For`. A probe hook on a server built as production read, for `GET /health`: no header, `request.ip` and the socket both `127.0.0.1`; with `X-Forwarded-For: 203.0.113.7, 198.51.100.9`, `request.ip` `203.0.113.7` and the socket still `127.0.0.1`. That is every route, not just sign-in, so any limit keyed on `request.ip` today is #114 again. Fastify's request log records `remoteAddress` from `request.ip` too, so the log carries the forged address as well (for D2 and I1; it has #114's fix).

ADR 0003 puts nothing in front of the app: no reverse proxy, no TLS terminator; callers are devices on the home network and tailnet, each with an address of its own. So nothing legitimate ever sets `X-Forwarded-For`, and the socket's address is the caller's. The key, therefore, is the socket's address with `trustProxy: false`. Details are in [Numbers for I2b](#numbers-for-i2b).

## Numbers for I2b

Each proposal gives its basis; the figures are I2b's to set. In every row a refusal is the same `429` whichever limit fired, with `Retry-After` (which today's sign-in `429` lacks) and RateLimit headers.

**The key (H1), one decision with `trustProxy`:** the socket's address, `request.socket.remoteAddress`, with `trustProxy: false`, so `request.ip` is that address. Fold IPv4-mapped IPv6 (`::ffff:a.b.c.d`) to its IPv4 form. Key on the whole address, not a /64: every caller is a home or tailnet device with an address of its own (ADR 0003), and a /64 of a tailnet's IPv6 range would put many devices on one key. ## Checks every scope issue carries

Applied:

- **Internal headers are trusted only when the server set them.** `X-Forwarded-For` sets `request.ip` on every route (probe 6). Fails: #114.
- **Nothing is left to a collaborator to bound.** Sending per key is bounded by Postgres (#133), the test email by the SMTP provider (#164), the preview by the CPU (#162, #137), guessing by scrypt (#122, #163). Fails.
- **Refusals give nothing away.** The sign-in `429` is one body whatever the email (A1, probe 7); here the 91 `429`s in probe 1a were all the same. The PRD's "one `429` whichever limit fired" can only be checked once there is more than one limit. Holds for the one there is.
- **Every refusal comes from a closed set.** No probe here met a `5xx`; every answer was `200`, `202`, `401` or `429`. Holds.
- **Run the probes against a real Postgres.** Every probe does, and the test emails go through a real Mailpit.
- **A test that passes either way proves nothing.** Each `it.fails` was run as a plain `it` and failed on its property assertion: `expected [ 401, 401, … ] to include 429` (1b, 1c), `[ 202, … ]` (2), `[ 200, … ]` (3a, 3b, 4), and `expected '203.0.113.7' to be '127.0.0.1'` (6). None failed on setup.

Not applied, and why:

- **An idempotency key is bound to its payload and its owner.** S2's; nothing here depends on one.
- **Odd input stops above the database.** S1's and A1's; the sign-in fields' length is #141.
- **A secret is sealed or hashed where it is kept.** No limit keeps a secret. The per-account key should be a hash of the email, which the table above says.
- **Logs are a copy of the data.** D2's. Noted for it: the request log's `remoteAddress` is `request.ip`, so it records a forged `X-Forwarded-For` (probe 6).
- **Middleware that matches by path matches by segment.** B1's; no limiter exists to be matched.
- **Configuration fails closed.** I3's, and the pre-condition's: once limits are built, no policy means no start. Noted for I3: `trustProxy` is hard-coded, not configuration.
