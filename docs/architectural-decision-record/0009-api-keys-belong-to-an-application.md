# API Keys belong to an Application

[ADR 0005](0005-templates-and-sending-only.md) gave every API Key every power of the `/v1` API, and [ADR 0008](0008-the-email-platform-is-inside-wizzaroos-trust-boundary.md) let that stand "until the round's findings say otherwise". The first pen-test round says otherwise. With the second Application's key it replaced Wizzaroo's reset Template so the next reset link also went to a server of its choosing, and deleted the Header every Wizzaroo email uses (#113, critical); sent as Wizzaroo's no-reply address and as an address no one configured (#117); and read a Wizzaroo Message's recipient, subject and status by its id (#118). The same gaps let one Application's Idempotency-Key find another's Message (#119, #120). Nothing told keys apart: the `/v1` hook authenticated a key and threw the row away.

## Decision

- **An Application is a row** (`applications`: id, unique name). Every API Key belongs to one (`api_keys.application_id`, required; an Application with keys can't be deleted). A User names it when making a key, in the UI or with `pnpm cli apikey:create <name> --application <name>`; a new name makes a new Application. A key made with none gets a new Application named after the key, so it reaches nothing that already exists.
- **Templates, Headers, Footers and Configurations may belong to an Application** (`application_id`, null for none). A key makes Templates, Headers and Footers for its own Application, and can replace or delete only its own Application's. Another Application's, or one owned by none, answers `404` exactly as an unknown id does, so a refusal doesn't say the row exists. A key can still read and send with any Template, Header or Footer.
- **A key sends only from its Application's addresses.** The from address a send ends up with (the request's, else the Template's Configuration's, else the default in Delivery) must be the address of one of its Application's Configurations or the default from address; every address Nodemailer would read in it is checked, case-insensitively. Anything else is refused with `422` (`field: "from"`). It is checked after the from is resolved, so another Application's Template or Configuration can't be used to send as it. Only the address is bound; the display name stays free text. A Configuration owned by no Application gives no key its address.
- **A Message records the Application and the key that sent it** (`messages.application_id`, `messages.api_key_id`; the key's is set to null when the key is deleted). A key reads only its own Application's Messages: any other answers `404` as an unknown id does. An Idempotency-Key is unique within the Application that sent it, so another Application's key is never found and never stops its email.
- **Users keep full rights** over every row, through `/app` and the UI: they choose each Template's, Header's, Footer's and Configuration's Application (or none), and list, rename and delete Applications. A User's test send is not a key's and is not bound to an Application's addresses. Who may do what among Users is ADR 0005's and a separate finding's.
- **An existing install keeps working.** The migration (`0006`) makes one Application when the install already has keys, Templates, Headers, Footers, Configurations or Messages, named after the only key when there is exactly one (a key is usually named after the application using it) and "Existing application" otherwise, and gives it every one of those rows. Users can rename it under **API keys**. A fresh install starts with none. `pnpm cli templates:add-built-ins --application <name>` gives the Built-in emails, their Header, Footer and Configuration to an Application.

## Consequences

- This supersedes the "API Keys with no scope" part of ADR 0005 and ADR 0008. The second-Application gate in ADR 0008 still stands: scoping keys is what the round asked for, not the end of the round.
- Wizzaroo's key must belong to the Application that owns the Wizzaroo Templates and Configuration, or its sends from `no-reply@wizzaroo…` are refused. The migration gives it that on an existing install; a new one runs `templates:add-built-ins --application <name>` with its key's Application.
- Two Applications that share a from address each need a Configuration of their own naming it.
- Reads stay open: any key can list and read every Template, Header and Footer, and send with it, as long as the from address is its own. Who last changed a Template, Header or Footer is still not recorded (#132).
- Considered and rejected: refusing another Application's row with `403`, which tells a key it exists; and leaving Configurations owned by no Application usable by every key, which would let a User's forgotten choice open an address to all of them.
